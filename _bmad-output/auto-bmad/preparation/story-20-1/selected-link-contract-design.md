Finalize validates canonical UUIDs/key/hash/signature/times, then takes the fixed replay advisory lock for tenant+file+correlation, rechecks and locks current membership/roles/source/link/file/object using the internal helper, and compares every supplied owner/purpose/storage field to the newly derived target. Response loss requires a fresh access/attestation/correlation; it does not replay a previously minted success URL.

## Locking and linearization

The authority point is the finalizer transaction's successful locked revalidation and audit commit. The prepare transaction ends before remote Storage signing; it cannot lock authority through network I/O. A change committed before finalizer revalidation must be denied, even when prepare passed. A revocation begun after finalizer holds relevant locks serializes after its success; it may still occur before the HTTP response is delivered and does not cancel the issued bearer URL. This bounded linearization is the precise current-authority promise.

Use `FOR SHARE`, not `FOR KEY SHARE`, on every row whose nonkey archive/status/role/association affects the decision: membership, all current membership_roles ordered by ID, required source ancestors before source row, exact file_link, files row, quote_version_attachments when used, and the matching storage.objects metadata row. Membership is locked before child roles so existing role-replacement/provisioning paths must be checked for compatible ordering; role removal/primary-role change/disable must conflict with these locks. Gather candidate IDs without authorizing, acquire locks in the fixed table/row order, then read and validate all fields after locks using READ COMMITTED statements. If a source/link/role row disappears during acquisition, fail closed. Row locks protect only selected existing authority: absence is never a grant.

Fixed order for new wrappers: replay advisory lock(finalize only), tenant_membership, membership_roles(ID order), CRM customer/facility/contact ancestors if required, quote/quote_version/quote_acceptance ancestors if required, calculation/job selected header if required, file_links, files, quote_version_attachments if required, storage.objects. Same helper order at prepare/finalize. After source/link locks, reconcile **every current relationship reference against the exact graph gathered and locked**: contact.customer_id/optional facility_id, facility.customer_id, acceptance.quote_version_id/quote_id, version.quote_id and selected link owner/type/purpose/file. Validate optional-null transitions as well. Any changed relationship fails closed with retryable SERVER_ERROR; do not authorize a replacement parent obtained by an unlocked lookup or acquire that replacement out of order. A fresh command retries full acquisition with a fresh prepare/proof. This prevents a contact reassignment from locked facilityF1 to unlockedF2 from authorizingF2 whileF2 is concurrently archived. Examine existing writer lock sequences before implementation and test lock-race/deadlock behavior; a deadlock/serialization/timeout is retryable failure with no returned URL, never permission to skip locks. Existing writers are not silently rewritten. No blanket locks on unrelated tenant data. No lock protects actual bearer consumption after final audit.
