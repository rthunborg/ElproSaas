# Story 7.2: Idempotent Accept Quote And Create Job Command

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a tenant admin,
I want acceptance and job/order creation to happen together safely — one atomic, idempotent, audited transaction that records the acceptance, flips the quote version lifecycle to `accepted`, creates the minimal job/order, and writes all lifecycle/audit events,
so that the system never leaves a half-accepted quote, a duplicate job, or a forked customer commitment on a retry, double-submit, or mid-transaction failure.

## Acceptance Criteria

**AC1 — Atomic accept-and-create-job (happy path)**
**Given** a valid sent quote version and acceptance input
**When** `acceptQuoteAndCreateJob` runs
**Then** it records the `quote_acceptances` row, updates the quote version lifecycle `sent → accepted`, creates a minimal `jobs` record with immutable source refs (accepted version id + acceptance id), writes `quote_events` (`accepted`), `job_events` (`created`), and one `audit_events` row, and commits ALL changes together (architecture §13 steps 1-10).

**AC2 — Idempotent retry / duplicate prevention**
**Given** the same acceptance request is retried, double-submitted, or a create-job is attempted after an acceptance already exists for the quote version
**When** the command runs again
**Then** it returns the EXISTING acceptance + job ids idempotently
**And** it creates NO second acceptance, NO second job, NO second lifecycle transition, and NO duplicate `quote_events`/`job_events`/`audit_events` rows (enforced by DB uniqueness constraints + row locks INSIDE the RPC — never a client-only check).

**AC3 — Atomicity / no partial state on failure**
**Given** any transaction step fails (a constraint violation on the job insert, an event/audit write, or a raced lifecycle flip)
**When** the command returns an error
**Then** NO partial state remains committed — no acceptance, no lifecycle change, no job, no event (NFR20 — commit-or-rollback-together, a behavioral rollback proof, not a field-exists check).

**AC4 — Sent-precondition + cross-tenant/anon rejection (server truth)**
**Given** a draft/accepted/rejected/expired/superseded/cross-tenant quote version, or an anonymous caller
**When** `acceptQuoteAndCreateJob` is attempted
**Then** the command + RPC reject it with a user-safe error re-validated server-side (a non-sent state ⇒ a stable lifecycle rejection; a foreign `quote_version_id` or evidence file id ⇒ `TENANT_ACCESS_DENIED`, no existence disclosure; anon ⇒ `UNAUTHENTICATED`) — verified under the caller's RLS + composite same-tenant FKs, BEFORE any write, matrix FINALIZED against the landed Epic 6 state machine (acceptance ONLY on `status = 'sent'`).

**AC5 — Adjusted accepted price gated + öre discipline (carried from 7.1, re-enforced in the transaction)**
**Given** the accepted price differs from the frozen source sent total
**When** the acceptance is recorded inside the transaction
**Then** an explicit adjustment reason/evidence is REQUIRED (re-validated server-side — the client cannot bypass), the delta is computed with `@/lib/money` in öre (never re-derived ad hoc), and accepted price + source sent total persist as integer öre (`bigint`, canonical `isOreAmount`/`ORE_AMOUNT_MAX` guards).

**AC6 — Immutable job source references**
**Given** a job is created from an acceptance
**When** the job row persists
**Then** it stores the accepted `quote_version_id` + `quote_acceptance_id` as immutable source references (composite same-tenant FKs, ON DELETE RESTRICT), plus `customer_id`/`facility_id`/`contact_id` (carried from the accepted version), a Phase-A `status` default `'created'`, `title`, and planned dates — and NO cost/margin/invoice/Fortnox/time-material/deviation/field-worker column.

## Scope Boundary (read first — this is a multi-story epic)

7.2 lands **the transaction**. Precisely what belongs where:

- **7.1 (DONE, do NOT rebuild):** the migration `20260709120000_acceptance_to_job_model.sql` (creating `quote_acceptances`/`jobs`/`job_events` + their uniqueness constraints, composite FKs, RLS, `TENANT_TABLES` enrollment); the `captureQuoteAcceptance` single-row-write command; the pure `acceptance-price.ts` delta module; the `quote_acceptance` owner-type activation; the sent-version acceptance-capture form. **All frozen. 7.2 REUSES these, never re-creates them.**
- **7.2 (THIS story):** the narrow atomic `accept_quote_and_create_job` RPC (ADR-A009) — the idempotent, transactional multi-record write (acceptance INSERT + `sent → accepted` lifecycle flip + job INSERT + `quote_events`/`job_events` + audit, row locks on the version + parent quote, uniqueness-backstopped duplicate prevention, existing-record idempotent return, rollback, concurrency); the `acceptQuoteAndCreateJob` server command that pre-validates then calls the RPC; the `ACCEPTANCE_ALREADY_RECORDED` stable code IF a distinct 7.2 conflict must surface; wiring the acceptance form to this transactional path so a capture on a sent version now ACCEPTS + creates the job (superseding 7.1's capture-only call at the acceptance UI). The transactional path OWNS the acceptance write mechanism from here on.
- **7.3 (LATER, do NOT build here):** the job/order detail + list UX, source traceability, `job`/`job_evidence` owner-type activation, allowed job edits. 7.2 creates `jobs` rows through the RPC; 7.3 surfaces them.
- **7.4 (LATER, do NOT build here):** the accepted-state DB immutability trigger/constraints + command lock code + correction-boundary UI. 7.2 flips a version to `accepted` and creates the acceptance/job; 7.4 LOCKS them. 7.2 must leave the accepted record + job source refs shaped so 7.4 can add the immutability trigger ADDITIVELY (same pattern as 6.1 leaving the door open for 6.4).

**Decision needed from 7.2 (do not defer silently) — does 7.2 reuse or supersede 7.1's `captureQuoteAcceptance`?** Two shapes: (a) 7.2's RPC OWNS the acceptance INSERT inside the transaction (the acceptance write moves into the RPC alongside the job/lifecycle/events), and the acceptance form now calls `acceptQuoteAndCreateJob` instead of `captureQuoteAcceptance`; or (b) 7.2 keeps 7.1's standalone `captureQuoteAcceptance` for a "capture-only, no job yet" path AND adds a separate accept-and-create-job path. **Prefer (a):** architecture §13 makes acceptance + job creation ONE transaction; the epic AC1 ("records acceptance, updates lifecycle, creates a job, writes events, commits together") and the atomicity/idempotency ACs (AC2/AC3) require the acceptance INSERT to be INSIDE the same transaction as the job insert (an acceptance persisted by a separate 7.1 command then a job created by a second command is a two-step non-atomic sequence that violates NFR20 and the "no client-side multi-step mutation sequence" security constraint). So the acceptance INSERT belongs in the 7.2 RPC. 7.1's `captureQuoteAcceptance` command MAY remain exported (its INT tests stay green) but the LIVE acceptance UI path (`AcceptanceCaptureForm` → `captureQuoteAcceptanceAction`) is re-pointed at `acceptQuoteAndCreateJob`. If the owner wants a capture-without-job path preserved, that is a documented decision — record it; the deliverable default is (a).

### The transaction — the highest-risk Phase A command (read this before writing the RPC)
- **Idempotency has TWO forms (Testability note 2) — both MUST be proven.** (a) *Sequential retry:* call twice with the same input; the second returns the SAME acceptance + job ids and creates NO second row. (b) *Concurrency:* two parallel `Promise.all` accepts of the same sent version (sleep-free per the harness rule) ⇒ exactly ONE creates, the other idempotent-returns the winner's records OR fails cleanly with `COMMAND_CONFLICT`/`ACCEPTANCE_ALREADY_RECORDED` — NEVER two jobs. The row lock on the version + parent quote (`FOR UPDATE`) + the `unique (quote_version_id)` / `unique (quote_acceptance_id)` constraints are the MECHANISM. A test that only proves the happy-path single accept is NOT evidence of idempotency.
- **Atomicity is a BEHAVIORAL rollback proof (Testability note 3), not a field-exists check.** Inject a failure at a step boundary INSIDE the transaction (e.g. force the job insert to violate a constraint, or the event write to fail) and assert the END STATE is empty — no acceptance, no lifecycle change, no job, no event. The single RPC transaction boundary makes this directly testable below the command layer (the epic-5/6/8 RPC-rollback precedent). Field-exists assertions on the happy path do NOT prove NFR20.
- **RPC-swap coverage inversion (Testability note 10, epic-8 retro):** the LIVE acceptance UI path moves from `captureQuoteAcceptance` to `acceptQuoteAndCreateJob`. Re-check that the idempotency/privilege/cross-tenant negatives target the LIVE entry point (`acceptQuoteAndCreateJob`), not the now-superseded 7.1 capture command. A coverage inversion is easy to miss after an RPC swap.
- **Determinism (H1, R-715):** the RPC takes explicit `p_accepted_at` (the accepted moment) + the injected command timestamp — NO internal `now()` for the accepted instant (a `default now()` on an event's `occurred_at` is fine only where the story does not assert on it; prefer passing the injected instant). Unit-pin the timestamp-injection adapter (7.2-UNIT-01, mirrors mark-sent's injected timestamp).

- [x] [Review][Decision][Med] RPC never receives the `p_command_at` command-timestamp param — the epic H1 contract is only partially wired — The epic Technical Note (epics.md:1470) and Task 2.6 call for the RPC to accept an explicit command-timestamp param for lifecycle determinism. `buildAcceptAndCreateJobRpcArgs` computes `p_command_at: clock.now().toISOString()` and `accept-and-create-job-timestamp.test.ts` asserts it, but the actual `rpc.rpc("accept_quote_and_create_job", {...})` call (accept-and-create-job.ts:445-460) omits it and the RPC SQL signature (20260710120000 migration) has no `p_command_at` parameter — so the computed value is dead (reaches the unit assertion, never the DB). Functionally low-risk: every persisted instant (`accepted_at`, `quote_events.occurred_at`, `job_events.occurred_at`) uses the explicit `p_accepted_at`, and audit timing comes from the injected `ctx.clock` via `writeAuditEvent`, so no wall-clock leaks — but the epic's "explicit command-timestamp param" contract and the intent of 7.2-UNIT-01 (pinning an arg that shapes the real transaction) are not honored end-to-end. Recommended: fix: remove the dead `p_command_at` from `buildAcceptAndCreateJobRpcArgs` and its unit assertion (all persisted instants derive from `p_accepted_at`/`occurred_at` + the audit clock, so determinism holds) OR — if the epic H1 param contract must stand — add `p_command_at` to the RPC signature and thread it into the `.rpc()` call; prefer removing the dead arg so the unit test no longer implies an end-to-end wiring that does not exist. **RESOLVED 2026-07-07 (chosen direction: remove the dead arg):** dropped `p_command_at` (and the now-unused `clock` param + `CommandClock` import) from `buildAcceptAndCreateJobRpcArgs` in `src/server/commands/quotes/accept-and-create-job.ts`; the adapter now returns `Omit<AcceptAndCreateJobRpcArgs, "p_tenant_id">` with no `p_command_at`. Determinism still holds: all persisted instants derive from the explicit `p_accepted_at`, audit timing from the injected `ctx.clock` via `writeAuditEvent`.
- [x] [Review][Defer][Low] Parent-`quotes` row read/lock has no `if not found` guard — fail-closed only incidentally via a downstream NOT NULL [supabase/migrations/20260710120000_accept_quote_and_create_job.sql:940] — The parent-quote read (`select q.customer_id, q.facility_id, q.contact_id ... for update`) has no `if not found`/null guard, unlike the version read directly above it which raises `QV409` on not-found. If the parent quote were not visible (an RLS race), `v_customer_id` would be NULL and the job INSERT would rely on `jobs.customer_id NOT NULL` (7.1 model) to raise 23514/NOT-NULL and roll back. This is fail-closed (no partial state; NFR20/AC3 hold), but the safety is incidental to a downstream constraint rather than an explicit precondition check; a symmetric `QV409` on a missing parent would be the honest signal. Not reachable today given the version→quote FK guarantees co-existence — deferred, pre-existing robustness gap.
- [x] [Review][Defer][Low] Idempotent re-entry on an already-`accepted` version still runs the adjusted-price + evidence gates BEFORE the RPC short-circuit [src/server/commands/quotes/accept-and-create-job.ts:414] — The command relaxes the sent-state gate to let `accepted` flow through, but `computeAcceptanceDelta` + `reasonRequired` and the evidence-ownership check run before the RPC on the re-entry path too. A true identical-input retry is harmless (delta 0 ⇒ no reason needed), but a re-attempt on an already-accepted version supplying a *different* price with no reason surfaces `VALIDATION_FAILED` instead of the idempotent existing-record return the RPC would otherwise give under the lock. AC2's "same acceptance request" framing makes divergent-input re-entry an edge, not a strict violation; the INT/E2E idempotent tests only exercise identical-input retries, so this path is unproven — deferred as a minor edge/robustness note.
