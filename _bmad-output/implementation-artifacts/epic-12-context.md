# Epic 12 Context: Tenant Provisioning and Onboarding

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Make ElproSaas deliverable to independent companies without engineering intervention: an authorised platform operator can create a new tenant, establish its baseline, invite the first Admin, and that Admin can complete the existing configuration needed for a working tenant. The flow must preserve pooled-tenancy isolation throughout and provide an end-to-end proof with a second tenant.

## Stories

- Story 12.1: Platform Operator Identity and the Provision-Tenant Command
- Story 12.2: Operator Console
- Story 12.3: First-Admin Onboarding Checklist

## Requirements & Constraints

- Provisioning is internal, contract-after-signing work only. No public self-registration route, UI, copy, or future-facing signup seam may ship.
- ElPro tenants are companies/legal entities, not individuals. V1 accepts Swedish non-personal legal entities only (`SE` + normalized checksum-valid ten-digit organisation number), rejects personnummer-shaped identities and sole proprietorship tenants, and treats formatting/name variations as the same identity. Archived/inactive tenants retain the durable identity reservation. This does not restrict CRM end customers, which may be companies or private individuals without personnummer capture.
- The flow creates a tenant, applies the exact immutable catalogue baseline, and creates the invited first-Admin membership atomically before any Auth Admin call. The authoritative execution catalogue is migration-owned, insert-only database data with baseline ID, monotonic version, canonical content, and content hash; no runtime role has DML. Published rows are never edited, changes insert a new version, preview returns all three identity fields, and execution reloads/re-hashes the exact row or returns `PREVIEW_STALE`. TypeScript `TENANT_PROVISIONING_BASELINES` is only the preview/build-time mirror and mandatory DB/TypeScript coherence tests keep it exact. This supersedes TypeScript-only execution authority. Dual idempotency uses request UUID + canonical request hash plus canonical organisation identity: same ID/hash returns the existing tenant/current state after provider-free reconciliation; same ID/different content returns `IDEMPOTENCY_CONFLICT`; different ID/same identity returns `ALREADY_PROVISIONED`; no replay silently updates.
- Use strict `schema_version = 1`, never free text. Required fields are request ID, legal identity/name, first Admin, baseline profile/version, subscription plan/status, included users, additional-user price in integer öre, and contract start. Optional fields are VAT, contacts/address, contract/trial end, billing reference, structured commercial overrides, Reply-To, known active modules/approved flags, and supported profile fields. Unknown/version-mismatched fields fail explicitly; future recognized fields may appear as deferred but block execution and are never stored for later.
- The selected migration-owned database catalogue row applies `sv-SE`, `Europe/Stockholm`, `SEK`, approved existing VAT/tax-profile references, terms placeholders/sign-off warnings, approved number-series defaults, and conservative display defaults. Requests select only baseline ID/version and cannot submit arbitrary baseline values. V1 rejects logo/files, Fortnox setup, schedules/calendar, extra initial users/imports, pending modules, arbitrary flags, raw tax rates, final legal terms, free-text agent instructions, and secrets.
- Preview is stateless and writes no DB, audit, Auth, or preview row. It returns the schema/request IDs, normalized identity, validations/warnings, action, exact baseline ID/version/content hash, every proposed value, first Admin, proposed audit events, unsupported/deferred fields, and server hash. Execution resubmits the original request/hash with explicit approval; mismatch rejects and missing/changed catalogue content returns `PREVIEW_STALE`. Approver comes only from the authenticated allow-listed `auth.uid()`; one operator may preview and approve.
- First-Admin email normalization trims, applies Unicode NFC, IDNA-normalizes and lowercases the domain, and lowercases the local part; plus-addressing is preserved, dots/tags are not stripped, and display-name/comment/malformed/multiple-address syntax is rejected. Optional VAT is trimmed, uppercased, stripped of spaces, and accepted only as `SE` + the matching normalized ten-digit organisation number + `01`; its canonical value is stored but never substitutes for organisation identity.
- Commercial terms are tenant data, never application logic. Store subscription status/plan, included users, additional-user price, enabled modules/feature flags, dates, billing reference, and commercial overrides; do not hardcode prices, discounts, or special terms.
- An operator may see only tenant identity, provisioning status, created date, and first-Admin state. The console and provisioning path must never expose or traverse tenant business data; unauthorised and cross-tenant attempts receive generic denials.
- A newly invited first Admin reaches a working state by completing company settings, VAT/display settings, quote terms (with the carried sign-off warning), work roles/pricing baseline, and user invitations. Completion is derived from real server state, not click tracking.
- Required evidence includes atomic rollback, idempotency, operator/forged-claim/absent-claim denials, console data-exposure negatives, tenant-isolation negatives, audit assertions, checklist derivation and dismissal/resume tests, plus an automated or scripted provisioning-to-working-state proof.

## Technical Decisions

- Keep the pooled Supabase tenancy model. `platform_operators` and the migration-owned `tenant_provisioning_baselines` catalogue are narrowly enumerated platform-scoped exceptions: operator identity permits self-read only, and the catalogue is insert-only migration data with no runtime DML. All other new data remains tenant-scoped.
- Gate operator access with a hardened `is_platform_operator()` DEFINER helper: fixed empty search path, schema-qualified references, explicit authorisation, revoked PUBLIC access, and standing negative tests.
- `provision_tenant` is the sole public authenticated provisioning writer and the one Epic 12 SECURITY DEFINER RPC. Server provisioning code invokes it under the operator's normal Supabase Auth JWT; the function derives and rechecks current allow-listed `auth.uid()` and every mutating action also verifies a server-minted, domain-separated HMAC-SHA-256 attestation. `authenticated` receives EXECUTE on this exact RPC only; `PUBLIC`, `anon`, `authenticator`, and `service_role` receive neither provisioning-RPC execution nor provisioning-table DML, and no caller joins the owner role. The RPC owner is a dedicated least-privilege `NOLOGIN NOINHERIT` role with only required table operations and filtered Vault access. Its variants may only perform initial atomic provisioning, signed dispatch reservation, exact-reservation requested/unknown/failed outcome recording, provider-free reconciliation recording, and transition audit. Remove the legacy delegate/fallback and broad service-role mutation grants. Supabase Auth administration starts only after a signed reservation commits, runs server-side, and never executes inside the RPC. The existing Epic 11 acceptance path may mark `ready`; do not introduce a second callable DEFINER writer, custom provisioning JWT, or service-role database call.
- Use a dedicated 256-bit provisioning-attestation key separate from JWT, service-role, and quote-PDF keys, held in the app secret store and filtered Supabase Vault. Follow the repository's length-prefixed Node/Postgres HMAC pattern with explicit key IDs, fail-closed verification, at most a two-minute TTL, and current/previous-key overlap bounded to that TTL. The attestation binds action/schema, actor, request/canonical projection+hash, organisation identity, preview hash/explicit approval, baseline ID/version/hash, invitation-token hash, exact invitation/membership/reservation IDs, absolute dispatch and approval generations, expected current generation, sanitized outcome, attestation/key IDs, and issued/expiry. It is never persisted, logged, audited, or returned to the browser; invalid proof yields a generic zero-write failure.
- Persist `pending_first_admin_invite`, `first_admin_invite_unknown`, `first_admin_invite_requested`, `first_admin_invite_failed`, and `ready`. Provider acceptance means requested, not delivered; timeout means unknown; definitive failure stores only a sanitized code plus operator retry. `ready` requires completed atomic provisioning, recorded approved baseline ID/version/hash, active first-Admin membership with non-null Auth user ID, matching normalized Auth email, and no unresolved definitive failure.
- Reuse Epic 11 invitation acceptance and membership activation, but apply Decisions 7C/8A to dispatch secrets: initial dispatch and every explicit `retry_first_admin_invite` generate a fresh 32-byte CSPRNG application token in memory and sign only its SHA-256 hash. A signed `reserve_dispatch` call atomically revokes the prior hash, installs the fresh hash/current generation, reserves the attempt, and returns the durable normalized email/membership/`tenant_admin`/expiry/reservation facts; retry identity comes only from this RPC result, never caller input. After commit, at most one provider call occurs, followed by a separately signed sanitized outcome for that exact reservation/generation. Stale, out-of-order, and conflicting outcomes fail closed. Every current token remains bound to invitation, tenant, membership, normalized email, `tenant_admin`, and expiry; older links are invalid, and acceptance requires the current binding and verified Auth identity. Raw tokens never enter the RPC, storage, operator/browser output, logs, or audits, and v1 adds no escrow, deterministic derivation, or callback/provider redesign.
- Same-request replay and reconciliation return tenant ID, current state, attempt number, and reconciliation action without token rotation or provider work. A resend requires explicit authorised `retry_first_admin_invite` after reconciliation, permits at most one provider call per command execution, and `unknown` never auto-resends. One approved provisioning snapshot permits three total dispatch attempts, each with a fresh token; a fourth requires a fresh hash-bound preview/approval whose signed monotonic approval generation authorizes the next dispatch generation. Trusted `fresh_approval` booleans are forbidden. This supersedes the earlier same-token reuse across dispatch attempts.
- Roll out Decision 8A in order: provision the app/Vault key without committing it; deploy the compatible signer/server path; then apply the enforcement migration that installs catalogue/owner/grants and removes the legacy function and service-role provisioning DML. Current/previous key overlap lasts no longer than the two-minute attestation TTL.
- Provisioning activation adds `Platform.Operator.Access` as `scope: platform`, `tenantGrantable: false`, `tenantRoles: []`. It is non-granting classification metadata: authorization remains exclusively `is_platform_operator()`, tenant role/entitlement/nav/module-settings consumers exclude it, the operator registry may consume it separately, and coherence validators verify it without treating platform infrastructure as a tenant module.
- Provisioning/onboarding status uses additive `tenants` columns. Derive checklist state server-side from existing settings, pricing, and user state; only per-admin dismissal is persisted as a small column, not a checklist table.
- Phase B ships no AI provisioning flow. Free-text agent instructions are rejected; no client or off-product assistant receives database access, arbitrary production SQL, secrets, or credentials.
- Treat operator console tables/routes as platform-scoped manifest entries, not a tenant-module activation. Preserve Phase B scope guardrails and RLS/H4 conventions for touched schema.

## UX & Interaction Patterns

- Place the console in the same application at `operator/**`, with its own layout outside tenant context, the tenant AppShell, and tenant navigation. Enforce operator authorisation on every server entry, not merely the layout.
- The Swedish operator wizard has three data-entry steps plus a hash-bound approval confirmation: eligible company identity/details, displayed exact baseline ID/version/content hash and values, then first-Admin name/normalized e-mail. Dry run says nothing was saved and shows every required preview field. Resume derives from durable state; request conflict, already-provisioned identity, stale baseline, current attempt/reconciliation action, and each first-Admin handoff state have explicit truthful outcomes. `unknown` offers reconciliation before an explicit retry; attempts one through three are distinct fresh-token dispatch generations under the approved snapshot, and a fourth requires a new preview/approval and invitation generation. Neither provider acceptance nor any other state is presented as email delivery.
- On first sign-in, pin the `Kom igång` checklist on the dashboard until all five server-derived items are green. It is dismissible and resumable, and every item deep-links to its real settings surface. Provide a reminder affordance when an incomplete checklist was dismissed.
- Provisioning is connectivity-required. Show progress, clear failure/retry states, and success only after server-confirmed persistence; do not present stale state as current. Use concise Swedish operational labels and messages.
