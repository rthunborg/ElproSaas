### Review Findings

- [x] [Review][Defer][Med] (auto-resolved: defer per triage recommendation, epic mode) "Admin user" (AC1) is never pinned to the immutable acceptance/job row — captured only in the mutable-adjacent `audit_events` actor — 7.1 AC1 lists "admin user" among the captured fields, but `quote_acceptances`/`jobs` carry no `accepted_by`/`created_by` column; the acting admin exists only as the `audit_events` actor. 7.1's own review dismissed this and named 7.4 as the reopen point, but 7.4 locked the acceptance row (its whole purpose) WITHOUT ever adding the accepting-user column, so "who accepted" is now permanently absent from the immutable commitment record and reachable only via a separate, softer audit table not covered by the 7.4 trigger. Recommended: defer: keep as an owner decision — the actor IS captured on the append-only audit event and Task 1.1 deliberately omitted the column; add `accepted_by` to the (already-locked) row only if a real-customer/legal need surfaces (out of Phase-A demo-data scope). Log to the epic deferred ledger.
- [x] [Review][Decision][Med] (resolution chosen: fix — render BOTH fields in JobEvidenceLink when both present; DB-XOR CHECK stays ledger-deferred) Evidence exclusivity ("file OR reference, never both") is a prose convention enforced by no command or DB CHECK — a both-present row silently drops the external reference on the job detail — Both `captureQuoteAcceptance` (7.1) and `acceptQuoteAndCreateJob` (7.2) validate evidence presence as an OR, not an XOR, and no `quote_acceptances` CHECK forbids both `evidence_file_id` AND `evidence_reference`. `JobEvidenceLink` branches on `evidenceFileId` first (`src/components/jobs/JobEvidenceLink.tsx:33`), so if both are populated the `evidence_reference` text is silently, permanently invisible on the job detail (AC1 "shows the acceptance evidence" degrades). Spans the 7.1/7.2 write side and the 7.3 display side; no single story owns the guarantee. Recommended: fix: make `JobEvidenceLink` render BOTH fields when both are present (defensive display, no data drop) — the cheapest correct fix; a DB XOR CHECK is the stronger option but is a migration and owner-gated. Apply the display fix; log the DB-XOR option to the deferred ledger.
- [x] [Review][Defer][Med] (auto-resolved: defer per triage recommendation, epic mode; reconcile the exit-criteria text at the retro) The epic exit-criteria "correction-attempt-rejected event/audit" is promised by test-design-epic-7 but implemented by no story — `test-design-epic-7.md` Exit Criteria (lines 467-469) + the Interworking table (line 235) promise acceptance-recorded, job-created, AND correction-attempt-rejected events/audit rows. The shared envelope + `updateJob` self-audit write an audit row ONLY on success; a rejected mutation (command `VALIDATION_FAILED` unknown-field reject, or the 7.4 `AR704` DB-trigger reject) writes NO `audit_events` row anywhere. No story implements or tests this; it is not in any deferred ledger. Recommended: defer: reconcile the test-design exit-criteria text to the shipped shape (rejected direct-SQL mutations are DB-trigger-rejected below the command and are not a command-audited event in Phase A) rather than build a rejected-attempt audit path now (owner-gated, and the DB-direct attack is not a live UI path). Log to the epic deferred ledger + flag for the epic retro.

- [x] [Review][Patch][Med] No `planned_start_date <= planned_end_date` ordering check anywhere — an inverted date range persists on the acceptance and the job [src/server/commands/quotes/validation.ts; src/server/commands/jobs/validation.ts] — The acceptance validator (7.1/7.2), the `updateJob` validator (7.3), and all three DB migrations validate each planned date individually but never cross-check `planned_end_date >= planned_start_date`. A job/acceptance can be saved with an end date before its start date, rendered nonsensically on the detail/list and feeding a nonsensical job-planning window. Fix: add a cross-field ordering check (both present ⇒ `planned_end_date >= planned_start_date`, else `VALIDATION_FAILED`) in the acceptance validator AND `validateUpdateJob`.
- [x] [Review][Patch][Low] `evaluateAcceptancePriceGate` is exported + unit-tested as "the gate the command re-validates," but no command calls it — both `accept.ts` (7.1) and `accept-and-create-job.ts` (7.2) re-implement the reason rule inline (`computeAcceptanceDelta` + a hand-rolled `hasReason`) [src/features/quotes/acceptance-price.ts:88] — Two parallel (currently-consistent, independently-maintained) implementations of the AC2/AC5 reason rule; the module docstring claims it is the single authority the command consumes, which is false in the shipped code. Fix: either have the command call `evaluateAcceptancePriceGate` (fold delta + `hasReason` into the one authority) or drop the unused export + its "the command consumes this" docstring so the module does not imply an end-to-end wiring that does not exist.
- [x] [Review][Patch][Low] Idempotent short-circuit can return a NULL `job_id`, surfacing an orphaned-acceptance data-integrity anomaly as an opaque `SERVER_ERROR` [supabase/migrations/20260710120000_accept_quote_and_create_job.sql] — In the existing-record branch, `select j.id into v_job_id ... where j.quote_acceptance_id = v_acceptance_id` leaves `v_job_id` NULL if an acceptance exists without its job (partial/legacy state); the RPC still `return query select v_acceptance_id, v_job_id, true`, then `extractAcceptAndCreateJobResult` rejects the non-string `job_id` → the command throws a generic "RPC returned no result" Error → `SERVER_ERROR`, masking the anomaly behind a transient-looking error. Fix: in the short-circuit, `if v_job_id is null then raise exception ... using errcode = 'QV409'` (an acceptance always has a job — assert the invariant with a distinct, mapped code instead of a NULL passthrough).
- [x] [Review][Patch][Low] `readJobDetail` coerces a missing `quote_acceptance_id`/`quote_version_id` to the literal string `"null"`/`"undefined"` and renders a fabricated `0 kr` accepted price instead of surfacing a broken source ref [src/features/jobs/read.ts] — `String(jobRaw.quote_acceptance_id)` / `String(jobRaw.quote_version_id)` on a null/undefined column produces `"null"`/`"undefined"`, which the dependent reads match to zero rows → every money field defaults to `0` (`?? 0`) and names to null, so a job with a broken source reference silently shows "Accepterat pris: 0 kr" on a money-critical surface — contradicting the file's own "never re-derive, never mask" (R-708) goal. Fix: guard the two ids (`if (!acceptanceId || !versionId) return` a distinct partial/error detail, or null-check before stringifying) so a broken ref surfaces loudly rather than as a fabricated 0 kr.
- [x] [Review][Patch][Low] The immutability-lock triggers use `create trigger` (not `create or replace trigger` / `drop trigger if exists`), breaking migration re-run idempotency [supabase/migrations/20260711120000_accepted_record_lock.sql] — The lock functions use idempotent `create or replace function`, but the two triggers use bare `create trigger`, so a replay against a DB where the trigger already exists (partial apply, re-pointed env, reset race) fails with "trigger already exists." Asymmetric with the function definitions. Fix: precede each `create trigger` with `drop trigger if exists <name> on <table>;` (or use `create or replace trigger`) to match the function idempotency.
