# Story 8.3: Tenant-Authorized Signed File Access

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a tenant admin,
I want to preview and download my tenant's private files through short-lived links that re-authorize on expiry,
so that files stay private (never a public bucket, never a client-controlled path) while remaining usable in the pilot workflow — and a cross-tenant / expired / wrong-lifecycle attempt is denied with a generic, user-safe error that never reveals whether another tenant's file exists.

## Acceptance Criteria

**AC1 — Metadata-first authorization funnel before any signed URL (from epics.md 8.3 AC1; R-804/R-810)**
**Given** a tenant-owned file surfaced in an entity file panel
**When** the admin requests preview/download
**Then** the server verifies (in this order) tenant membership → file-metadata ownership (visible under the caller's RLS) → lifecycle state (access-eligible) BEFORE creating a short-lived signed URL — via the EXISTING `createSignedFileAccess` command (no competing signing path; R-814 STOP)
**And** the UI never renders or accepts a raw `bucket_id` / `object_path` (the signed URL is the ONLY storage handle the client ever sees — R-810).

**AC2 — Expiry → refresh re-runs the FULL authorization check (from epics.md 8.3 AC2; R-806)**
**Given** an expired (or about-to-expire) signed URL
**When** the admin retries preview/download through the normal UI
**Then** a FRESH full authorization check is performed (membership + ownership + lifecycle — NOT a bare re-sign of the old URL) and a NEW signed URL is issued only if still allowed
**And** a file whose lifecycle changed to archived/deleted (or whose ownership is no longer visible) between the first sign and the retry is NOT re-signed — the retry denies with the generic file-access error.

**AC3 — Full storage negative matrix denied with generic user-safe errors (from epics.md 8.3 AC3; R-805/R-809)**
**Given** tenant A attempts to sign, list, read, or spoof a tenant B storage path (or an anonymous caller attempts any of these)
**When** the storage negative matrix runs
**Then** every attempt is denied — cross-tenant sign/list/read, path-spoof (`{tenantB.id}/…`), malformed-segment, anonymous, and expired-URL
**And** the failure returns the SAME generic user-safe shape for not-found vs forbidden (a cross-tenant/non-existent `file_id` both surface `TENANT_ACCESS_DENIED`; a wrong-lifecycle/unsignable OWNED file surfaces `FILE_ACCESS_DENIED`) — no existence disclosure (R-809), no raw storage error across the boundary.

### Architecture patterns & constraints (MUST follow)

- **REUSE the EXISTING signing command — do NOT build a second funnel (R-814 STOP).** `createSignedFileAccess` (`src/server/commands/files/files.ts:75-122`) is the ONLY signing path. It runs the full funnel EVERY call: envelope resolves user → active `tenant_admin`; `ownership: { table: "files", id: file_id }` denies a foreign/non-existent id with `TENANT_ACCESS_DENIED` (zero rows under RLS) BEFORE execute; `execute` re-loads the row (`loadFileForAccess`), applies the lifecycle gate (`isAccessEligibleLifecycle` ⇒ archived/deleted `FILE_ACCESS_DENIED`), then signs the SERVER-STORED `object_path` on the caller's RLS client. So **expiry-refresh reauthorization = call the same command again** (a fresh full auth), NOT re-issuing a cached URL. [Source: src/server/commands/files/files.ts:75-122; architecture.md#5,#6]
- **Anon+RLS client ONLY — NO service-role key on any path.** The signing runs under `ctx.db` (the request-bound anon-key RLS client); `storage.objects` RLS re-checks the tenant path prefix on the sign. The service-role containment guards (source + built-bundle) must stay green — the preview path adds NO service-role usage. [Source: architecture.md#5, ADR-A002; scripts/verify/check-service-role-containment.mjs; signed-access.ts header]
- **Metadata-first, storage-second (R-810) — assert it at the UX layer too.** The command already resolves `files` ownership + lifecycle BEFORE `createSignedFileUrl`. The preview UX must NOT reorder that into a spoof window and must NEVER render a raw `bucket_id`/`object_path` — the signed URL is the ONLY storage handle the client sees. `readEntityFiles` already excludes the path from its projection (proven by its type + 8.2). [Source: test-design-epic-8.md §"Metadata-first"; src/features/files/read.ts:24-33,72-74]
- **Generic user-safe errors, no existence disclosure (R-809).** A cross-tenant `file_id` and a non-existent `file_id` BOTH surface `TENANT_ACCESS_DENIED` (identical shape — no "exists but not yours" leak). A wrong-lifecycle/unsignable OWNED file surfaces `FILE_ACCESS_DENIED`. A transient storage fault (5xx/network) surfaces a retryable `SERVER_ERROR` — NEVER a permanent denial (the `signed-access.ts` transient-vs-permanent discipline: `isPermanentStorageDenial`). Never a raw storage error across the boundary. [Source: src/server/storage/signed-access.ts:99-176; command-errors.ts]
- **Expiry is env-configurable + testable (R-806/R-815).** `SUPABASE_SIGNED_URL_TTL_SECONDS` (default 300s, 24h MAX clamp via `resolveSignedUrlTtlSeconds`) — a LOW test-env value proves an expired URL is rejected WITHOUT sleeping (the storage suite's expired-URL case). Do NOT hardcode a TTL (it blocks the expiry test); do NOT change the clamp semantics. [Source: src/server/storage/signed-access.ts:18-50; test-design-epic-8.md §"Expiry is a real behavioral test"]
- **Pure-`.ts` coverage-shape lesson:** the signed-access-refresh/expiry DECISION goes in a pure `.ts` module under `src/features/files/` with `node --test` units in `tests/unit/**` — NEVER buried in a `.tsx` (it escapes the fast gate otherwise, and the epic-8 test design names the "signed-access-refresh decision (8.3)" as an explicit target for this pattern). [Source: test-design-epic-8.md §"Coverage-shape lesson applies to the Wave-2 UI logic"]
- **Reuse the signed-preview state family — this is its THIRD instance.** `src/features/jobs/evidence-preview-state.ts` + `previewJobEvidenceAction` (7.3) and the quote-PDF preview (6.3) already map `createSignedFileAccess`'s Result to a `useActionState` shape. The panel's per-file download is the SAME shape — do NOT invent a new mechanism. [Source: src/features/jobs/{evidence-preview-state.ts, actions.ts:110-135}; src/components/jobs/JobEvidenceLink.tsx]
