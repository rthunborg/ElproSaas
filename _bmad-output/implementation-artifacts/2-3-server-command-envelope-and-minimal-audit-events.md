# Story 2.3: Server Command Envelope And Minimal Audit Events

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an implementation lead,
I want sensitive mutations wrapped in a consistent command envelope with audit events,
so that later lifecycle changes are authenticated, tenant-scoped, validated, and traceable.

## Acceptance Criteria

1. **Given** a server-side command that handles a sensitive mutation, **when** it runs, **then** the reusable command envelope, IN ORDER (architecture §5 steps 1-9): (a) resolves the authenticated Supabase user from server cookies, (b) resolves active `tenant_admin` membership / tenant context (reusing `resolveTenantContext`), (c) validates input with a typed schema, (d) verifies tenant ownership of every target id (a client-supplied `tenant_id`/parent id is IGNORED or verified against the resolved tenant — never trusted), (e) writes an append-only `audit_events` row where the command is marked auditable, and (f) returns a typed `Result` with `data` on success or a STABLE user-safe error code on failure. No raw throw, stack trace, SQL, or tenant/user-existence signal crosses the boundary.
2. **Given** the envelope reaches each distinct failure point, **when** it short-circuits, **then** it returns the correct stable code with a user-safe message and writes NO audit row for the failed gate: unauthenticated → `UNAUTHENTICATED`; authenticated but no active `tenant_admin` membership → `TENANT_MEMBERSHIP_REQUIRED`; input fails the typed schema → `VALIDATION_FAILED`; a target id resolves to a different tenant (or a client-submitted mismatch) → `TENANT_ACCESS_DENIED`; a transient infra failure during the envelope → `SERVER_ERROR`. (`SERVER_ERROR` reuses the Story 2.2 transient code; the others are new envelope codes.)
3. **Given** a critical/auditable command succeeds, **when** the audit write runs, **then** the `audit_events` row records, by exact `snake_case` column: `tenant_id` (the resolved tenant), `actor_user_id` (the authenticated user), `command` (the command name), `event_type`, `target_type` + `target_id`, `correlation_id` (the per-request id), `metadata` (narrow, safe JSON — see AC5), `created_at` (the single deterministic command timestamp — see AC6). The row is written under the resolved tenant only.
4. **Given** `audit_events` exists, **when** an authenticated app-path (anon-key) caller attempts to UPDATE or DELETE any audit row, OR a Tenant A admin attempts to SELECT/INSERT/UPDATE/DELETE a Tenant B audit row, **then** RLS + the GRANT/append-only discipline DENY it (UPDATE/DELETE are append-only — blocked through normal app paths by trigger/constraint/absence-of-policy, not UI; cross-tenant read/write returns zero rows or a permission error). Audit rows are append-only through every normal app path.
5. **Given** audit metadata is assembled, **when** it is persisted, **then** it contains ONLY narrow, pre-approved safe fields and NEVER stores real secrets, `.env` values, raw file contents, service-role details, full request bodies, or broad free-text PII. A unit/contract test asserts forbidden content is never persisted (a metadata allow-list / sanitizer, not free-form pass-through).
6. **Given** the command resolves a single command timestamp (injectable clock OR DB `now()` captured once per command — H1), **when** lifecycle fields, event types, and the audit `created_at` are written, **then** they all use that ONE timestamp, and time-dependent tests assert on the deterministic timestamp WITHOUT sleeps.
7. **Given** a tenant admin views a record's context later, **when** audit history would be surfaced, **then** only minimal relevant lifecycle/audit events are exposed and NO broad audit-analytics module, dashboard, route, or nav item is created (this story builds the append-only audit substrate + the envelope only; consumer UIs land in their own stories).

### Architecture compliance
