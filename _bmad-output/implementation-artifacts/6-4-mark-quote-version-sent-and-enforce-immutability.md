# Story 6.4: Mark Quote Version Sent And Enforce Immutability

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a tenant admin,
I want to mark a draft quote version as sent and lock it,
so that customer commitments cannot be overwritten by accident.

## Acceptance Criteria

1. **Given** a DRAFT quote version that passes the BLOCKING readiness checks, **when** the admin confirms `mark sent`, **then** the system records a sent timestamp (an EXPLICIT RPC parameter from the single command clock — no wall-clock), the optional channel/reference, a `quote_events` `sent` event, an `audit_events` record (allow-listed `{ targetId }` metadata only), and the immutable lifecycle state (`status` → `sent`) — all written CONSISTENTLY through a narrow SECURITY INVOKER RPC (ADR-A009), and AFTER that transition the version's customer-visible fields, selected attachments, and PDF SOURCE data can no longer be updated through any normal app path. The send is GATED by the SAME Story-5.4 readiness blocker classification the pre-quote preview used (no forked rule table): a version whose blocking conditions are not satisfied is UNSENDABLE. The `terms_approved_at` / `requires_sign_off` state that fail-closes the gate is RE-DERIVED as SERVER TRUTH at send time (not trusted from the persisted snapshot the direct-RPC path could have forged). [Source: epics.md#Story 6.4 AC1 + Technical Notes (narrow RPC for lock/event/audit; explicit sent-timestamp parameter; locking enforced below the UI); architecture.md#5 (command time discipline — a single injected timestamp; lifecycle/event/audit written from it) + #11 (once sent: customer-visible fields / selected attachments / PDF source data immutable) + ADR-A005/A009; test-design-epic-6.md#6.4-INT-01/6.4-INT-04/6.4-UNIT-01, R-608; deferred-work.md#6-1 code review [Low] (direct-RPC forge of terms_approved_at/requires_sign_off → 6.4 re-derives as server truth)]
2. **Given** a SENT (or any non-draft) version, **when** a user or command attempts to mutate customer-visible content, selected attachments, or PDF SOURCE data, **then** the change is rejected at BOTH layers: (a) command validation returns the stable typed `QUOTE_VERSION_LOCKED` (introduced by THIS story), and (b) a DATABASE trigger/constraint rejects a DIRECT own-tenant authenticated UPDATE (locking is BELOW the command layer — a UI-only lock is a STOP condition; architecture §9). The DB lock MUST EXEMPT the derived PDF-render columns `pdf_status` / `pdf_file_id` / `pdf_generated_at` (a sent version's PDF stays regenerable/retryable — 6.3 forward obligation) and the append-only lifecycle machinery (an allowed status transition to `accepted`/`rejected`/`expired`/`superseded`, the soft-delete `archived_at`, and the trigger-owned `updated_at`). **And** the quote-detail UI explains the lifecycle rule and offers a "create new version" affordance (the new-version FLOW itself is Story 6.5). [Source: epics.md#Story 6.4 AC2; architecture.md#9 (immutable lifecycle tables block normal updates through triggers/constraints/command-only rules, NOT just UI disabling) + #11 (customer-visible/attachment/PDF-source immutability after send); test-design-epic-6.md#6.4-INT-02 (command ⇒ QUOTE_VERSION_LOCKED)/6.4-INT-03 (direct UPDATE ⇒ trigger reject)/6.4-E2E-01 (UI explains rule + new-version affordance), R-605/R-616; deferred-work.md#6-3 (6.4 trigger MUST exempt pdf_status/pdf_file_id/pdf_generated_at); src/server/commands/command-errors.ts (QUOTE_VERSION_LOCKED reserved-in-comments, introduced here)]
3. **Given** tenant A and tenant B quote versions, **when** a cross-tenant send or a cross-tenant mutation attempt occurs, **then** RLS AND command validation reject it (a foreign version id is invisible under the caller's RLS → `TENANT_ACCESS_DENIED` before execute; the own-tenant WITH CHECK / composite same-tenant FKs backstop any forged tenant/parent id at the DB). No cross-tenant existence is leaked (generic denial). An authenticated tenant_admin can issue a direct RLS-client `update({ status: "draft" }).eq("id", sentId)` on a sent version — only `status` changed and it is exempt, so the trigger returns NEW and the row is now `draft`, disarming both the sent-lock (`old.status = 'draft'` early-return) and the child-lock (which keys off parent `status <> 'draft'`), re-opening every customer-visible/money column and the frozen lines/attachments to free mutation. This defeats the story's central "irreversible mark-sent + DB-enforced immutability" guarantee below the command layer. Fix: add a legal-transition guard in `enforce_quote_version_sent_lock()` rejecting any move OUT of a non-draft state back to `draft` (e.g. `if old.status <> 'draft' and new.status = 'draft' then raise ... using errcode = 'QV409'`), and ideally allow only sanctioned forward transitions (`sent → accepted|rejected|expired|superseded`). Do NOT rely on `status` being in the exempt list alone. (Merged: security review MEDIUM + Acceptance Auditor finding #2 — same issue; max severity Med.)
- [x] [Review][Patch][Med] Sent-lock trigger omits `quote_id` (and `id`/`tenant_id`/`created_at`) from BOTH the exempt list and the locked comparison tuple — an own-tenant re-parent of a sent version passes the trigger [supabase/migrations/20260707120000_quote_version_sent_lock.sql:896] — The trigger compares a hand-listed customer-visible tuple, not "the whole row minus exempt". `quote_id`, `id`, `tenant_id`, `created_at` are in neither list, so a valid own-tenant `UPDATE quote_versions SET quote_id = <another own-tenant quote id> WHERE id = <sent version>` (re-parenting a sent commitment to a different own-tenant quote) passes the composite same-tenant FK + RLS WITH CHECK and slips past the sent-lock trigger because `quote_id` is not in the compared tuple. This contradicts the comment's "FAIL-CLOSED BY CONSTRUCTION … everything not exempt is locked" claim and leaves a commitment-relevant field mutable on a sent version. Fix: add `quote_id` (and defensively `tenant_id`/`id`/`created_at`) to the locked comparison tuple in BOTH the exempt-branch and no-exempt-branch `row(...)` comparisons, so any change to them on a non-draft row RAISEs QV409.
- [x] [Review][Defer][Low] `quote_events` remains INSERT-able by `authenticated` — the append-only trigger only blocks UPDATE/DELETE, so a tenant admin can forge lifecycle timeline events below the RPC [supabase/migrations/20260707120000_quote_version_sent_lock.sql:1066] — `quote_events_append_only` fires `before update or delete` only, while the retained 6.1 own-tenant INSERT policy + grant let an authenticated own-tenant caller `insert({ ..., event_type: "sent", occurred_at, channel, reference })` directly, forging a `sent`/`accepted` lifecycle event (arbitrary occurred_at/channel/reference) that the quote-detail timeline renders as genuine — without going through `mark_quote_version_sent`. Impact is confined to the caller's OWN tenant, and the app derives the draft/read-only authorization state from `quote_versions.status` (not from events), so this is an event-log/timeline integrity gap, not an authorization bypass (security review rated it LOW). Fix direction (deferred): if the lifecycle event log is meant to be RPC-only, drop the own-tenant INSERT policy/grant on `quote_events` for `authenticated` and let only the SECURITY INVOKER RPCs write it, or add a BEFORE INSERT guard restricting direct client inserts. Deferred — genuine-but-minor own-tenant integrity gap, broader than the sent-immutability scope; owner: a later quote-events hardening pass (or the RBAC seam). deferred, pre-existing.
