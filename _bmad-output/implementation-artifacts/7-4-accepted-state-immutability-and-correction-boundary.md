# Story 7.4: Accepted State Immutability And Correction Boundary

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a tenant admin,
I want accepted quote and job source data to be locked at BOTH the command layer and the database — so an already-committed acceptance record (accepted version reference, acceptance evidence, accepted price, accepted timestamp, channel, source sent total) and a job's immutable source references cannot be silently edited through any normal app path OR a direct own-tenant SQL UPDATE, while the sanctioned lifecycle machinery (the 7.2 idempotent accept retry, the 7.3 allowed job edits, soft-delete/archival, append-only events) still works,
so that a mistake requires an explicit audited correction workflow — not a silent edit — and the accepted commitment stays trustworthy end-to-end.

## Acceptance Criteria

**AC1 — Accepted commitment fields are immutable at BOTH layers (command lock code AND DB trigger)**
**Given** a quote version has been accepted (a live `quote_acceptances` row + its one `jobs` row exist via the 7.2 `accept_quote_and_create_job` RPC)
**When** a user attempts to edit any immutable field — on `quote_acceptances`: `quote_id`, `quote_version_id`, `channel`, `accepted_at`, `accepted_price_ore`, `source_sent_total_ore`, `adjustment_reason`, `evidence_file_id`, `evidence_reference`; on `jobs`: the source references `quote_acceptance_id`, `quote_version_id`, `customer_id` (the immutable commitment linkage) — via ANY command OR a DIRECT own-tenant authenticated (anon-key RLS-client) UPDATE
**Then** command validation rejects the mutation with a STABLE lock code (a new `ACCEPTED_RECORD_LOCKED` command code, exact-code-asserted field-by-field) AND a DB trigger/constraint RAISES below the command (a custom SQLSTATE mapped to that same code) — UI-only locking is a STOP; the DB enforcement is the load-bearing proof (architecture §9: immutable lifecycle tables block updates via triggers/constraints, NOT just UI disabling) (R-704; 7.4-INT-01/02).
**And** the UI on the accepted/job surface explains that corrections require an approved audited workflow — no silent edit affordance renders for any immutable field (R-714; 7.4-E2E-01).

**AC2 — No normal edit path mutates immutable accepted data; the event is not hidden or silently overwritten**
**Given** a legitimate correction need on an accepted record
**When** the user (or a crafted request) attempts normal edit paths — an id-only update, an empty-patch update, a bulk update, the 7.3 `updateJob` allowed-edit command, or a re-run of the 7.2 accept RPC
**Then** NO normal edit path changes immutable accepted data: the 7.3 `updateJob` command touches ONLY its four Phase-A-safe columns (`title`/`status`/`planned_start_date`/`planned_end_date`) and its unknown-field reject already blocks smuggling an immutable field; an id-only/empty-patch update is a clean no-op (no false denial, no write); a status-change still appends ONE `job_events` row and never silently overwrites or hides an event (R-704, R-714; 7.4-INT-03).
**And** the 7.2 idempotent accept-retry path is PRESERVED — an already-`accepted` version reaching the RPC's existing-record short-circuit still returns the existing `(acceptance_id, job_id)` with NO write, and the accepted-lock trigger MUST NOT fire on that path (it performs no immutable-field UPDATE) (retro constraint — see Constraints).

**AC3 — Cross-tenant attack on accepted records fails (read + immutable-field update)**
**Given** tenant A and tenant B accepted records (`quote_acceptances`/`jobs`)
**When** tenant A attempts to read OR mutate an immutable field of a tenant B `quote_acceptances`/`jobs` record (via the read path, the command, OR a direct SQL UPDATE)
**Then** RLS rejects the read (foreign id ⇒ zero rows ⇒ generic not-found; anon ⇒ `UNAUTHENTICATED`) AND the immutable-field update fails — a foreign id is invisible under RLS so the trigger never sees the row, and an own-tenant crafted mutation of an immutable field on a visible row is rejected by the trigger; no existence disclosure (R-701, R-704; 7.4-RLS-01). The three tables are already enrolled in the H4 tenant-inventory gate (7.1); 7.4 adds NO table, so the H4/enrollment coverage is unchanged — 7.4's negatives target the LIVE accepted-record immutability path.

## Scope Boundary (read first — this is the LAST story in a multi-story epic)

7.4 lands **the DB-level accepted-immutability trigger + the command lock code + the correction-boundary UI message + the regression suite**. It adds NO new table and NO new column — it is purely ADDITIVE triggers/functions on the EXISTING (frozen) 7.1 tables, plus a new stable command error code, a small write-error-mapper branch, one UI notice, and tests. Precisely what belongs where:

- **7.1 (DONE, do NOT rebuild):** the migration `20260709120000_acceptance_to_job_model.sql` creating `quote_acceptances`/`jobs`/`job_events` (columns, composite same-tenant FKs, `unique (quote_version_id)`/`unique (quote_acceptance_id)` backstops, RLS own-tenant SELECT/INSERT/UPDATE policies, GRANTs, indexes, `TENANT_TABLES` enrollment); the `captureQuoteAcceptance` command + `acceptance-price.ts` delta module; the `quote_acceptance` file-owner activation. **All frozen. 7.4 REUSES the tables verbatim — it adds NO column and NO table. The 7.1 migration header EXPLICITLY reserves the immutability trigger for Story 7.4 ("7.1 CREATES the tables shaped so Story 7.4 can add the accepted-immutability trigger ADDITIVELY").**
- **7.2 (DONE, do NOT rebuild):** the `accept_quote_and_create_job` RPC (migration `20260710120000_accept_quote_and_create_job.sql`) that POPULATES `quote_acceptances`/`jobs`/`job_events` transactionally + idempotently; the `acceptQuoteAndCreateJob` command; the `sent → accepted` lifecycle flip (status ALONE); the epic-6 affordance gating. **7.4 must NOT touch the RPC or the accept transaction. It must ensure the accepted-lock trigger does NOT break the RPC's idempotent short-circuit (which does NO immutable-field write on a retry).**
- **7.3 (DONE, do NOT rebuild):** the `/jobs` list + `/jobs/[jobId]` detail read UX; `src/features/jobs/read.ts`; the `updateJob` allowed-edit command (title/status/planned dates only, audited) + `src/server/commands/jobs/{jobs.ts,jobs-db.ts,validation.ts,index.ts}`; the `job` file-owner-type activation; the accepted-version→job deep link. **7.4 EXTENDS the job command surface with the DB-lock error mapping + the UI correction-boundary message — it does NOT re-do the allowed-edit command or the read layer.** The 7.3 `updateJob` already rejects any unknown field (an immutable field can't be smuggled at the command layer); 7.4 adds the DB backstop below it and the exact-code mapping.
- **7.4 (THIS story):** (a) the ADDITIVE migration `supabase/migrations/20260711120000_accepted_record_lock.sql` — the accepted-immutability BEFORE-UPDATE trigger on `quote_acceptances` and `jobs` (fail-closed-by-construction, custom SQLSTATE), mirroring the 6.4 sent-lock trigger pattern VERBATIM; (b) the new `ACCEPTED_RECORD_LOCKED` stable command code + message in `command-errors.ts`; (c) the write-error-mapper branch (`throwMappedJobWriteError`, and any acceptance mutation path) that maps the new SQLSTATE → `ACCEPTED_RECORD_LOCKED`; (d) the correction-boundary UI notice on the job detail (and, if a mutation is attempted, the message that corrections require an approved audited workflow); (e) the DOCS-01 Lovable-oracle delta note (in the migration header); (f) the INT/RLS regression suite (`7.4-INT-01/02/03`, `7.4-RLS-01`) + the E2E message check (`7.4-E2E-01`).

**HARD STOPS (require human approval):**
- **Do NOT implement a broad correction/edit workflow after acceptance.** 7.4 enforces the immutability BOUNDARY only (mutation rejected at command + DB; UI explains corrections need an approved audited workflow). The correction WORKFLOW itself is owner-gated (R-714). If implementing a correction workflow becomes required, STOP — that needs an explicit owner-approved policy/story.
- **Do NOT modify the 6.4 sent-lock trigger (`enforce_quote_version_sent_lock` / `enforce_quote_version_child_sent_lock`) or the 7.2 accept RPC.** Relying on the sanctioned `sent → accepted` transition is the design — modifying a frozen migration is a drift STOP. The accepted-record lock and the sent-version lock are ONE model at three scopes (Epic 6 sent-freeze R-605, Epic 7 accepted-lock R-704, Epic 8.4 locked-evidence-file) and must AGREE — use the SAME lock-code family and trigger shape; a fork is a STOP.
- **Do NOT add a new table or column** (H4/migration-reset per-table policy enumeration stays unchanged). If you find yourself writing a `create table`/`add column`, that is a design-drift STOP.
