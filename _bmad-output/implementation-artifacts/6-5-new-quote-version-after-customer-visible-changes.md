# Story 6.5: New Quote Version After Customer-Visible Changes

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a tenant admin,
I want to create a new quote version when a sent quote needs customer-visible changes,
so that previous sent commitments stay available for audit and comparison.

## Acceptance Criteria

1. **Given** a SENT (or any non-draft — accepted/rejected/expired/superseded) quote version, **when** customer-visible content must change (lines/sections, price, discount, VAT, ROT/grön teknik, terms, validity, intro text, facility/customer display, attachment selection, or quote-visible notes), **then** the system creates a NEW DRAFT version on the SAME parent quote (a new `quote_versions` row with `version_number = MAX(version_number for that quote) + 1`, `status='draft'`, its OWN fresh frozen composite snapshot re-captured from the CURRENT authoritative source, its OWN `quote_events 'created'` event referencing the parent quote+new version) — through a NARROW SECURITY INVOKER RPC (ADR-A009) that reuses the Story-6.1 version-creation transaction pattern with an EXPLICIT parent-quote relationship. The sent version is NEVER edited: the new version is the mutation surface (a version is the commitment; a change spawns a version, it does not overwrite one). The RPC allocates NO new `quote_number` (the quote number is a per-QUOTE identifier allocated once at 6.1 — every version of the same quote SHARES it; only the `version_number` increments). [Source: epics.md#Story 6.5 AC1 + Technical Notes (reuse the 6.1 narrow RPC pattern with an explicit parent quote/version relationship + event); architecture.md#5 (command time discipline — injected timestamps; lifecycle/event/audit from a single clock) + #11 (a version is the immutable commitment; a change requires a new version, never a mutation of the sent one) + ADR-A005/A009; test-design-epic-6.md#6.5-INT-01, R-609; supabase/migrations/20260705120000_quote_version_model.sql:264-266 (quote_number is per-quote; version_number unique per quote — the new version increments version_number, not quote_number)]

2. **Given** multiple versions exist on one quote, **when** the admin views the quote timeline, **then** every PRIOR version remains available with its COMPLETE frozen state — its snapshot rows (`quote_versions` + `quote_version_lines` + `quote_version_attachments`), its PDF render metadata (`pdf_status`/`pdf_file_id`/`pdf_generated_at`), its `quote_events`, and its `status` history — BYTE-UNCHANGED by the v2 creation, AND the latest draft/sent/accepted state is clear (the timeline header/current-commitment logic — the EXISTING `@/features/quotes/timeline` helpers — resolves the current commitment). Creating v2 mutates NOTHING on v1. [Source: epics.md#Story 6.5 AC2 (prior sent versions remain available with snapshot/PDF metadata/events/status; latest state clear); architecture.md#11 (prior-version preservation; a version is immutable) + #9 (immutable lifecycle tables); test-design-epic-6.md#6.5-INT-02/6.5-E2E-01, R-609; src/features/quotes/timeline.ts (currentCommitmentVersion/latestVersion/orderVersionsByNumber — reuse, never fork); src/features/quotes/read.ts (the multi-version detail read already returns all versions)]

3. **Given** a Phase A lifecycle state change is applied (rejected / expired / superseded), **when** the lifecycle changes, **then** the event is tenant-scoped, audited (an `audit_events` row with allow-listed `{ targetId }` metadata only), and does NOT mutate prior sent content — the status transition on a NON-draft version is REJECTED unless it is a SANCTIONED forward transition (the 6.4 sent-lock trigger's legal-transition guard already allows `sent/accepted/rejected/expired/superseded` and rejects a reversal back to `draft`; a `superseded` mark on v1 when v2 is created is one such sanctioned transition), and it changes ONLY the `status` column (an exempt column) — never a customer-visible/commitment column. Illegal transitions (e.g. `sent→draft`, `superseded→sent`) are rejected below the command AND at the command layer. [Source: epics.md#Story 6.5 AC3 (rejected/expired/superseded events are tenant-scoped, audited, do not mutate prior sent content); architecture.md#9 (lifecycle immutability; closed transition set) + #11; test-design-epic-6.md#6.5-INT-02/6.5-INT-03, R-608/R-609; supabase/migrations/20260707120000_quote_version_sent_lock.sql:118-134 (the legal-transition guard — status change out of a non-draft state allowed ONLY within sent/accepted/rejected/expired/superseded; a reversal to draft RAISES QV409); epic-6 retro-notes#Story 6-4 (immutability trigger tests must cover state-machine REVERSAL, not only content columns)]
