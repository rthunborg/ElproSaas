# Story 9.3: Golden-Master Comparison Harness For Core Workflow

Status: ready-for-dev

## Story

As a pilot operator,
I want automated old/new comparisons for the core pilot workflow,
so that the team can approve selected workflows based on evidence instead of memory.

## Acceptance Criteria

1. **Given** anonymized fixtures, **when** golden-master comparisons run, **then** they compare **calculation totals, VAT/tax blocks, option/tillval behavior, hidden row behavior, quote-visible lines, PDF text/visual output, attachment selection, acceptance transition, accepted price, and job source references** — driving the REAL new-side engine (`@/lib/money` / `totals.ts` / `readiness.ts` / `vat-posture.ts` / the quote-PDF view-model + renderer / the accept-quote-to-job oracle) as the new-side oracle, and REFERENCING the existing per-category money/calc/quote-pdf/snapshot/accepted-price golden fixtures as the single numeric authority (never re-pinning a value another golden owns). [Source: epics.md#Story 9.3 AC1; architecture.md#17 (comparison categories) / #18 (Golden-master layer); test-design-epic-9.md 9.3-CMP-01/02/03, R-903/R-904/R-912]
2. **Given** a comparison difference, **when** the report is generated, **then** the delta is classified as **expected simplification, bug, or unresolved business assumption** with a non-empty note, and a `documented-delta` / `old-lovable` case **carries the divergent old value it diverges from** — where that divergent value may be a NUMBER **or** a CLASSIFICATION CODE (widen the numeric-only LABELLING guard to `number | classification-code`). [Source: epics.md#Story 9.3 AC2; test-design-epic-9.md 9.3-DELTA-01, R-906/R-913; retro-notes/epic-9.md#epic-9 (widen numeric-only LABELLING to number|classification-code)]
3. **Given** a workflow touches tenant-owned data or files, **when** the comparison harness runs integration cases, **then** it **includes two-tenant RLS/storage negative cases where applicable** — any touched tenant-owned table enrolled in `TENANT_TABLES` with cross-tenant list/read/sign/spoof negatives (the standing Epics 3-9 security-harness contract). [Source: epics.md#Story 9.3 AC3; test-design-epic-9.md 9.3-RLS-01, R-915; project-context.md#Security Harness Rules]

**Representativeness gate (epic blocker, R-903 / 9.3-VALID-01):** EVERY comparison code/enum value in EVERY comparison fixture MUST be validated against the REAL exported union at pack build — a fixture pinning an unknown code FAILS the pack. As part of THIS story, ALIGN the two existing FICTIONAL `ReadinessCode` values (`REQUIRES_SIGN_OFF`, `DEDUCTION_ESTIMATE_UNAPPROVED`) that `tests/fixtures/golden/snapshots/quote-version-source.json` mis-pins (lines ~48, ~94 — the 6.1-review-ledgered trap) to the real `ReadinessCode` union in `src/features/calculations/readiness.ts`. A harness built on a fixture that green-passes against a code the system never emits is a mirage of parity. [Source: test-design-epic-9.md 9.3-VALID-01, R-903, Non-Negotiable Requirements; deferred-work.md 6-1 review (fictional golden codes); retro-notes/epic-9.md#epic-9 (R-903 representativeness)]
