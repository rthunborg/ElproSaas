# Story 3.2: CRM Tenant-Admin UX And Lifecycle Context

Status: done

## Story

As a tenant admin,
I want a focused CRM interface for customers, facilities, and contacts,
so that I can find or create the right context before building a calculation.

## Acceptance Criteria

1. **Given** the CRM customer list at `/customers`, **when** the admin searches or filters, **then** customers can be found by the approved Phase A fields (display name, email, phone, city, and the type-driven identifier — org_nr — where allowed) **and** filter by customer type works, **and** the list clearly renders distinct **empty** (no customers yet), **loading**, **failed-to-load**, **no-results** (search returned nothing), and **duplicate-like warning** states. The list projection MUST NOT include or display `personnummer` (it is access-controlled; private-data posture). [Source: epics.md#Story 3.2 AC1; ux-design-specification.md#3 (Customer list: search by name/email/phone/city/org number; filter by type), #9 (CRM states table); owner-decisions-applied-2026-06-18.md#Story 3.2 (search per approved fields; not shown in list); architecture.md#4 (`/customers` Kunder)]
2. **Given** a customer detail screen at `/customers/[customerId]`, **when** the admin views it, **then** the record shows the customer's facilities (Anläggningar), contacts (Kontakter), and ONLY the Phase A-owned related areas that are backed by completed stories (e.g. files/calculations/quotes/jobs/event-history regions appear only as honest "not yet built" affordances where their owning story does not exist yet) — **and** NO deferred-module section, nav label, route, or placeholder is shown anywhere. The detail screen MAY show `personnummer` for a `private` customer in a restrained/masked form (it is not in the list, but the detail is the access-controlled surface where it is intentionally surfaced). [Source: epics.md#Story 3.2 AC2; ux-design-specification.md#3 (Customer detail hub), #11 (Explicit non-goals — no deferred-module UI/placeholders); owner-decisions-applied-2026-06-18.md#Story 3.2 (personnummer present for private with restrained/masked display); architecture.md#4]
3. **Given** facility/contact create+edit dialogs (or detail views), **when** they open and close, **then** focus moves predictably (focus into the dialog on open; focus returns to the invoking control on close — the established `AppShell` drawer pattern), **and** validation errors are programmatically associated with their fields (`aria-describedby` → the error node, `aria-invalid`, an `aria-live` error summary), with blocking errors separated from warnings, plain-language messages, no color-only signalling, and unsaved form data preserved on a validation failure. [Source: epics.md#Story 3.2 AC3; ux-design-specification.md#9 (validation next to field + summary; separate blocking vs warning; no color-only; preserve unsaved data), #10 (focus moves predictably on open/close; programmatic error association; icon-only controls have accessible names); src/components/app-shell/AppShell.tsx (focus-trap/return-focus pattern to mirror)]
4. **Given** every CRM mutation in the UI (create/update/archive customer/facility/contact), **when** the admin submits, **then** the UI invokes the EXISTING Story 3.1 server commands through the established command envelope (`createCustomer`/`updateCustomer`/`archiveCustomer`, `createFacility`/`updateFacility`/`archiveFacility`, `createContact`/`updateContact`/`archiveContact`) via a server action or route handler — it NEVER writes to Supabase directly from the client, never uses a service-role key, and never bypasses the envelope. The UI is NOT the security boundary; tenant isolation + validation are enforced server-side by RLS + the 3.1 commands. The typed `Result` error codes (`VALIDATION_FAILED`, `TENANT_ACCESS_DENIED`, `UNAUTHENTICATED`, `TENANT_MEMBERSHIP_REQUIRED`, `SERVER_ERROR`) are surfaced as the documented UI states; a transient `SERVER_ERROR` is presented as a retryable failure, NOT as a permanent access denial. [Source: epics.md#Story 3.2 Security/RLS Impact (UI cannot be the security boundary); architecture.md#3 ADR-A003 (server command authority), #5 (command surface); project-context.md#Architecture Rules (prefer the envelope; no service-role on client paths); src/server/commands/crm/*.ts; epic-3 retro-note (server-side RLS already built in 3.1 — UI must call the envelope)]
5. **Given** an unauthenticated or no-membership caller, **when** they request any `/customers` route, **then** route authorization holds via the EXISTING `(app)` server layout boundary (`UNAUTHENTICATED → redirect("/login")`; no active `tenant_admin` membership → `NoTenantAccess`). [Source: epics.md#Story 3.2 Test Requirements (route authorization); src/app/(app)/layout.tsx (the protected boundary); project-context.md#Framework-Specific Rules (force-dynamic on protected routes; auth decided server-side)]

[Source: epics.md#Story 3.2 Technical Notes (Swedish labels) + Stop Conditions (no broad CRM analytics); ux-design-specification.md#1/#11; project-context.md#Framework-Specific Rules (nav is exactly seven; never add a deferred module); src/components/app-shell/nav-items.ts]

No new tenant-owned table or migration is added (this is a UI-only story), so the H4 inventory gate is unaffected. Source: thin Tier-A code review (epic mode) — Acceptance Auditor lens (1 reviewer model) + dedicated security review (0 findings). Blind Hunter and Edge Case Hunter lenses are deliberately NOT run in Tier A (they run in the epic-level Tier-B integration review). Triaged 2026-06-30.

- [x] [Review][Decision][Med] AC1 "duplicate-like warning" is surfaced only inside the create dialog, not as a distinct LIST state — AC1 enumerates duplicate-like among the states the *list* renders, but `CustomerList.tsx` renders only failed/empty/no-results/populated; the advisory lives in `CustomerDialog.tsx` (`findDuplicateLikeNames` → `FormWarning`) while typing a create name. Task 1.4 explicitly re-scopes duplicate-like to "surface when a create/typed name closely matches an existing active customer" as a non-blocking advisory, which the dialog placement satisfies — so AC text and the approved task decomposition disagree only on *where* the state appears. Recommended: dismiss: the Task 1.4 create-dialog placement is the sanctioned intent and AC1 is met in spirit (non-blocking advisory present); no list-level duplicate state is required by the approved scope.
- [x] [Review][Decision][Med] AC1 "loading" is not implemented as a distinct rendered state (4 of 5 list states realized) — no loading/skeleton UI exists in `CustomerList.tsx`; the list is a synchronous server read with a client-side filter, so there is no async client fetch transition to show. Task 1.4 scopes "loading" to "relevant if any client-side fetch/transition is used," which the chosen server-read architecture makes inapplicable. Recommended: dismiss: loading is architecturally inapplicable given the server-read + client-filter design (no client fetch to await); the four applicable states are explicit and non-color-only.
- [x] [Review][Defer][Low] A contact's `is_primary` flag cannot be turned OFF via the edit dialog [src/features/crm/form-parsing.ts:257] — an unchecked HTML checkbox submits no form entry; `parseUpdateContactForm` reads it via `bool(form, "is_primary")` (returns `undefined` when absent) and only sets `input.is_primary` when `!== undefined`, so `buildContactPatch` skips it. A contact already flagged primary can never be un-flagged via edit — unchecking is a silent no-op. Genuine but minor: owner decided no enforced/exactly-one-primary rule, no data corruption, no security impact. Deferred — follow-up fix: render a hidden `is_primary=false` companion (or have the update parser treat a present-but-unchecked checkbox as explicit `false`) so the edit form can clear the flag.
- [x] [Review][Defer][Low] A contact's facility binding cannot be CLEARED ("Ingen anläggning") via the edit dialog [src/features/crm/form-parsing.ts:251] — `ContactDialog.tsx` offers an `value=""` "Ingen anläggning" option, but `parseUpdateContactForm` reads `facility_id: field(form, "facility_id")` and `field()` returns `undefined` for an empty string, so `buildContactPatch` (skips undefined) never writes `facility_id = null`; an already-bound contact keeps its binding. Same omitted-vs-nulled shape applies to other cleared optional fields on update; facility unbind is the user-visible case. Genuine but minor: no data corruption, no security impact; a presented edit action is inert. Deferred — follow-up fix: have the update parser map a present-but-blank optional field to an explicit `null` (or model "clear" distinctly from "unchanged") for facility/address fields on update.
