### Key Insights And Patterns

Bob (Scrum Master): "Here's what stood out across all four stories and the epic-boundary review."

1. **Every Epic-6 retro commitment to Epic 7 landed — the first fully clean handoff in this project's retro history.** Six items tracked, six done, two (affordance-gating, reversal/identity checklist) closed ahead of or beyond the committed scope. The "retro escalation → hard mechanism → resolution" pipeline that broke the 4-epic `pnpm audit` carry in Epic 6 is now demonstrated twice running as a repeatable process for smaller, story-scoped commitments too, not just multi-epic CONCERNS carries.

2. **The chunked-review seam is real, and only the epic-level auditor lens catches it.** The 7.1↔7.3 evidence-file `owner_type` mismatch survived one full review iteration's per-chunk lenses undetected and was caught only by the dedicated whole-epic pass in iteration 2. This validates the two-tier review structure (per-story chunks + a dedicated epic auditor) as load-bearing, not redundant — a per-chunk-only review would have shipped this gap silently.

3. **A review-recommended fix that reuses an existing error code for a new condition carries a mislabel forward.** This happened twice this epic in the same shape (the `p_command_at` dead-arg finding's own resolution note calls it out explicitly, and the orphan-acceptance `QV409` reuse repeats it in iteration 2). This should become a named review-checklist item: when a fix RAISEs/throws for a genuinely NEW condition, it must get a NEW code, not reuse an adjacent one that already carries a different user-facing meaning.

4. **Fix commits need their own test coverage as a matter of process, not judgment call.** Two iteration-2 fixes (the orphan-acceptance RAISE, the `JobEvidenceLink` dual-render) shipped without a test proving the NEW behavior. Both were low-severity, but "the fix is correct" and "the fix is tested" are being treated as the same claim when they aren't — a review-fix checklist item ("does this fix have its own assertion?") would close this gap mechanically.

5. **The 7.3 ATDD scaffold-vs-real-API drift is now a two-epic pattern, not a one-off.** Red-phase scaffolds authored in a resumed/multi-session context keep drifting from the actual command/factory/audit API shape (nonexistent params, wrong seed casing, wrong filter shapes). This is a narrower, recurring instance of the "trust recorded state over reality" family the Epic 5 retro first named — but specifically at the ATDD-authoring boundary now, across two epics running.

6. **Locking a record makes every field NOT captured on it a PERMANENT absence, not just a deferred one.** The "admin user on the acceptance row" item was correctly dismissed as a minor omission in 7.1's review — but the moment 7.4 locked the row without adding the column, the character of the gap changed from "not yet captured" to "now un-addable without a migration + a correction-workflow policy decision." Any future "defer, reopen at the locking story" pattern should explicitly ask "will locking make this permanent?" before re-deferring past the lock point.

7. **A two-layer immutability design, done twice, is now provably better on the second attempt.** 6.4's sent-lock had a status early-return that turned out to be a real hole (a `sent→draft` reversal could disarm both locks — caught and fixed in Epic 6's own review). 7.4's accepted-lock has NO such early-return by design — an accepted record is immutable unconditionally. This is direct evidence the 6.4 lesson was actually internalized at design time, not just patched reactively.

## Key Takeaways

1. **Every Epic-6 retro commitment to Epic 7 landed — the first fully clean retro-to-retro handoff in this project.** Two items (affordance-gating, reversal/identity checklist) closed ahead of or beyond what was committed. This is the strongest evidence yet that the retro action-item mechanism actually changes downstream behavior.
2. **The two-tier review structure (per-chunk lenses + a dedicated whole-epic auditor pass) is load-bearing, not redundant** — the 7.1↔7.3 evidence-file `owner_type` mismatch survived a full iteration of per-chunk review and was caught only by the epic-level lens.
3. **A review-fix that reuses an existing error code for a genuinely new condition carries a mislabel forward** — this happened twice this epic in the same shape; it is now a named checklist gap to close in Epic 8.

5. **Locking a record turns every previously-deferred, not-yet-captured field into a permanently absent one** — the "admin user on the acceptance row" item crossed that line this epic when 7.4 locked the row without adding the column.
6. **The dual-layer immutability pattern is now proven twice, and the second attempt is measurably better** — 7.4's accepted-lock has no status early-return, directly incorporating the hole the 6.4 review found and fixed in Epic 6.
