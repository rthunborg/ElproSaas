# Story 5.2: Calculation Editor UX For Sections And Rows

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a tenant admin,
I want a focused calculation editor with sections, rows, totals, and warnings,
so that I can prepare a quote-ready estimate efficiently.

## Acceptance Criteria

1. **Given** a calculation, **when** the admin opens the editor at `/calculations/[calculationId]`, **then** the screen shows a record header (title + status), customer context (customer, and facility/contact when set), a section/row workspace, and a totals/readiness summary on desktop **AND** the layout stacks safely on narrower screens without overlapping controls (the desktop summary panel becomes an inline summary block below the editor on narrow viewports). A foreign/other-tenant `calculationId` is invisible under RLS (zero rows) → a GENERIC not-found/no-access state that NEVER reveals whether the calc exists in another tenant. [Source: epics.md#Story 5.2 AC1; architecture.md#4 (`/calculations/[calculationId]` = Kalkyl: section/row editor, money/tax summary, readiness checks); ux-design-specification.md#5 (record header + customer context + status + primary actions; persistent totals/readiness summary on desktop; sticky summary → inline block on narrow screens); test-design-epic-5.md#5.2-E2E-03, R-515; src/app/(app)/customers/[customerId]/page.tsx (server-read + generic not-found no-leak pattern to mirror)]
2. **Given** section and row editing, **when** the admin creates, renames, reorders, duplicates where supported, or deletes sections/rows, **then** destructive actions require confirmation when rows would be removed **AND** validation errors preserve the admin's unsaved input (never clear the form on a validation failure). Ordering is server-owned: a reorder routes through the atomic `reorderSections`/`reorderRows` command (Story 5.1's narrow SECURITY INVOKER RPC), NOT client-side multi-step persistence. [Source: epics.md#Story 5.2 AC2; ux-design-specification.md#5 (section create/rename/reorder/duplicate-if-useful/delete with confirmation where rows would be removed); test-design-epic-5.md#5.2-E2E-01/02, #5.2-UNIT-02, R-503/R-515; src/server/commands/calculations/reorder.ts (reorderSections/reorderRows); src/features/crm/action-state.ts (preserve-input-on-VALIDATION_FAILED pattern)]
3. **Given** row fields, **when** the admin edits labor, material, subcontractor, machinery, or other rows, **then** quantity, unit, unit cost/sell price (in kronor at the UI boundary, stored as integer öre), markup/margin, VAT, line total, quote-visible label/description, internal note, and quote-visible note are available as approved — each row field maps 1:1 to the Story 5.1 `createRow`/`updateRow` validated input; no field the command does not accept is invented. [Source: epics.md#Story 5.2 AC3; src/server/commands/calculations/validation.ts (CreateRowInput/UpdateRowInput: row_type, quantity, unit, unit_cost_ore, unit_sell_ore, markup_bp, vat_rate_bp, is_hidden/is_optional/is_selected, label, description, internal_note, quote_note); src/features/pricing/money-display.ts (kronor↔öre UI boundary); test-design-epic-5.md#5.2-UNIT-03/04]
4. **Given** any displayed total (line total, section total, VAT, gross), **when** the editor renders or refreshes it, **then** it is computed ONLY by the frozen `@/lib/money` engine primitives (`lineNetOre`/`sumOre`/`lineVatOre`/`sumVatOre`/`vatBreakdown`/`selectVatDisplay`/`formatOreAsKronor`) — NEVER an inline `+`/`*`/`0.25`/`Number(x)*rate` in a command or a `"use client"` component, and NEVER a forked öre/rounding/VAT rule. The total-derivation logic is EXTRACTED out of the client island into a pure function unit-pinned to equal the engine output; the totals/readiness summary REFRESHES on any row/section edit. [Source: epics.md#Story 5.2 Money/Tax Impact (High — totals must use Epic 4 primitives); architecture.md#10 (line-level rounding via engine; sum-of-rounded); test-design-epic-5.md#5.2-UNIT-01/04, #5.2-E2E-04, R-505; src/lib/money/index.ts (the exported totals authority)]
5. **Given** the editor route, **when** an anonymous (no-session) caller visits `/calculations` or `/calculations/[calculationId]`, **then** they are redirected to `/login` (the `(app)` layout is the auth boundary); every read runs on the per-request cookie-bound RLS client (anon key — NEVER service-role) and every mutation routes through a Story 5.1 tenant-scoped envelope command (`createCalculation`/`updateCalculation`/`archiveCalculation`/`create|update|archiveSection`/`create|update|archiveRow`/`reorderSections`/`reorderRows`) — the UI adds NO new auth/error/audit mechanism and NO direct table write. [Source: epics.md#Story 5.2 Security/RLS Impact (UI must call tenant-scoped server commands; include route authorization and command-level negative tests from Story 5.1); architecture.md#5; project-context.md#Architecture Rules (no service-role from client paths); src/app/(app)/layout.tsx (auth boundary); src/features/pricing/actions.ts (`"use server"` → runCommand pattern)]
6. **Given** the calculation editor, **when** the admin uses it, **then** NO deferred-workflow label or control appears (no field-worker/scheduling, project planning, time/material reporting, ÄTA/deviation, supplier/import/API/sync, AI estimation, or broad analytics), and the seven-item app-shell nav is UNCHANGED (the editor lives under the EXISTING `Kalkyler` nav entry — no new top-level nav item, placeholder, or dormant UI). Internal integer-öre jargon is NOT exposed in everyday row editing (kronor at the input boundary; öre/rounding wording only in review summaries where an admin needs it). [Source: epics.md#Epic 5 Explicit non-scope + #Story 5.2 Technical Notes (Swedish labels, do not expose integer öre jargon except in review summaries); ux-design-specification.md#5, #Global patterns; test-design-epic-5.md#5.2-E2E-05, Not-in-Scope; src/components/app-shell/nav-items.ts (exactly seven items — Kalkyler already present at /calculations)]

If duplicate materially complicates the atomic-write model, ship WITHOUT it (create/rename/reorder/delete are the required verbs; duplicate is "where supported") and note it — it is NOT a blocker. [Source: epics.md#Story 5.2 AC2 ("duplicate where supported"); ux-design-specification.md#5 ("duplicate if useful"); test-design-epic-5.md#5.2-UNIT-02 (ordering incl. duplicate as one of the verbs)]
2. **Markup vs sell-price interplay in the row editor.** The row carries BOTH `unit_sell_ore` and `markup_bp`; the editor may let the admin enter a sell price directly OR derive it from cost + markup. Conservative default: treat `unit_sell_ore` as the authoritative persisted sell value; if a markup-driven sell is offered, compute the derived sell via the `@/lib/money` engine (never inline `cost*(1+markup)`) and persist the resulting öre — do NOT store a second float. Confirm the exact UX (sell-direct vs markup-derived) with the owner/readiness needs; the sell-direct default stands until then. [Source: src/server/commands/calculations/validation.ts (unit_sell_ore + markup_bp both optional); architecture.md#10 (öre authority; engine math only)]

Conservative default: explicit per-form save (each section/row form submits via its action) with a clear saved/error indicator — matching the pricing/CRM pattern — NOT a debounced autosave (autosave adds a consistency/atomicity surface without a clear Phase-A requirement). Confirm at the Epic 5 working session; explicit save stands until then.
