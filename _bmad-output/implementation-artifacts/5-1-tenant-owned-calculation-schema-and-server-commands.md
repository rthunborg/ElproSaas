# Story 5.1: Tenant-Owned Calculation Schema And Server Commands

Status: done

## Story

As a tenant admin,
I want to create and edit calculations linked to CRM context,
so that I can estimate work before creating a quote version.

## Acceptance Criteria

1. **Given** calculation migrations, **when** the database is reset from empty, **then** `calculations`, `calculation_sections`, and `calculation_rows` are created — each carrying a DIRECT `tenant_id` (FK → `public.tenants`, `on delete cascade`), COMPOSITE same-tenant parent FKs so a child can only reference a parent IN THE SAME tenant (`calculations` → `customers`/`facilities`/`contacts (id, tenant_id)`; `calculation_sections` → `calculations (id, tenant_id)`; `calculation_rows` → `calculation_sections (id, tenant_id)`), lifecycle/status fields, ordering columns, integer öre money fields (`bigint`, DB `CHECK (..._ore >= 0)`), an archive/soft-delete column (`archived_at`, NULL = active), and `created_at`/`updated_at` timestamps with the reused `public.set_updated_at()` trigger — **AND no deferred job/project/field-worker table (or column) is created.** The composite-FK targets must be UNIQUE: `customers`/`facilities` already carry `unique (id, tenant_id)`, but `contacts` does NOT — the new migration must additively `add constraint contacts_id_tenant_unique unique (id, tenant_id)` (and add the same on `calculations`/`calculation_sections`) before the referencing FKs, or the migration fails to apply. [Source: epics.md#Story 5.1 AC1; architecture.md#6 (direct tenant_id + composite same-tenant child FK), #7 (calculations/calculation_sections/calculation_rows IN; deferred tables absent), #10 (integer öre); test-design-epic-5.md#5.1-INT-01, R-501/R-506; supabase/migrations/20260630120000_crm_data_model.sql:127,162,172-206 (customers/facilities have id-tenant unique; contacts does not)]
2. **Given** a tenant admin, **when** the admin creates or edits a calculation, section, or row via server commands, **then** the commands validate tenant membership, CRM parent ownership (customer/facility/contact belong to the resolved tenant), row type (closed union: `labor`/`material`/`subcontractor`/`machinery`/`other`), quantity (> 0) + explicit unit, money values (integer öre re-validated with the CANONICAL `isOreAmount`/`ORE_AMOUNT_MAX` from `@/lib/money`, never a fork), VAT assumptions (present + basis-points-shaped, e.g. `2500`), and lifecycle state (legal transitions only) — all as a typed `Result<T, CommandErrorCode>`; an invalid input ⇒ `VALIDATION_FAILED` and the raw invalid value is NEVER echoed. [Source: epics.md#Story 5.1 AC2; architecture.md#5 (command steps 1-9), #10 (öre + VAT bp); test-design-epic-5.md#5.1-UNIT-01/02, #5.1-INT-04, R-504/R-506; src/server/commands/crm/validation.ts (the validator convention to mirror)]
3. **Given** tenant A and tenant B fixtures, **when** tenant A attempts to read/write tenant B calculations OR to link tenant B customer/facility/contact IDs as a calc parent, **then** RLS denies the cross-tenant read/write (asserted by the SQLSTATE `42501` denial MECHANISM + an independent BYPASSRLS re-read proving the target row is unchanged — never a vacuous empty-set/`null` disjunction) AND the command's ownership check returns `TENANT_ACCESS_DENIED` for the cross-tenant parent link.
