# Story 4.1: Integer Ore Money And Rounding Primitives

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a tenant admin,
I want money totals to be calculated consistently in exact öre,
so that customer-visible amounts can be reproduced and trusted.

## Acceptance Criteria

1. **Given** monetary inputs, **when** calculations are performed, **then** internal money values use INTEGER ÖRE (a non-negative safe integer `number`, never a floating-point kronor value) throughout the new `src/lib/money` engine, **and** formatting to Swedish kronor happens ONLY at a single presentation/PDF boundary formatter (never mid-calculation). A pure `src/lib/money` module exports the öre-arithmetic primitives; every internal value that crosses a function boundary is öre, and the kronor string is produced only by the boundary formatter. NO float kronor value survives off the presentation boundary. [Source: epics.md#Story 4.1 AC1 + Technical Notes ("pure functions in `src/lib/money` or equivalent"); architecture.md#10 (monetary values use integer öre `bigint`, never floating-point kronor; kronor formatting only at presentation), #22 (money pure logic lives in `src/lib/money`), #22 Data Formats (money responses include integer öre fields and formatted display strings only at presentation boundaries); test-design-epic-4.md R-401 + 4.1-UNIT-01; project-context.md#Money, Tax, And Quote Rules (SEK money stored as INTEGER ÖRE; `isOreAmount`)]

2. **Given** fractional quantities and unit prices, **when** line totals are calculated, **then** line net = round(quantity × unit_price_öre) to the NEAREST öre under the conservative pilot rounding policy — **line-level** rounding (not document-level) with a single explicitly-pinned half-rounding mode (**round half away from zero / half-up on non-negative inputs**, chosen as the conservative pilot default), **and** section/quote totals PRESERVE exact öre by SUMMING the already-rounded line values (sum-of-rounded, never round-of-sum) even if a UI/PDF later displays whole kronor. The half-rounding mode is GOLDEN-pinned so an accidental flip (e.g. to half-to-even / banker's rounding) fails loud. Quantity is an explicit decimal/numeric input (architecture §10); unit price is integer öre. [Source: epics.md#Story 4.1 AC2; architecture.md#10 Rounding (calculate line net from quantity and unit price, then round to nearest öre; sum rounded line values for section/quote totals; preserve exact öre; conservative Phase A assumption requires sign-off), #10 Storage (quantities use explicit decimal/numeric quantity plus unit); test-design-epic-4.md R-402 + 4.1-UNIT-02 + 4.1-GOLDEN-01 (rounding mode pinned; the load-bearing policy pin); epics.md#Story 4.1 Stop Conditions (document-level rounding is a stop-condition)]

3. **Given** invalid money input, **when** validation runs, **then** negative or malformed money values are REJECTED where not explicitly allowed by a story, **and** errors are user-safe and testable (a stable typed failure, never a raw echoed value, stack, or `NaN`). Money-amount validity REUSES the existing `isOreAmount(v)` / `ORE_AMOUNT_MAX` discipline (`src/server/commands/pricing/validation.ts`) — the new engine validates öre with the SAME unit (no forked money-validity rule): it rejects floats, negatives, `NaN`/±`Infinity`, overflow (> `Number.MAX_SAFE_INTEGER`), locale-comma strings (`"850,00"`), decimal/numeric strings (`"850.00"`), and null/undefined/object. Quantity input is validated as a finite non-negative decimal; a malformed quantity is rejected the same way. [Source: epics.md#Story 4.1 AC3 + Test Requirements; test-design-epic-4.md R-401/R-413 + 4.1-UNIT-03 + 4.1-UNIT-04 (invalid money rejected; negative/zero-row semantics; reuse `isOreAmount` rejects; no raw value echoed); project-context.md#Money, Tax, And Quote Rules (`isOreAmount` rejects floats/negatives/NaN/overflow/locale-comma/decimal strings — "Reuse `isOreAmount` for every new öre field"); `src/server/commands/pricing/validation.ts` (`isOreAmount`/`ORE_AMOUNT_MAX`)]

4. **Given** this story establishes the money FOUNDATION only, **when** the deliverable lands, **then** it is a PURE `src/lib/money` module + types + `node --test` UNIT tests + a golden-pinned rounding-mode fixture — and it builds NO database schema (beyond test fixtures), NO migration, NO VAT/ROT/grön-teknik math (Epics 4.2/4.3), NO calculation rows (Epic 5), NO quote/snapshot persistence (Epic 6), NO new dependency, NO `.env` edit, and NO new nav item/route/UI. The kronor-display formatter this story adds is a PURE presentation helper; it performs no business calculation. [Source: epics.md#Story 4.1 Technical Notes ("Implement pure functions in `src/lib/money` or equivalent. No database schema beyond test fixtures unless implementation needs typed persistence in a later story"), Security/RLS Impact ("None directly; no tenant data required for pure unit tests"); architecture.md#10/#22; project-context.md#Money rules ("NO money/VAT/ROT CALCULATION ENGINE exists yet — Epic 4 owns it"); test-design-epic-4.md Not-in-Scope (Epic 4 is primitives; DB/UI consumers are Epics 5-6; no INT/RLS/E2E in Epic 4's own coverage)]
