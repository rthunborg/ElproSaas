# Story 5.3: Pricing Source Selection And Row Snapshots

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a tenant admin,
I want calculation rows to use work-role or optional article pricing while preserving the chosen source,
so that later quote snapshots can explain where prices came from.

## Acceptance Criteria

1. **Given** a labor row, **when** the admin selects a work role, **then** the role ID, role display name, cost/sell rate in INTEGER ÖRE, the source timestamp/"version" (`work_roles.updated_at`), and tenant ownership are stored on the row's SNAPSHOT-SOURCE fields — copied BY VALUE and frozen at capture, NOT a live reference to the mutable `work_roles` row. The chosen source is resolved via the Story 3.5 `resolveSnapshotSource("work_role", id)` under the caller's RLS (a foreign/nonexistent id → `TENANT_ACCESS_DENIED`, never accepted), then the Story 3.5 pure `buildWorkRoleSnapshot` builder produces the copy-by-value frozen payload the row persists. Manual/free-text labor rows (no source) remain fully supported. [Source: epics.md#Story 5.3 AC1; test-design-epic-5.md#5.3-INT-01, R-507, R-502; src/server/snapshots/resolve-source.ts (resolveSnapshotSource); src/lib/snapshots/build.ts (buildWorkRoleSnapshot / WorkRoleSourceRow); src/lib/snapshots/types.ts (WorkRoleSnapshot); architecture.md#11 (snapshot source model)]
2. **Given** articles are enabled for Phase A, **when** the admin selects a manual article/material source, **then** the article ID, name, number (`sku`), unit, unit price in INTEGER ÖRE, the source timestamp/"version" (`articles.updated_at`), and tenant ownership are stored on the row snapshot fields (via `resolveSnapshotSource("article", id)` + `buildArticleSnapshot`) **AND** NO supplier IDs, import metadata, API behavior, credentials, or external mappings are introduced anywhere — the `articles` source table has none and this story must not invent one. The new source columns must NOT use any of the forbidden name tokens `supplier|credential|api_key|apikey|sync|import|external|fortnox|mapping` (a frozen migration-reset guard scans EVERY calc-table column and FAILS on a match). [Source: epics.md#Story 5.3 AC2 (no supplier/import/API/credential/external); test-design-epic-5.md#5.3-INT-01, Not-in-Scope (HARD no-supplier-scope), R-507; src/lib/snapshots/build.ts (buildArticleSnapshot / ArticleSourceRow — NO supplier field); tests/integration/rls/calc-tables-migration-reset.int.test.ts:334-345 (forbidden-column-name guard)]
3. **Given** a source is archived or its rate changed later, **when** an existing row is viewed, **then** the row remains fully explainable from its OWN preserved source snapshot fields — the displayed source id/name/rate reflect what was captured AT SELECTION time, NEVER a re-read of the now-changed/archived source. Mutating or archiving the `work_role`/`article` after capture does NOT change any prior row's stored snapshot (the copy-by-value + `Object.freeze` build contract guarantees this at the data layer; the row read surfaces these frozen fields). [Source: epics.md#Story 5.3 AC3; test-design-epic-5.md#5.3-INT-02 (freeze proof), #5.3-INT-04 (archived-source explainability), R-507; src/lib/snapshots/build.ts (R-008 copy-by-value + freeze)]
4. **Given** the source-selection write path, **when** a row is created or updated with a pricing source, **then** the mutation routes ONLY through the Story 5.1 envelope command surface (`createRow`/`updateRow` extended to accept + persist the source-snapshot fields) on the per-request cookie-bound RLS client (anon key — NEVER service-role); no new auth/error/audit mechanism, no direct table write, and no bypass of the command envelope. A cross-tenant work-role/article source id is rejected at BOTH layers — the resolver's RLS SELECT (zero rows → `TENANT_ACCESS_DENIED`) AND the DB (a same-tenant integrity backstop). [Source: epics.md#Story 5.3 Security/RLS Impact (High — source IDs must be tenant-owned and validated); test-design-epic-5.md#5.3-INT-03 (cross-tenant source spoof at both layers), R-502; architecture.md#5 (server command pattern); src/server/commands/calculations/rows.ts (createRow/updateRow to extend); project-context.md#Architecture Rules (no service-role from client)]
5. **Given** the new source-snapshot money columns, **when** the migration resets from empty, **then** EVERY new `%_ore` source-price column is `bigint` INTEGER ÖRE (never `numeric`/`double precision`/`real`/float kronor), with a non-negative DB `CHECK` belt-and-braces with the canonical `isOreAmount` re-validation in the command validator — matching the frozen Story 5.1 öre discipline. The migration is ADDITIVE (`alter table public.calculation_rows add column ...`) — it does NOT edit the frozen 5.1 migration, creates NO new table, and adds NO deferred/job/project/field-worker column. [Source: epics.md#Story 5.3 (row snapshot fields); test-design-epic-5.md#R-506, R-501, Exit Criteria (öre discipline); tests/integration/rls/calc-tables-migration-reset.int.test.ts:219-230 (every %_ore column MUST be bigint); supabase/migrations/20260702120000_calculation_data_model.sql (the frozen 5.1 schema this ADDS to); architecture.md#10]
6. **Given** the row editor (Story 5.2), **when** the admin edits a labor or material row, **then** a source-SELECTION affordance lets them choose a work role (labor) / article (material) from the tenant's ACTIVE sources; selecting a source PREFILLS the row's öre price from the source's captured rate (still editable — the row price is authoritative, the snapshot explains provenance) and shows a small "source" provenance indicator (name + rate + captured "version"); NO deferred-workflow/supplier/import/API label or control appears, and the seven-item app-shell nav stays UNCHANGED. Manual rows with no source stay supported. [Source: epics.md#Story 5.3 AC1/AC2 + Technical Notes (manual/free-text rows remain supported); ux-design-specification.md#5 (row types; source-based rows); src/components/calculations/RowEditor.tsx:11-12 (the Story-5.2 seam that defers source selection here); src/features/pricing/read.ts (readWorkRoles/readArticles — the ACTIVE source lists to offer); test-design-epic-5.md#5.2-E2E-05 (deferred-label absence continues to hold)]

### Open Questions (assumptions-pending, do NOT block coding — proceed with the conservative default)

1. **Source price captured: sell-only vs sell+cost.** AC1 says "cost/sell rate" for a work role; the `WorkRoleSnapshot` carries BOTH `costRateOre` + `sellRateOre`. Conservative default: capture BOTH onto the row (`source_price_ore` = the SELL rate that prefills the row price + `source_cost_ore` = the cost rate for provenance/margin explainability); an article has only `unit_price_ore` (→ `source_price_ore`, `source_cost_ore` null). If the owner wants sell-only provenance, drop `source_cost_ore` — but capturing both is the more explainable default and matches the snapshot contract. [Source: epics.md#Story 5.3 AC1 (cost/sell rate); src/lib/snapshots/types.ts (WorkRoleSnapshot costRateOre + sellRateOre)]
2. **Prefill authority: does selecting a source LOCK the price or just prefill it?** Conservative default: PREFILL only — the row's `unit_sell_ore` stays editable and authoritative; the snapshot explains provenance, it does not lock the price. If the owner wants a locked source-priced row, that is a materially different row model (a STOP-adjacent owner decision) — surface it, but ship the prefill-editable default (matches "manual/free-text rows remain supported" + the row-price-authoritative money model). [Source: epics.md#Story 5.3 Technical Notes (manual rows supported); architecture.md#10 (row unit_sell_ore is the money authority)]
3. **Which row types offer which source.** AC1 ties `work_role` to labor; AC2 ties `article` to material. Conservative default: offer work-role selection on `labor` rows and article selection on `material` rows; the other three row types (`subcontractor`/`machinery`/`other`) stay manual (no source) unless the owner extends the mapping. The `source_kind` column supports either kind on any row at the DB level, so extending the UI mapping later is additive.
