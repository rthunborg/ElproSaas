# Story 3.3: Company Identity, Quote Terms, And VAT Defaults

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a tenant admin,
I want to maintain company quote identity, default terms, and VAT display assumptions,
so that quote snapshots can use approved tenant-owned defaults.

## Acceptance Criteria

1. **Given** tenant-owned settings tables, **when** the admin updates company identity (name/address/contact/org-nr/branding fields a quote PDF needs), default VAT display mode, the configurable VAT rate (basis points), or quote terms, **then** the change is **validated** (typed input; reject malformed values with user-safe messages), **tenant-scoped** (the resolved-membership tenant is the only authority — a client-supplied `tenant_id` is ignored), **audited** (an append-only `audit_events` row via the envelope's `writeAuditEvent` DEFINER path, metadata allow-listed — NO raw free-text/PII/secret), and **visible** when the settings UI is reloaded. New tables (`company_settings`, `quote_terms`) carry a DIRECT `tenant_id`, enable+FORCE RLS with own-tenant `is_tenant_admin` policies, explicit GRANTs (`authenticated → SELECT/INSERT/UPDATE`, `service_role → DML`, `anon → none`), and are enrolled in the H4 inventory gate. [Source: epics.md#Story 3.3 AC1; architecture.md#5 (updateCompanySettings audits settings change), #7 (company_settings/quote_terms IN), #10 (VAT basis points; VAT defaults are tenant settings); project-context.md#Architecture Rules (RLS-by-default + GRANTs; envelope for sensitive mutations); owner-decisions-applied-2026-06-18.md#Story 3.3 (VAT rate stays a configurable setting, never a literal)]
2. **Given** quote terms are edited, **when** the admin views/saves them, **then** the UI shows the owner/legal **sign-off STATUS** (e.g. "Kräver godkännande av ägare/juridik" / "Godkänd av …" with who+when) or a clear **WARNING**, and customer-facing terms text is **NEVER silently/auto approved by the implementation**: a newly-created or freshly-edited terms record DEFAULTS to **not-approved** (`approved_at`/`approved_by` null) and only a deliberate human action transitions it to approved. The code path MUST NOT hardcode an `approved` default, and editing approved terms re-sets them to not-approved (an edit invalidates a prior sign-off). [Source: epics.md#Story 3.3 AC2 (UI shows sign-off status/warning; customer-facing text not silently approved) + Stop Conditions; epic-3 retro-note (HARD STOP-CONDITION — customer-facing tax/legal/quote-terms wording must NEVER be silently/auto approved; UI shows owner/legal sign-off STATUS or WARNING; terms default to NOT-approved; never code a default of 'approved'); ux-design-specification.md#4 (quote-terms settings: "ordered editable terms with approval status or clear requires owner/legal sign-off warning before pilot use"), #9 (Settings states: unapproved quote terms / VAT-tax sign-off warning); NFR15/AR for sign-off]
3. **Given** tenant A and tenant B settings, **when** tenant A attempts to read/write tenant B `company_settings` or `quote_terms` (cross-tenant SELECT, INSERT spoofing B's `tenant_id`, UPDATE of B's row, or DELETE), **then** RLS and the command validation reject it: a cross-tenant SELECT/UPDATE sees zero rows (RLS USING invisibility), a cross-tenant INSERT fails the WITH CHECK (`42501`), and no DELETE policy/grant exists on the app path. The new tables are enrolled in `TENANT_TABLES` (cross-tenant + anon-path suites) and the H4 gate, with assert-the-mechanism negatives (zero-rows-affected PLUS an independent BYPASSRLS re-read proving the target row is UNCHANGED). [Source: epics.md#Story 3.3 AC3 (cross-tenant read/write rejected); architecture.md#9 (RLS test matrix); project-context.md#Security Regression Harness Rules (H4 single enrollment contract; anon-path-isolation; cross-tenant negatives); epic-3 retro-note (every new tenant-owned table MUST be enrolled in the H4 RLS inventory gate — cross-tenant + anon-DML seams; assert-the-mechanism; anon asserts anon-DML-empty)]
4. **Given** the settings UI under `/settings`, **when** the admin opens Company settings and Quote-terms settings, **then** `/settings/company` (Företagsinställningar — company identity + VAT display/rate defaults) and `/settings/quote-terms` (Offertvillkor — terms editor with sign-off status/warning) exist as real screens, each `export const dynamic = "force-dynamic"`, reading via the per-request cookie-bound RLS client and writing ONLY through the envelope command(s) via a `"use server"` action — NEVER a direct client write, NEVER a service-role key. Form validation is programmatically associated (`aria-invalid`/`aria-describedby` → error node, `aria-live` blocking summary), input is preserved on failure, and the typed `Result` codes map to the documented UI states (`VALIDATION_FAILED` → field/summary; `TENANT_ACCESS_DENIED` → generic; transient `SERVER_ERROR` → retryable, NOT a permanent denial). Route auth is the EXISTING `(app)` server-layout boundary; this story adds NO new auth mechanism. `nav-items.ts` stays EXACTLY the seven IN-scope modules (no new nav item; `/settings/pricing` is Story 3.4 and is NOT built here). [Source: epics.md#Story 3.3 AC1 (visible in settings UI) + Test Requirements (form validation tests); architecture.md#4 (/settings/company, /settings/quote-terms routes; English paths + Swedish labels); ux-design-specification.md#4 (Settings screens), #9/#10 (validation + a11y); project-context.md#Framework-Specific Rules (force-dynamic; nav exactly seven; auth server-side); 3-2 story (the established server-action + RLS-client + useActionState UI pattern)]
5. **Given** the VAT display defaults, **when** the admin sets the default VAT display mode, **then** the owner-approved rule is encoded as a tenant setting (not a code literal): `private` customers → PDF **always** shows VAT rate + VAT amount + incl-VAT total (NOT togglable); `company` customers → incl-VAT display is **togglable**. The VAT **rate value** itself is a configurable setting (legacy default 25% = `2500` basis points) — NEVER hardcoded as a literal in calc/quote code. NO VAT/ROT/grön teknik **calculation engine** is built here (Epic 4 owns that): this story STORES the VAT defaults + assumptions as approved tenant-owned settings for later snapshotting, and any monetary/VAT-rate value is stored as an integer (basis points for rates; öre `bigint` for any money field — NO float money fields). ### Critical Constraints (read first)

- **This story builds TWO new tenant-owned settings tables (`company_settings`, `quote_terms`) + their server command(s) + a settings UI** over the Epic-2 foundation (envelope, RLS helpers, audit, harness) and the Epic-3 patterns established by Story 3.1 (CRM migration/commands) and Story 3.2 (settings UI shape). It is the FIRST settings story. State your operating mode (implementation) before editing. [Source: epics.md#Story 3.3; architecture.md#7]
- **HARD STOP-CONDITION (honor it; it is NOT a needs-human halt if implemented correctly): customer-facing tax/legal/quote-terms wording must NEVER be silently or automatically approved by the implementation.** The schema represents approval ONLY as a nullable `approved_at` (default NULL = not-approved) — there is no `status='approved'` default to accidentally set. A fresh/edited terms record is not-approved by construction; editing approved terms RESETS approval; the ONLY path that approves is a deliberate human-triggered `approveQuoteTerms` command. The UI ALWAYS shows the sign-off STATUS or a WARNING. Do NOT code a default of 'approved', an auto-approve, or an implicit approval inside the edit path. [Source: epic-3 retro-note (HARD STOP-CONDITION); epics.md#Story 3.3 AC2 + Stop Conditions; ux-design-specification.md#4/#9; NFR15]
- **Integer-öre / basis-points money discipline — NO float money fields, and NO money/VAT calculation ENGINE here.** This is the FIRST VAT-touching story, but the VAT/ROT/grön-teknik calculation engine is Epic 4's, not this story's. Store the VAT defaults (display mode + `vat_rate_bp` in basis points) and quote terms as APPROVED tenant-owned settings for later snapshotting; do NOT compute any VAT/ROT total. Any monetary value is integer öre (`bigint`); any rate is basis points (integer, `2500` = 25.00%). Never a float, never a hardcoded VAT literal in code. [Source: epic-3 retro-note (integer-öre discipline; first VAT story but NO engine yet — Epic 4 owns it; store defaults, don't build the engine); architecture.md#10 (öre `bigint`; VAT basis points); owner-decisions-applied-2026-06-18.md#Story 3.3 (VAT rate configurable, never a literal)]
- **Every new tenant-owned table MUST be enrolled in the H4 RLS inventory gate (cross-tenant + anon-DML seams) — non-negotiable exit criterion.** A new table is NOT done until it has (a) `tenant_id` scoping, (b) enable+`force` RLS with own-tenant policies on the DEFINER helpers, (c) explicit role GRANTs (`anon → none`), AND (d) enrollment in `TENANT_TABLES` (with BOTH the cross-tenant and anon-path metadata seams). The `assertNever` exhaustiveness switch makes incomplete enrollment a COMPILE error; the H4 gate fails CI with a named "table not covered" message if you forget. The migration-reset exact-policy enumeration WILL grow — EXTEND it, do NOT loosen it to a superset. RLS negatives assert-the-mechanism (zero-rows + unchanged re-read for cross-tenant UPDATE); anon asserts anon-DML-empty (SELECT/INSERT/UPDATE/DELETE denied), NOT anon-grant-empty (Supabase grants every role non-DML REFERENCES/TRIGGER by default). [Source: epic-3 retro-note (STANDING CONTRACT — every new tenant-owned table enrolled in H4; assertNever compile-error; migration-reset enumeration grows/not-loosened; anon-DML-empty); project-context.md#Security Regression Harness Rules; #Critical Don't-Miss Rules (RLS-by-default + GRANTs + enrollment)]
- **The UI is NOT the security boundary; settings writes go through the envelope command(s) on the RLS client.** Reads run on the per-request cookie-bound anon-key RLS client; writes run ONLY through `runCommand(<settings command>, { client, input })` (the envelope resolves user → active `tenant_admin` → validate → execute on the RLS client → append-only audit → typed `Result`). NEVER a service-role client, NEVER a direct `.insert()/.update()` from a page/action. The two source + bundle containment guards fail loud on a service-role leak. [Source: project-context.md#Architecture Rules (prefer the envelope; no service-role on client paths); architecture.md#5; src/server/commands/envelope.ts]
- **GATED actions / Stop Conditions (this story):** STOP if final VAT/rounding/tax wording is treated as approved WITHOUT owner/accounting/legal sign-off (the whole point of the sign-off mechanism — encode "not approved", do not assume approval); STOP if the VAT rate is hardcoded as a calc/quote literal instead of a configurable setting; STOP if a money field would be a float; adding ANY dependency is approval-gated + EXACT-pinned; NO `.env` edit; NO `/settings/pricing` (Story 3.4); NO VAT/ROT calculation engine (Epic 4). [Source: epics.md#Story 3.3 Stop Conditions; owner-decisions-applied-2026-06-18.md#Story 3.3; epic-3 retro-note]

## Open Questions

These are surfaced for visibility and DO need owner/accounting/legal input on the tax/legal items, but they do NOT block implementation under the conservative defaults (encode "not approved" / configurable rate / placeholder text; proceed and confirm at the working session / PR review). The story intentionally does NOT resolve the sign-off items itself.

1. **VAT rate value (basis points) — pending the working session (owner gate).** Owner kept the VAT rate a configurable setting with the legacy default of 25% (`2500` bp); the authoritative rate (and any per-customer-type variation, caps, schablon) is still gated on the Epic-4 working session. Proceed: store it as a configurable `vat_rate_bp` defaulting to `2500`, NEVER a code literal. Confirm the authoritative value before real pilot use. [Source: owner-decisions-applied-2026-06-18.md#Story 3.3 + #Still gated on the working session]
2. **Quote-terms customer-facing wording (sign-off REQUIRED — owner/legal).** Final customer-facing terms wording is a full-release / owner+legal sign-off item; placeholder text is acceptable for the pilot. The story implements the NOT-approved-by-default + sign-off-status/warning mechanism precisely BECAUSE the wording is not signed off — do NOT mark any terms approved in code or fixtures. A human must sign off the real wording. [Source: epics.md#Story 3.3 Stop Conditions; epic-3 retro-note (never silently/auto approve); owner-decisions-applied-2026-06-18.md#Story 3.3 (placeholder acceptable; final wording full-release)]
3. **VAT display defaults precision — private always incl-VAT (not togglable) vs company togglable.** The owner gave the rule at the display-mode level; the EXACT set of `default_vat_display` enum values and how the per-type behavior (private=forced incl-VAT, company=togglable) is encoded as the tenant setting is a modeling choice. Proceed with the conservative encoding (the setting captures the default display mode + the togglability per type as owner-stated); confirm the precise enum/labels in the working session. No VAT calculation is built here. [Source: owner-decisions-applied-2026-06-18.md#Story 3.3]
4. **Exact mandatory company-identity fields for a PDF-ready quote.** Owner gave "kundrelevant info" + company identity for the PDF, not a precise required-field list (still open for Epic 3). Proceed with sensible required defaults (company_name required; org_nr + address + contact optional but recommended); confirm the exact required set in the working session. Not a data-model blocker. [Source: owner-decisions-applied-2026-06-18.md#Still open for Epic 3]
5. **Single-active-terms-row vs versioned terms shape.** This story models ONE active terms set per tenant (simplest, matches `company_settings` one-per-tenant). If the owner later wants multiple named/ordered terms templates or a terms history, that is a follow-up extension. Proceed with single-active; surface if a richer model is needed. [Source: ux-design-specification.md#4 (ordered editable terms); architecture.md#7 (reusable quote terms)]
