- [x] [Review][Decision][High] Pipeline "accepted value" money leaf sums the frozen SENT total, not the actual accepted commitment — `readQuotePipeline`/`aggregateQuotePipeline` sum `quote_versions.accepted_price_ore` (src/server/read-models/quote-pipeline.ts:138-148; quote-pipeline-aggregate.ts:141-147), but `quote_versions.accepted_price_ore` is documented as the SOURCE SENT TOTAL the adjusted-price delta is measured against (src/server/commands/quotes/quote-db.ts:288), NOT what was accepted. The real accepted commitment lives in `quote_acceptances.accepted_price_ore`, which acceptance can capture at an ADJUSTED price. So for any deal accepted at an adjusted price, `acceptedValueOre` reports the quoted amount, not the accepted amount — and this is the precedent-setting money leaf E19's Offertpipeline widget inherits. SETTLED DESIGN DECISION 5 named this column. Recommended: fix: source `acceptedValueOre` from `quote_acceptances.accepted_price_ore` (still an existing frozen integer öre value — R-1042 "no new money path" preserved) and reconcile SETTLED DECISION 5; else owner must confirm "accepted value = sent gross of accepted versions" is the intended metric and record it for E19.
- [x] [Review][Decision][High] Open follow-ups on already-decided (accepted OR lost) quotes are never completed and keep escalating — the follow-up completion surface (`FollowUpPanel`) renders ONLY in the `selected.status === "sent"` branch (src/components/quotes/QuoteDetailView.tsx:507-565); the acceptance action never touches `quote_follow_ups` (src/features/quotes/actions.ts:556-618, no completeQuoteFollowUp call), and the standalone/lost paths only auto-complete when a hidden `follow_up_id` is carried. Both the LIVE list projection (`has_open_follow_up`/`overdue_follow_up` keyed purely on `quote_follow_ups.status='open'` with no lifecycle join, src/features/quotes/read.ts:138-206) and the 10.4 pipeline aggregate count these, so an accepted (won) quote shows "Försenad uppföljning" in `/quotes` today and inflates `openFollowUpCount`/`overdueFollowUpCount`. The actions.ts "recoverable — the sheet stays available; the user can Klarmarkera it manually" comment (src/features/quotes/actions.ts:355) is FALSE, since the sheet unmounts the moment the version leaves `sent`. Recommended: fix: exclude follow-ups whose quote's latest version is terminal (accepted/lost) from the list projection AND the pipeline aggregate (join `quote_follow_ups`→latest `quote_versions.status`), and/or auto-complete the open follow-up inside `acceptQuoteAndCreateJob`; correct the false recovery comment. If deferred, get owner sign-off (E19 visibility) — the escalation badge is user-visible in `/quotes` now, not just latent.
- [x] [Review][Decision][Med] Fail-open entitlement default — `resolveMoneyEntitled` returns `true` (money-entitled) when no `EntitlementInput` is supplied (src/server/read-models/entitlements.ts:86-90): the least-known caller (no input) is the MOST permissive, while an explicit empty role set is unentitled. Security considered-and-excluded it as not currently reachable (no production caller; B1a is all-`tenant_admin`) but flagged it for Epic 11. This is the phase-defining precedent every later Phase-B read-model inherits (R-1040). Recommended: fix: make an omitted `EntitlementInput` resolve the SAME as empty roles (withhold, fail-closed) for defense-in-depth, or document why fail-open-on-omission is deliberate and add a "callers MUST pass an explicit EntitlementInput" contract note carried into the Epic 11 seam.
- [x] [Review][Decision][Med] Duplicate lost/new-version affordances in the transient "sent + follow-up just completed (jumps)" state — `QuoteDetailView` mounts a standalone `MarkLostButton` + (read-only-notice) `CreateNewVersionButton` for a sent version (QuoteDetailView.tsx:519,606), AND `FollowUpPanel`'s jumps branch re-renders a second `MarkLostButton` + `CreateNewVersionButton` (src/components/quotes/FollowUpPanel.tsx:93,96). During the jumps state two controls with identical accessible names and a duplicated `data-testid="mark-lost-section"` co-render; the 10.3 E2E already routes around it by scoping to `follow-up-jumps`. Recommended: fix: pick one owner for these affordances during jumps — suppress the `FollowUpPanel` jumps-branch duplicates (the standalone instances already provide them), or gate the standalone `MarkLostButton`/`CreateNewVersionButton` off while jumps show — so only one control per accessible name renders.
- [x] [Review][Decision][Med] `validateManifestCoherence` under-enforces documented invariants — it does not check `activatedAt` presence on active modules, module-`id` uniqueness, or cross-module uniqueness of `publicSurfaces`/`notificationCategories`/`deferredFileToken` (src/scope/manifest-schema.ts), yet the docstring + AGENTS.md advertise "presence AND coherence"; enforcement of these rests solely on hand-written unit tests. Recommended: fix: either add the missing coherence rules (new rule ids `missing-activation-date`, `duplicate-module-id`, `duplicate-soft-surface`) so the validator matches the docs, or soften the docstring/AGENTS.md to name only the invariants actually enforced and keep the unit tests as the authority for the rest.
- [x] [Review][Decision][Low] Planning a follow-up with a PAST `due_date` is accepted → an immediately-overdue follow-up — `validatePlanQuoteFollowUp` only checks `due_date` is a real ISO calendar date, never that it is ≥ today (src/server/commands/quotes/validation.ts); a user or crafted request can plan a follow-up due last month, which the chip/list instantly escalate as "Försenad uppföljning." Recommended: fix: reject a `due_date` earlier than today (Europe/Stockholm) with a new error code `FOLLOW_UP_DUE_DATE_IN_PAST` and set `min={todayStockholmISO}` on the date input; else dismiss if intentional backdating is desired (document it).
- [x] [Review][Decision][Low] RESOLVED won't-fix (auto-resolved as dismiss per triage recommendation, epic mode): "currently open" is the intended semantics for follow-up counts — the fix delegate documents this in the 10.4 completion notes so E19's period widget never treats them as period metrics. Original finding: Pipeline follow-up counts are point-in-time, not period-scoped — `open`/`overdue` follow-ups are counted with no window filter while `sent`/`accepted`/`lost` counts, hit-rate and money ARE window-filtered (src/server/read-models/quote-pipeline-aggregate.ts:150-156; quote-pipeline.ts:155-158), so a period-selecting descriptor mixes current-state follow-up counts with period-bound metrics — tension with AC1 "queried for a period." Recommended: dismiss: if "currently open" is the intended semantics, document it in the completion notes so an E19 period widget does not treat these as period metrics; else fix by window-filtering follow-ups.
