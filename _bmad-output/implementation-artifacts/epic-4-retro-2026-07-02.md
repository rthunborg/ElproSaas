### Key Insights And Patterns

**Insight 1 — Single-authority consolidation discipline is now a repeating, self-reinforcing pattern, not a one-off fix.**
`isOreAmount`/`ORE_AMOUNT_MAX` moved canonical in 4.1; `isVatRateBp`/`VAT_RATE_BP_MIN`/`MAX` moved canonical in 4.2, explicitly mirroring the 4.1 move. Each story's create-story phase spelled out the export/move/reconstruct options up front so the dev agent kept exactly one authority rather than forking a second copy. This is the money-domain equivalent of Epic 2's H4 inventory-gate pattern: a structural discipline that scales cleanly across stories without inventing a new mechanism each time.

**Insight 2 — Silent-failure bugs on a pure logic engine take a different shape than on a DB/UI epic, but the review architecture still catches them.**
Epic 3's silent-failure bugs were shaped by "unbound action state + force-nulled optional upsert field" (DB/UI surface). Epic 4 has no DB/UI, yet the review still caught two analogous silent-failure shapes: an error code that leaks the wrong domain's identity across a story boundary (`INVALID_VAT_RATE_BP` returned for a tax-profile rate failure) and a fallback that fabricates data instead of surfacing an error (`selectVatDisplay` relabeling an unrecognized posture as `'private'`). The generalizable lesson: "silent failure via a plausible-looking fallback" is a recurring code smell independent of domain — worth a standing review-checklist line, not just a DB/UI-specific one.

**Insight 3 — Stale story-artifact prose from earlier phases is a recurring low-severity risk, now seen in two different shapes across two epics.**
Epic 3 saw a stale *planning document* (test-design R-009 wording superseded by a later owner decision). Epic 4 saw a stale *story-file claim* (Story 4.3's Dev Notes asserting an ATDD scaffold didn't exist, when Phase 4 had already run and committed it between create-story and dev-story). Both are instances of the same root cause: a downstream phase trusts a claim written by an earlier phase without re-verifying it against current reality. Epic 3's lesson was "reconcile stale planning text at the retro." Epic 4 generalizes it further: any phase that asserts "X doesn't exist yet" should be treated as time-stamped, not permanent, if another phase can run in between and change that fact.

**Insight 4 — The two-tier / multi-lens review architecture continues to pay for itself even on a surface with zero security/auth footprint.**
Epic 3 validated the two-tier (per-story + cross-story integration) review architecture on a DB/RLS epic. Epic 4 validates a complementary claim: on a pure-logic epic with a dedicated security pass returning 0 findings (correctly — there is no PII/auth surface), the *multiple reviewer lenses* (blind/edge/acceptance × two models) are still what catches real correctness bugs (the VAT-display posture-falsification, the leaked error-code identity) that a single pass would plausibly have missed or under-rated as cosmetic.

**Insight 5 — A three-epic carried-forward NFR CONCERNS is now a process failure mode in its own right, independent of the two specific items.**
This is the second retro in a row explicitly naming this. The `pnpm audit` CI gate and coverage reporter are individually small (quick-win estimates of 0.5–2 hours each per the NFR report), but the pattern of "flagged, agreed as needing a decision, then not decided" across three consecutive epic retros is itself the finding: a CONCERNS-level NFR item without a hard deadline or named owner will keep losing to story-scoped urgency indefinitely. The fix is procedural (assign an owner and a deadline this cycle), not technical.
