# Story 3.1: Tenant-Owned CRM Data Model And Commands

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a tenant admin,
I want to manage customers, facilities, and contacts,
so that calculations and quotes can use the correct customer context.

## Acceptance Criteria

1. **Given** tenant-owned CRM migrations run from an empty database, **when** the reset completes, **then** `customers`, `facilities`, and `contacts` tables exist, each carrying a direct `tenant_id` (FK → `public.tenants`, `on delete cascade`), an archive/soft-delete column, `created_at`/`updated_at` timestamps (with the `set_updated_at` trigger), and parent-tenant consistency constraints so a `facility`/`contact` can only reference a parent (`customer`/`facility`) IN THE SAME tenant (the architecture §6 composite-FK rule, NOT a bare `references` that would let a child point at another tenant's parent). [Source: epics.md#Story 3.1 AC1; architecture.md#6 (child duplicates `tenant_id` + composite constraint), #7, #22]
2. **Given** the four approved customer types (`private`, `company`, `brf`, `public`), **when** a `customers` row is created, **then** `customer_type` is constrained to exactly those four values, and the type-driven identifier is captured: `personnummer` for `private` (required for ROT downstream — owner decision 2026-06-18 REVERSES the "no personnummer" default), `org_nr` for `company`/`brf`/`public`. Personnummer is tenant-owned, access-controlled, and NOT surfaced in any default list projection. [Source: owner-decisions-applied-2026-06-18.md#Story 3.1; epics.md#Story 3.1 AC1 ("no personnummer field … by default" — overridden by the owner decision for `private`)]
3. **Given** a tenant admin, **when** the admin creates / views / updates / archives / searches CRM records via the server commands (`createCustomer`, `updateCustomer`, `archiveCustomer`, `createFacility`, `updateFacility`, `archiveFacility`, `createContact`, `updateContact`, `archiveContact`), **then** every command runs through the established `defineCommand`/`runCommand` envelope (resolve user → resolve active `tenant_admin` membership → validate typed input → verify tenant ownership of parents/targets → execute → append-only audit), validates inputs, enforces parent ownership, and writes an audit event for critical changes. No command invents its own auth/error/audit mechanism. [Source: epics.md#Story 3.1 AC2; architecture.md#5 (command shape + Phase A command table), #15; src/server/commands/envelope.ts]
4. **Given** tenant A and tenant B fixtures, **when** tenant A attempts to read/write tenant B CRM rows OR to create a `facility`/`contact` that links to a tenant B parent id, **then** RLS denies the cross-tenant read/write (asserted by the SQLSTATE `42501` denial MECHANISM + independent BYPASSRLS re-read, never a vacuous empty-set/`null` disjunction) AND the command's ownership check returns `TENANT_ACCESS_DENIED` for the cross-tenant parent link. [Source: epics.md#Story 3.1 AC3; architecture.md#9 (read/insert/update/delete/command isolation rows); project-context.md#Security Regression Harness Rules (assert-the-mechanism)]
5. **Given** the H4 RLS table-inventory gate, **when** CI runs `test:int`, **then** `customers`, `facilities`, and `contacts` are enrolled in `tests/integration/rls/tenant-table-inventory.ts` (`TENANT_TABLES` + BOTH metadata seams: `spoofedRowFor`/`tenantBFilter`/`hijackMutationFor` AND `anonRowFor`/`anonFilterFor`/`anonMutationFor`), the gate is GREEN (every tenant-owned table covered), and each table has explicit role GRANTs (`authenticated → SELECT/INSERT/UPDATE`; `service_role → full DML`; `anon → none`) with RLS ENABLE + FORCE and own-tenant policies built on the `is_active_tenant_member`/`is_tenant_admin` helpers. The standing contract: an unenrolled new tenant-owned table is a CI failure, not a reviewer catch. [Source: epic-2-retro#Action Items 1; project-context.md#Architecture Rules (RLS narrows; GRANTs expose), #Security Regression Harness Rules; tenant-table-inventory.ts STANDING CONTRACT]
6. **Given** anonymous (no-session) callers, **when** the anon-path negative suite runs, **then** anon SELECT/INSERT/UPDATE/DELETE on `customers`/`facilities`/`contacts` is denied (`42501`) — the anon seam is covered for every new table, not just the cross-tenant seam. [Source: tenant-table-inventory.ts (anon helpers); epic-3 retro-note (the anon seam is the easiest-to-forget H4 obligation)]
7. **Given** the CRM tables exist, **when** the dev verifies, **then** NO migration creates a deferred-module table, NO supplier/credential/sync/import/external-mapping/API field appears on any CRM table, and NO broad CRM-analytics or document-center structure is introduced. Money fields (none required by this story) — if any are added — are integer öre (`bigint`), never floating kronor. [Source: epics.md#Epic 3 non-scope + Story 3.1 Stop Conditions; architecture.md#7 (explicitly absent v0 tables); epic-3 retro-note (no supplier-scope; integer-öre)]

## Dev Notes

### Critical Constraints (read first)

- **This is the FIRST product-feature story of Epic 3 and the FIRST story to add tenant-owned BUSINESS tables.** It creates a migration (`customers`/`facilities`/`contacts`), nine server commands, factory seeds, and the H4 enrollment + negatives. It is NOT a UI story — `nav-items.ts` stays seven; the CRM UX is Story 3.2. State your operating mode (implementation) before editing. A Phase A story authorizes the migration + product code. [Source: epics.md#Epic 3, #Story 3.1/3.2; project-context.md#Development Workflow Rules]
- **The H4 inventory gate WILL fail-loud the moment the new `tenant_id`-carrying tables land — that is EXPECTED, not a bug.** `introspectTenantOwnedTables` detects any application table with a direct `tenant_id` and DEMANDS its enrollment in `TENANT_TABLES`; until Task 4.1 enrolls all three (with BOTH metadata seams), CI/`test:int` goes red with a named "table not covered" message. Register/extend the inventory — do not weaken or skip the gate. This is the standing Epic 3-9 contract. [Source: epic-2-retro#Action Items 1, #Key Takeaways 4; epic-3 retro-note (STANDING CONTRACT — every new tenant-owned table enrolled, esp. the anon seam); tenant-table-inventory.ts]
- **GRANTs and RLS are a single per-table checklist item — RLS alone is not isolation on this stack.** New `public` tables are NOT auto-exposed to the Data API roles; RLS only NARROWS an already-granted role. A missing GRANT surfaces as `42501 permission denied` on the app-path write (a STRONGER denial than RLS zero-rows). Every CRM table needs (a) `tenant_id` scoping, (b) enable+FORCE RLS with own-tenant helper policies, (c) explicit role GRANTs (`anon → none`), (d) `TENANT_TABLES` enrollment — missing any one is a tenant-isolation or availability defect. UNLIKE `tenant_memberships` (admin-only, SELECT to authenticated), CRM tables grant `authenticated → SELECT/INSERT/UPDATE` (the admin manages them via the app path); DELETE is NOT granted — archive via `archived_at` UPDATE. [Source: project-context.md#Architecture Rules (RLS narrows; GRANTs expose), #Critical Don't-Miss Rules; epic-2-retro#Key Insights Insight 1, #Key Takeaways 2; 20260625122433_tenant_foundation.sql:178-205]
- **Owner decision REVERSES the architecture/PRD "no personnummer" default — personnummer IS required for `private` customers (needed for ROT).** Architecture §7/§10, AR16, NFR16, and epics.md AC1 say "no personnummer by default"; the owner's 2026-06-18 sign-off (`owner-decisions-applied-2026-06-18.md`) supersedes that for `private`: implement personnummer, tenant-owned + access-controlled + not in default list UI; org.nr is the identifier for `company`/`brf`/`public`. The OLD Stop Condition ("stop if personnummer capture is requested") is RESOLVED — do not halt on it. Full GDPR/retention is deferred to full release (internal pilot). Surface the tension in the PR. [Source: owner-decisions-applied-2026-06-18.md#Story 3.1; epics.md#Story 3.1 AC1/Stop Conditions; architecture.md#7/#10 (the superseded default)]
- **Money discipline applies even though this story stores little/no money.** If any monetary field is added it MUST be integer öre (`bigint`), never floating kronor (NFR9/AR13). ### Architecture compliance

- **Command shape (architecture §5):** every CRM command follows steps 1-9 (resolve user → resolve active `tenant_admin` membership → reject unauth/no-membership → validate typed input, ignore client `tenant_id` → load target by tenant/lifecycle → execute via RLS-protected query → write append-only audit → return typed Result + user-safe code). The §5 command table lists EXACTLY the nine CRM commands this story builds. Time discipline: single command timestamp (injectable clock) for lifecycle/audit fields; tests assert it, never sleep. [Source: architecture.md#5]
- **Postgres + RLS (architecture §6/§9):** every business table carries a direct `tenant_id` (CRM tables do); child records duplicate `tenant_id` and use COMPOSITE constraints so child tenant matches parent (the same-tenant FK). RLS helpers `is_active_tenant_member`/`is_tenant_admin` express own-tenant policies (SELECT/INSERT/UPDATE; prefer archive over delete). The §9 test matrix rows this story exercises: Read/Insert/Update/Delete-archive isolation, Command isolation (reject mismatched parent ids), Unauthenticated access. [Source: architecture.md#6, #9]
- **Schema scope (architecture §7):** create ONLY `customers`/`facilities`/`contacts` from the v0 IN list. Do NOT create `company_settings`/`quote_terms`/`work_roles`/`articles`/`tenant_counters` (later Epic 3 stories) or any explicitly-absent deferred table. [Source: architecture.md#7]
- **Audit (architecture §15):** settings/pricing/CRM lifecycle changes are critical audit events. `actor_user_id` is nullable `ON DELETE SET NULL`; the table is append-only. Audit metadata excludes secrets/`.env`/raw files/broad free-text PII — the `sanitizeAuditMetadata` allow-list enforces it; route NO PII into metadata. [Source: architecture.md#15; src/server/commands/audit-metadata.ts]
