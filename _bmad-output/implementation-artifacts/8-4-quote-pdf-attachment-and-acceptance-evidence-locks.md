# Story 8.4: Quote, PDF, Attachment, And Acceptance Evidence Locks

Status: review

## Story

As a tenant admin,
I want a sent quote version's linked PDF/attachment file-links and an accepted acceptance's evidence file-link to become LOCKED (immutable + archive-only-on-delete) the moment the parent lifecycle rule requires it,
so that sent and accepted customer commitments cannot be silently re-pointed, mutated, or hard-deleted below the UI — enforced at BOTH the command layer AND a DB trigger that joins the frozen `QV409`/`AR704` lock-code FAMILY (not a divergent mechanism), with every archive/lock/blocked-delete written to `audit_events`.

## Context & Why This Story Is The Wave-2 Lock

This is **Wave 2 of Epic 8** and the **third and final scope of the shared lock-code FAMILY**. Epic 6 froze the SENT lock (`QV409 → QUOTE_VERSION_LOCKED`, `20260707120000_quote_version_sent_lock.sql`); Epic 7 froze the ACCEPTED lock (`AR704 → ACCEPTED_RECORD_LOCKED`, `20260711120000_accepted_record_lock.sql`). **Both migration headers explicitly name "Epic 8.4 locked-evidence-file" as the third scope of the family** (see `20260711120000_accepted_record_lock.sql` header: "Epic 6 sent-freeze R-605, Epic 7 accepted-lock R-704, Epic 8.4 locked-evidence-file"). 8.4 delivers the FILE-SIDE lock: `file_links.is_locked`/`locked_at` (persisted inert by 8.1) and `files.lifecycle_state='locked'` finally get ENFORCEMENT.

Story 8.1 **persisted the lock fields but shipped NO enforcement trigger** (see the migration comment: "the lock-ENFORCEMENT trigger is Story 8.4"). Today a locked-shaped `file_links` row is fully mutable/deletable at the DB, and NOTHING in `src/server` ever sets `is_locked=true`, `locked_at`, or `lifecycle_state='locked'` (grepped: zero writers). This story closes both halves: it LOCKS at the right lifecycle moment AND ENFORCES the lock two-layer.

**The two lock surfaces (R-822 — must AGREE with the parent locks):**
1. **`acceptance_evidence`** file-link (`owner_type='quote_acceptance'`, `purpose='acceptance_evidence'`) — created inside the frozen `accept_quote_and_create_job` RPC (7.2) and by `captureQuoteAcceptance` (7.1, `accept.ts`). Its parent `quote_acceptances` row is ALWAYS immutable once it exists (AR704 has no draft state). So the evidence link must be immutable the moment the acceptance exists.
2. **`quote_pdf`** file-link (`owner_type='quote_version'`, `purpose='quote_pdf'`) AND **`quote_attachment_snapshot`** file-link (`owner_type='quote_version'`, `purpose='quote_attachment_snapshot'`) — created by `generateQuotePdf` (6.3, `generate-pdf.ts`) and 6.1's version-creation RPC. Their parent `quote_versions` row is locked once `status <> 'draft'` (QV409). So these links must be immutable once the parent version is non-draft (sent/accepted/…).

**Scope of THIS story (the lock ENFORCEMENT + application + archive-only-delete + audit):**
- A `file_links` lock-enforcement DB trigger reusing the EXACT frozen `QV409`/`AR704` trigger SHAPE (fail-closed-by-construction, custom SQLSTATE, `security invoker`, `set search_path = ''`, schema-qualified) with a NEW sibling code (`FL823 → FILE_LINK_LOCKED`) — the family, not a fork.
- Lock APPLICATION: `file_links.is_locked=true` + `locked_at` + `files.lifecycle_state='locked'` set at the correct lifecycle moment (parent-state-keyed, mirroring `enforce_quote_version_child_sent_lock`'s parent-status lookup — because the RPCs that create the evidence/PDF links are FROZEN and cannot be edited).
- Archive-only-on-delete for a locked file (deletion is BLOCKED or converted to an `archived_at`/lifecycle UPDATE) + an `audit_events` row (who/what/when/why/target).
- The two-layer INT proof (command lock code AND direct-SQL trigger rejection) + AGREEMENT with `QV409`/`AR704` + the quote/acceptance lifecycle golden cases + the documented Lovable delta.

**Explicitly NOT in this story:** any NEW `files`/`file_links` COLUMN or NEW TABLE (H4 inventory + migration-reset EXACT policy enumeration stay UNTOUCHED — like 6.4/7.4, this migration adds only triggers/functions on the EXISTING tables and adds NO policy); editing ANY frozen migration or frozen RPC (`create_file_with_link`, `link_existing_file`, `mark_quote_version_sent`, `accept_quote_and_create_job`, both lock migrations); a hard-delete retention workflow for locked customer evidence (a STOP requiring legal sign-off — R-818/R-816); the correction/edit workflow after acceptance (owner-gated, R-714 — 8.4 enforces the immutability BOUNDARY only); object-byte reclamation from the bucket (archive-over-delete; a later storage-retention story); the file index + broad file audit UI (8.5); a MIME/size upload policy change (8.2/R-817).

## Acceptance Criteria

**AC1 — Sent-version file-links are locked; replace/delete through normal paths is blocked (from epics.md 8.4 AC1; R-812/R-822)**
**Given** a quote version whose `status <> 'draft'` (sent/accepted/…) with a linked `quote_pdf` and/or `quote_attachment_snapshot` file-link
**When** the linked PDF/attachment file-link is materialized at the send (or first-generation-after-send) moment
**Then** that `file_links` row is LOCKED (`is_locked=true`, `locked_at` set) and its `files.lifecycle_state` is `locked`
**And** replacing (re-pointing `file_id`), mutating any commitment column, or hard-deleting that link through a normal own-tenant path is BLOCKED at BOTH layers — the command surfaces the stable `FILE_LINK_LOCKED` code AND a DIRECT own-tenant authenticated UPDATE/DELETE below the command RAISES (SQLSTATE `FL823`)
**And** the file-side lock AGREES with the parent `QV409` sent-lock: a sent version's PDF/attachment link is immutable exactly when the version's own snapshot is (no divergence).

**AC2 — Accepted evidence becomes immutable except through an approved audited correction (from epics.md 8.4 AC2; R-812/R-822)**
**Given** a `quote_acceptance` with a linked `acceptance_evidence` file-link
**When** acceptance is committed (the `quote_acceptances` row exists)
**Then** the `acceptance_evidence` `file_links` row is LOCKED (`is_locked=true`, `locked_at`) and its `files.lifecycle_state` is `locked`
**And** replacing/mutating/deleting the evidence link through a normal path is rejected — `FILE_LINK_LOCKED` at the command AND `FL823` at the DB — the ONLY sanctioned change is the approved audited correction workflow (owner-gated, R-714; NOT built here)
**And** the file-side lock AGREES with the parent `AR704` accepted-lock (immutable once the acceptance exists).

**AC3 — Deletion of a locked file is archive-only, with a full audit event (from epics.md 8.4 AC3; R-813/§15)**
**Given** a locked file (or its locked link)
**When** deletion is requested through the app path
**Then** the hard delete is BLOCKED or converted to archive-only (an `archived_at` / `lifecycle_state='archived'` UPDATE) per the lifecycle rules — never a bytes/metadata hard delete (archive-over-delete; deletion of locked files is archive-only unless a later approved retention workflow says otherwise — architecture §14)
**And** an `audit_events` row records who (`actor_user_id`), what (`event_type` + `target_type='file_link'`/`file`, `target_id`), when, why (a user-safe reason), and the target record — with allow-listed metadata ONLY (NO raw file contents, NO bucket/object path, NO PII — §15).

**AC4 — Partial-lock / broken archive-delete leaves a consistent, retryable state (derived from R-813)**
**Given** the lock-apply + audit (or the archive + audit) sequence
**When** a mid-flow failure is injected
**Then** the end state is consistent and retryable — a file is NEVER locked without its lock persisted-and-auditable (or vice versa), an archive NEVER half-applies, and a "delete" NEVER partially removes a locked file
**And** the write is transactional or verified-compensated (per ADR-A009 — reuse the narrow-RPC discipline where a multi-record write must be atomic).

**AC5 — Cross-tenant locked-file attacks are denied with generic user-safe errors (derived from R-812/R-809)**
**Given** tenant A attempts to lock, unlock, mutate, archive, or delete a tenant B locked file/link (directly or via a crafted request)
**When** the cross-tenant locked-file negative matrix runs
**Then** every attempt is denied with the SAME generic user-safe shape (`TENANT_ACCESS_DENIED`) as not-found — no existence disclosure (R-809), no raw storage/DB error across the boundary
**And** the `FL823` lock trigger never leaks a locked-target detail (the RAISE message is generic, like `QV409`/`AR704`).

## Dev Notes
