# Story 2.4: Security Regression Harness For Tenant And Service-Role Boundaries

Status: review

## Story

As an implementation lead,
I want automated security regression checks for tenant isolation and privileged boundaries,
so that later stories cannot silently weaken Phase A security.

## Acceptance Criteria

1. **Given** the security harness, **when** the RLS negative suite runs, **then** for EVERY current tenant-owned table (`tenants`, `tenant_memberships`, `audit_events`) it covers read, insert, update, delete/archive, command-mismatch, anonymous access, and service-role containment dimensions — and the suite stays data-driven over a single tenant-table inventory so a new table enrolls by data, not by a copy-pasted parallel suite. (This story GENERALIZES the existing data-driven suites built in 2.2/2.3; it does not rewrite their assertions.)
2. **Given** the produced browser/client build output (`next build` → `.next`), **when** the containment check runs, **then** no service-role key name, secret placeholder, or server-only command internal is present in any browser-reachable bundle, public route payload, or build/log artifact — and the check FAILS (red) if a service-role reference is planted in a client path or a `NEXT_PUBLIC_`-prefixed service-role var name appears. The R-002 verification is the BUILT-bundle grep (the authoritative payload check), not only the source-level `check-service-role-containment.mjs` source scan.
3. **Given** a future PR adds a new tenant-owned table without enrolling it in the parameterized cross-tenant negative suite, **when** CI runs the security harness, **then** the harness compares the set of tenant-owned tables in the live schema against the set enrolled in the parameterized RLS negative suite and CI FAILS with a clear "table not covered" message naming the missing table (the H4 RLS table-inventory gate). This is the standing regression mechanism protecting every later tenant-owned table (Epics 3-9).
4. **Given** the inventory gate exists, **when** it is verified, **then** deliberately excluding one tenant-owned table from the enrolled set (on a scratch branch / via a test fixture) makes CI red — proving the gate actually bites, not that it is wired but inert. The harness MUST also fail on an intentionally mismatched tenant access attempt (an injected weakened/incorrect access path), proving the negative suite is not vacuously green.
5. **Given** anonymous (no-session) callers, **when** the harness runs, **then** anonymous privileged-access negatives cover the current protected DB surface (every tenant-owned table's SELECT/INSERT/UPDATE/DELETE AND the `is_active_tenant_member` / `is_tenant_admin` / `record_audit_event` privileged functions) — no anonymous caller can read, write, or EXECUTE a privileged path, asserted by the denial MECHANISM (SQLSTATE `42501`), not a vacuous empty-set/`false` disjunction.
6. **Given** the harness runs locally and in CI, **when** it executes, **then** it requires NO external/network-only security service, NO secrets, and NO global machine changes — all checks are local-Supabase + bare-Node + built-bundle grep, wired into the existing `.github/workflows/ci.yml` gate sequence (architecture §19) without weakening or reordering any existing gate.

### Inherited Epic-2 facts & gotchas (apply directly — from the retro feed + Stories 2.1/2.2/2.3)

- **DB-backed test assertions MUST assert the DENIAL MECHANISM, not a vacuous disjunction** (the hardest, most-repeated Story 2.2 review lesson). NEVER `expect(error !== null || (data ?? []).length === 0)` (cannot distinguish "denied" from "matched zero rows") and NEVER `expect(data ?? []).toEqual([])` (vacuously true when `data` is null). Use `expect(error).not.toBeNull()` + assert the SQLSTATE (`42501` permission denied; `23514` check violation) + `expect(data).toBeNull()`, plus an independent BYPASSRLS re-read proving the target row is unchanged. For a spoof-INSERT use a FRESH `crypto.randomUUID()` id so the denial is the privilege layer (`42501`), not a PK collision (`23505`). The existing suites already do this — keep it when you generalize them.
