# Story 6.2: Draft Quote Version Review And Timeline UX

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a tenant admin,
I want to review draft and historical quote versions in a timeline,
so that I can understand the current customer commitment and prior versions.

## Acceptance Criteria

1. **Given** a quote detail screen (`/quotes/[quoteId]`), **when** the admin opens it, **then** it shows a lifecycle header (quote status + customer + latest-version state + source calculation), a version timeline of ALL versions with **status badges that use TEXT not color alone**, and — for the selected version — its immutable snapshot (customer/facility/contact display, lines/section display model, totals, VAT/tax assumptions, terms, selected attachments, PDF status, acceptance-state placeholder, files, and lifecycle events). Every displayed money/VAT/total value is READ VERBATIM from the frozen `quote_versions`/`quote_version_lines` snapshot rows — NEVER recomputed from live calc/settings/pricing (R-616; AC Money/Tax Impact HIGH). A foreign/other-tenant quote id → generic not-found (no cross-tenant existence leak). [Source: epics.md#Story 6.2 AC1 + Technical Notes + Money/Tax Impact; ux-design-specification.md#6 (quote detail layout: lifecycle header + version timeline Draft/Sent/Accepted/Rejected-Lost/Superseded + selected-version immutable snapshot); architecture.md#4 (`/quotes/[quoteId]` route: Version timeline, selected version snapshot, PDF status, acceptance state, events), #11 (snapshot field list); test-design-epic-6.md#6.2-E2E-01/6.2-UNIT-02, R-616]
2. **Given** a DRAFT quote version, **when** the admin edits customer-visible draft content before send, **then** allowed edits update ONLY the draft version (the source calc/settings/prior versions are never touched), **and** the UI makes explicit (a visible warning, text) that once SENT a version becomes IMMUTABLE. Draft-edit is scoped to `status = 'draft'` versions; the edit path runs through a server command on the RLS client that re-asserts the version is a draft (a sent/accepted version can NOT be edited even if the client submits the id). [Source: epics.md#Story 6.2 AC2 + Stop Conditions (STOP if draft edit scope would let customer-visible SENT content be mutated); ux-design-specification.md#6 (draft versions editable before send; sent UI disables customer-visible editing + directs to "Create new version"; internal notes visually separated from snapshot content); architecture.md#11 (draft versions editable before send; once sent customer-visible fields immutable); test-design-epic-6.md#6.2-E2E-02, R-616/R-605]
3. **Given** a SENT or ACCEPTED version, **when** the admin selects it, **then** customer-visible fields render READ-ONLY (no edit affordances) **and** the UI directs changes to a NEW-version path ("Create new version" — the flow itself is Story 6.5; 6.2 surfaces the affordance/message, does not build the new-version command). [Source: epics.md#Story 6.2 AC3; ux-design-specification.md#6 (sent version UI disables customer-visible editing + directs to Create new version; new version explains what changed + preserves prior sent version); architecture.md#11 (sent → customer-visible fields immutable, changes require a new quote version); test-design-epic-6.md#6.2-E2E-02, R-616]
