# Epic 8 — Integration Review Findings

**Epic:** 8 — Required Files And Private Storage (stories 8-1..8-5; 8-1 pre-merged, 8-2..8-5 on branch)
**Date:** 2026-07-07
**Reviewer roster:** 3 lenses (Blind Hunter, Edge Case Hunter, Acceptance Auditor) × 2 models (primary + secondary), run independently over 4 story-chunks (8-2, 8-3, 8-4, 8-5), plus a dedicated whole-epic security review (0 HIGH / 0 MED / 1 LOW).

This section is the triaged, deduplicated integration result (deduped across reviewers, lenses, chunks, and the security review). Findings are ordered Decision → Patch → Defer. Every surviving finding is tagged with its severity. Duplicates that collapse to the same issue were merged (severity = MAX across merged sources); items already dismissed/deferred in a story's own Review Findings with a documented rationale were kept consistent with that record unless the epic view materially escalated them.

### Review Findings

- [x] [Review][Decision][Med] Client-supplied `revalidate_path` reaches `revalidatePath()` gated only by `startsWith("/")` — no owner-route allow-list — In `src/features/files/actions.ts` BOTH `uploadFileAction` (~L139-150) and `archiveFileAction` (~L270-273) read the hidden `revalidate_path` form field and, if it merely starts with `/`, pass it straight to Next's `revalidatePath()`. A tampered/mistargeted client can force revalidation of an arbitrary in-app route (e.g. `revalidate_path=/` busts the whole router cache). Not a tenant/data-leak (same-origin cache invalidation only) and the caller is always an authenticated `tenant_admin`, so impact is bounded to cache-thrash; but it is client-controlled input reaching a cache primitive with no binding to the actual owner route the action already knows. Merged sources: Blind Hunter (primary+secondary, chunk 8-2 [High] + chunk 8-5), Edge Case Hunter (8-2, 8-5), Acceptance/Auditor context. Recommended: fix: derive the revalidation route server-side from the resolved `ownerType`/`ownerId` (extend `ownerRoute()` to cover facility/contact/quote_acceptance/quote_version) and IGNORE the client `revalidate_path`; if a client-supplied path must be retained transitionally, validate it against a server-computed allow-list of the owner's legitimate routes rather than a bare `/` prefix.

- [x] [Review][Patch][Low] `/files` index preview row has no expiry→re-mint timer, diverging from the 8.3 shared-row contract [src/components/files/FileIndexList.tsx] — `FileIndexRowItem` computes `hasFreshLink` once at render via `isSignedUrlExpired(state.expiresAt, new Date().toISOString())` with NO `useEffect`/`setTimeout` wall-clock tick, no `linkExpired` branch, and no re-open control — unlike the shared `FilePreviewRow` (used by every entity/commitment panel) which carries the full 8.3 timer + "Länken har gått ut — öppna igen" machinery. A signed link minted in the index stays rendered/clickable after its TTL passes; the click then fails with the generic denial (no security impact, graceful). Concrete defect with a realistic trigger (TTL elapses while the row stays mounted). Merged sources: Blind Hunter (primary 8-5), Edge Case Hunter (primary+secondary 8-5), Acceptance Auditor (primary+secondary 8-5, Low). Fix: reuse `FilePreviewRow` (or extract its `nowMs`/timer + `linkExpired`/re-open logic) in the index row so the index honors the same expiry→refresh behavior as every other file surface.

- [x] [Review][Defer][High] Acceptance-evidence upload has no lifecycle/lock gate — new evidence can still be attached to an already-accepted (committed) acceptance across the assembled epic [src/server/commands/files/files.ts (uploadFile.execute); src/features/files/acceptance-panel.tsx] — deferred, owner-accepted and already ledgered. `uploadFile.execute` gates only owner *visibility* (`assertUploadOwnerVisibleOrThrow`) and inserts a fresh `file_links` row with no accepted/locked-state check on the owner acceptance, so a tenant_admin can keep attaching new `acceptance_evidence` files to a committed acceptance. 8-4's `apply_file_link_lock` (BEFORE INSERT) locks each NEW link the instant it lands (closing the *immutability* half) but does NOT block the *upload* itself — so AC2's "wrong-lifecycle rejected" clause remains unmet for the acceptance owner, and the panel simultaneously shows "Filen är låst … kan inte ersättas eller tas bort" on existing evidence while offering a live upload form. Story 8-2 self-flagged this as `[Review][Defer][Med]` and named 8-4 as owner; 8-4's scope explicitly did NOT touch the upload path and no later story owns it — the epic view escalates the severity to High (a literal AC2 miss its named owner did not close) but not the disposition: under the owner's demo-data-only MVP decision (2026-07-03) this is an accepted residual, already tracked in deferred-work.md. Merged sources: Acceptance Auditor (8-2 primary [High] + secondary, 8-4 primary+secondary [Med], 8-5 secondary). Owner: an owner call plus a follow-up to add a lifecycle/lock gate (reject an upload targeting a committed/locked acceptance with a distinct user-safe code, e.g. `ACCEPTANCE_LOCKED`) if real-customer evidence use is proposed.

- [x] [Review][Defer][Med] Customer detail page fires unbounded parallel `readEntityFiles` per facility AND per contact (N+1 fan-out) [src/app/(app)/customers/[customerId]/page.tsx] — deferred, real-but-bounded scalability under the demo-data-only posture. Each facility and contact triggers an independent `readEntityFiles` (each constructing its own Supabase client) via `Promise.all(...map(...))` with no batching/limit; a large customer fans out to dozens/hundreds of concurrent reads on one force-dynamic render. No security/correctness defect; degrades TTFB/connection-pool pressure only at data volumes well beyond Phase-A pilot. Merged sources: Blind Hunter (primary+secondary 8-2, Med), Edge Case Hunter (primary+secondary 8-2). Owner: a scale-hardening pass — batch into a single `owner_id IN (...)` query grouped client-side when real data volumes are in scope.

- [x] [Review][Defer][Low] Upload MIME is the client-declared `File.type`, not byte-sniffed — content-vs-declared-type integrity gap [src/features/files/actions.ts; src/server/commands/files/validation.ts] — deferred, security-cleared and already ledgered (R-817 / owner-gated). The allow-list gates the client-declared `File.type` string, not the real leading bytes; `bytes` are cross-checked for LENGTH only. The dedicated whole-epic security review rated this its single LOW and confirmed it is NOT a reachable exploit: `ALLOWED_MIME_TYPES` is a closed allow-list excluding every active-content/XSS-capable type (`text/html`, `image/svg+xml`, `application/octet-stream`, executables), the bucket is private, and delivery is via short-lived signed URLs. The misleading "re-derived from the file itself" comments were already corrected (2026-07-07 story fix). Merged sources: Security review [LOW], Blind Hunter (primary [High] + secondary 8-2), Edge Case Hunter (8-2). Owner: owner Sign-Off / R-817 — add magic-byte sniffing (reject a declared-vs-real mismatch as `VALIDATION_FAILED`) plus an INT case with an allowed declared mime + disallowed real bytes, when a final file-type policy is set or real-customer uploads are proposed.

- [x] [Review][Defer][Low] `archiveFile(hardDelete:true)` returns `FILE_LINK_LOCKED` even for an UNLOCKED file — a misleading code [src/server/commands/files/files.ts:306] — deferred, already story-triaged (8-4/8-5 Low) and ledgered. The `hardDelete === true` guard throws `FILE_LINK_LOCKED` before loading/branching on lifecycle, so an unlocked draft/linked file's crafted hard-delete returns "Filen är låst…" though nothing is locked. Functionally safe (no row deleted; `authenticated` has no delete grant; `hardDelete` is a crafted-only surface with no UI). Merged sources: Blind Hunter (primary+secondary 8-4), Edge Case Hunter (secondary 8-4), Acceptance Auditor (primary 8-4, Low). Owner: a follow-up refinement — surface a distinct non-lock code (e.g. `HARD_DELETE_NOT_PERMITTED`) for an unlocked target so the message matches the reason.

- [x] [Review][Defer][Low] 8.3 expiry→refresh headline UX has no executing E2E; the denied-preview E2E can pass vacuously [tests/e2e/files/entity-file-preview.e2e.spec.ts] — deferred, already story-triaged (8-3 Low) and ledgered, and the assembled epic intentionally does not re-open it. `[8.3-E2E-04]` is unconditionally `test.fixme(true, …)` and `[8.3-E2E-03]`'s assertions sit inside `if (await previewError.count())` with no deterministic denial driver, so both provide no client-wiring teeth end-to-end. The AC2 authorization teeth ARE proven at the INT/command layer (archive/delete-mid-flight → `FILE_ACCESS_DENIED`) and the expiry verdict is unit-covered; only the UI timer→re-open loop is unproven E2E. Merged sources: Blind Hunter (primary+secondary 8-3), Edge Case Hunter (8-3), Acceptance Auditor (primary+secondary 8-3, Med/Low). Owner: a test-DX pass — add a low-TTL E2E env or deterministic clock seam so the re-open re-authorization can be exercised without a flaky sleep.
