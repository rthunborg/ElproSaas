# Epic 3 Integration Code Review — Triaged Findings

Chunked integration review of the assembled Epic 3 diff (Stories 3.1–3.5). Lenses:
per-story BLIND (adversarial) + EDGE (edge-case) for each of 3.1–3.5, two cross-story
integration auditors (different models), and one dedicated cross-story security pass
(0 HIGH / 0 MEDIUM / 0 LOW — clean). Findings were normalized, verified against
`diff.patch`, and deduplicated aggressively across chunk boundaries and across lenses
(on merge, severity = MAX).

Post-triage surviving counts: Critical 0 / High 1 / Med 4 / Low 4 (9 total). Dismissed
as noise/false-positive/already-guarded/informational: 34.

### Review Findings

- [x] [Review][Defer][Low] Personnummer is present in clear text in the client-component payload (mask is cosmetic only) — `CustomerDetail.tsx` is a `"use client"` island that receives `customer.personnummer` raw; `maskPersonnummer` + the "Visa" toggle only govern what is painted, so the raw value is serialized into the RSC/props payload on every private-customer detail view regardless of reveal. This surface is admin-only, own-tenant (RLS + `(app)` route auth), and the dedicated cross-story security pass reviewed exactly this path and cleared it as an owner-approved, access-controlled reveal surface (0 findings). Not a cross-tenant or unauthorized exposure. Recommended: dismiss: security pass cleared it as owner-approved and access-controlled (admin-only, own-tenant); if a stricter server-gated reveal (raw pnr never in payload until explicitly fetched) is later desired, log it as an Epic 6 privacy-hardening item, not an Epic 3 defect.
- [x] [Review][Defer][Low] Epic-3 test-design "no personnummer" P0/exit-criteria contradicts the shipped, owner-approved schema — the test design (R-009 + Exit Criteria "No personnummer field exists by default on any CRM table") asserts personnummer absence as a hard gate, but `customers` carries a `personnummer` column per the 2026-06-18 owner decision, correctly and consistently implemented (list projection excludes it, detail masks it, audit metadata drops it, identifier-by-type CHECK ties it to `private` only). The divergence lives only in migration prose, so an epic-boundary trace could auto-FAIL against the now-stale assertion. Recommended: defer: reconcile the test-design/exit-criteria text to the 2026-06-18 owner decision (personnummer IN for `private` customers) — no code change; a spec/gate-reconciliation item so the trace does not FAIL on an obsolete R-009 assertion.
- [x] [Review][Patch][High] Work-role / article REACTIVATE path is specified but implemented at NO layer — archive is a one-way door, the archived row is unrecoverable AND invisible to the editor [src/server/commands/pricing/work-roles.ts:6723-6733; src/server/commands/pricing/articles.ts:6377-6387; src/features/pricing/read.ts:4357,4395]. Story 3.4 AC2 explicitly lists "creates / updates / archives / **reactivates** a role" and Task 2.2 states the design intent "archive/reactivate via UPDATE". Verified in the diff: the `upsertWorkRole`/`upsertArticle` UPDATE branch writes ONLY `display_name`/rates (resp. `name`/`sku`/`unit`/price) and never touches `is_active`; `archiveWorkRole`/`archiveArticle` only set `is_active = false`; there is NO command anywhere that sets `is_active` back to `true`; and `readWorkRoles`/`readArticles` filter `.eq("is_active", true)`, so an archived row is never even listed for the admin to select. NOTE: the per-story 3-4 review deferred this as a [Low] on the premise that "the command/data model CAN reactivate" — that premise is factually wrong (no `.update({ is_active: true })` exists), so at the integration level this is a genuine High AC gap. Fix: add a reactivate path (either an `upsert*` UPDATE that can set `is_active = true`, or a dedicated `reactivateWorkRole`/`reactivateArticle` command) plus an "include archived"/reactivate affordance (lift the `is_active=true` read filter behind a toggle).
- [x] [Review][Patch][Med] `logo_url` is silently wiped to NULL on every company-settings save (data loss on the PDF-branding field) [src/components/settings/CompanySettingsForm.tsx:2765-2829; src/features/settings/form-parsing.ts:4743; src/server/commands/settings/company-settings.ts:6825]. `updateCompanySettings` UPSERTs the full row with `logo_url: input.logo_url ?? null`, and `parseCompanySettingsForm` reads `logo_url: field(form, "logo_url")` — but `CompanySettingsForm` renders NO `logo_url` input, so `input.logo_url` is always undefined and every UI save writes `logo_url = null`, discarding any previously-stored logo (the migration calls this "PDF-ready branding"). Fix: either render a `logo_url` TextField, or preserve the existing value on upsert (omit the field when absent rather than forcing `?? null`).
- [x] [Review][Patch][Med] Pricing archive failures are silently swallowed — the user sees nothing when an archive is denied or errors [src/components/pricing/WorkRolesEditor.tsx:2579-2582; src/components/pricing/ArticlesEditor.tsx:143-146]. Both editors do `const [, archiveAction] = useActionState(archive*Action, PRICING_ACTION_INITIAL)` — the returned archive state is destructured to nothing, so a `TENANT_ACCESS_DENIED`/`SERVER_ERROR` from `archiveWorkRoleAction`/`archiveArticleAction` produces no error banner, no retry affordance; the row simply stays and the admin believes it was archived. The full `runPricing`/`mapErrorToState` error state is built and then discarded. Fix: bind the archive state and render its `formError` (and retry affordance for transient `SERVER_ERROR`), mirroring the save form.
- [x] [Review][Patch][Low] Snapshot `company_settings.defaultVatDisplay` is typed as bare `string`, not the closed `VatDisplayMode` union — a cross-story type-safety gap in the one artifact billed as a "documented contract" [src/lib/snapshots/types.ts:5305; src/lib/snapshots/build.ts (CompanySettingsSourceRow.default_vat_display)]. The settings layer defines `VAT_DISPLAY_MODES = ["company_togglable","company_excl"] as const` / `VatDisplayMode`, and the DB CHECK constrains the column, so it is safe at runtime — but a downstream Epic 4/6 consumer reading `defaultVatDisplay` off a frozen snapshot gets no compile-time narrowing. Fix: import `VatDisplayMode` (or duplicate the literal union) into `src/lib/snapshots/types.ts` and type the field/source-row accordingly. (Independently flagged by both cross-story auditors.)
- [x] [Review][Defer][Med] Snapshot `company_settings` variant omits the PDF-identity fields Epic 6 will need (`org_nr`, address lines, `postal_code`, `city`, `email`, `phone`, `logo_url`) — captures only `companyName` [src/lib/snapshots/types.ts:5298-5306; src/server/snapshots/resolve-source.ts:7382-7387] — deferred
- [x] [Review][Defer][Med] Snapshot contract carries no compile/runtime marker forcing a future Epic 6 "mark sent" command to check terms `approvedAt !== null` before treating captured terms as usable — the stop-condition is prose-only [src/lib/snapshots/types.ts:5316-5322; src/lib/snapshots/build.ts] — deferred
- [x] [Review][Defer][Low] Empty-patch UPDATE: `updateCustomer`/`updateFacility`/`updateContact` issue `.update({})` when only `id` is supplied (no empty-patch guard); depending on PostgREST behavior an id-only update can yield zero rows and be mapped to a false `TENANT_ACCESS_DENIED` for a legitimately-owned row [src/server/commands/crm/customers.ts:5699-5711; src/server/commands/crm/facilities.ts:5842; src/server/commands/crm/contacts.ts:5479] — deferred

Notes on the two integration auditor Med findings deferred above: both auditors agree these are deliberate, documented scope decisions (Story 3.5 Open Question 1; Epic 6 owns PDF-identity capture and the send-time approval gate). They are recorded here as explicit Epic 5/6 obligations for the epic-boundary trace, not silent gaps, and a low-cost mitigation is a type-level doc/marker on the `CompanySettingsSnapshot` / `QuoteTermsSnapshot` variants.

- [x] [Review][Defer][Low] Archived-read failure now gates the ENTIRE pricing page. `page.tsx` folds `archivedWorkRolesError ?? archivedArticlesError` into the same top-level `const error` that renders the page-level banner and suppresses the primary editors, so a transient failure loading the OPTIONAL archived lists degrades the whole view even when the active work-roles/articles lists loaded fine. Archived is a secondary affordance behind a toggle; its read failure should not gate the main UI. Introduced by this fix; realistic trigger (a transient DB blip on one of the four now-parallel reads). Recommended: defer (fix-small) — scope the archived-read errors to a banner INSIDE the archived section (or ignore them and just render zero archived rows), leaving the page-level `error` to the two active reads only. [src/app/(app)/settings/pricing/page.tsx:35-39]
- [ ] [Review][Defer][Low] Stale lifecycle-error banner can persist across a later successful DIFFERENT action. `archiveState`/`reactivateState` are independent `useActionState` hooks; after a failed archive paints the `*-archive-error` banner, a subsequent SUCCESSFUL reactivate (or vice-versa) does not clear the other action's error state, so the stale red banner lingers until that exact action re-runs and succeeds. Minor UX residual, realistic two-step trigger. Recommended: defer to a pricing-UI polish pass — clear/supersede the lifecycle banner on any successful lifecycle action (e.g. prefer the most-recently-submitted action's state). [src/components/pricing/WorkRolesEditor.tsx:58-63; src/components/pricing/ArticlesEditor.tsx:106-111]
- [ ] [Review][Defer][Low] A no-op reactivate of an ALREADY-active row writes a spurious `*.reactivated` audit row. `reactivateWorkRole`/`reactivateArticle` do `.update({is_active:true}).eq("id",…).select("id")` with NO `.eq("is_active", false)` filter, so reactivating a row that is already active (stale archived list rendered in a concurrent tab) matches by id, returns the row (not zero → no denial), and appends a redundant reactivate audit row. Benign (append-only, correct tenant, allow-listed `{targetId}` metadata) but noisy. Realistic trigger (two tabs). Recommended: defer to a pricing-command hardening pass — add `.eq("is_active", false)` to the reactivate UPDATE (mirror the intent of archive) so a no-op reactivate is a clean zero-write, or accept the idempotent audit row as designed. [src/server/commands/pricing/work-roles.ts:146-159; src/server/commands/pricing/articles.ts:129-141]
- [ ] [Review][Defer][Low] Reactivate E2E derives its unique role name from `Date.now().toString(36)` (weaker than the integration suites' `crypto.randomUUID()`). Two parallel Playwright workers (or fast reruns) hitting the same millisecond produce identical names, and the test locates rows by `hasText: roleName` + asserts `toHaveCount(1)` — a flake risk. Test-quality only, no product impact. Recommended: defer to a test-hardening pass — switch the E2E name key to `crypto.randomUUID()` to match the integration discipline. [tests/e2e/pricing/pricing.e2e.spec.ts:~647]
- [ ] [Review][Defer][Low] No component/E2E test exercises a FAILING archive/reactivate to prove the new `*-archive-error` banner + "Försök igen." retry hint render. The auditor confirmed the banner logic is correct and the command-layer failure→state mapping (TENANT_ACCESS_DENIED / SERVER_ERROR) is integration-tested, but neither the E2E nor a component test drives a lifecycle-action failure to assert the banner actually paints. Coverage gap only (banner logic is a straightforward `status === "error"` render). Recommended: defer to a test-hardening pass — add a component/E2E case that forces an archive/reactivate error and asserts the `data-testid="{work-role|article}-archive-error"` `role="alert"` node (and the retryable suffix on `SERVER_ERROR`). [src/components/pricing/{WorkRolesEditor,ArticlesEditor}.tsx; tests/e2e/pricing/pricing.e2e.spec.ts]
