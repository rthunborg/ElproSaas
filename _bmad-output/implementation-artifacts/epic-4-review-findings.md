### Review Findings

- [x] [Review][Decision][Med] Deduction rate validated with VAT-named rule leaks a VAT-scoped error code across the story boundary — `estimateDeduction` validates `profile.deductionPercentBp` via the reused `isVatRateBp` predicate (spec-sanctioned) but returns `code: "INVALID_VAT_RATE_BP"` on failure, so a malformed *tax* profile rate surfaces as an `INVALID_VAT_RATE_BP` discriminant with no `INVALID_DEDUCTION_RATE_BP` alternative. Defense-in-depth only — shipped profiles are frozen `const` and always valid, so the branch is effectively unreachable in production; the smudge is a self-describing-error-surface contract issue, not a live bug. [src/lib/money/tax.ts:802-803] (blind@primary + edge@primary + auditor@primary) Recommended: fix: widen `MoneyErrorCode` additively with a tax-scoped `INVALID_DEDUCTION_RATE_BP` and return it here (the additive widening is exactly what Story 4.3 Dev Notes told the dev to do), keeping the reused `isVatRateBp` predicate. _Auto-resolved (epic mode): fix per triage recommendation — carried into the epic fix pass._
- [x] [Review][Decision][Med] `selectVatDisplay` silently falls back to `private`/gross on an unknown posture AND falsifies the returned `posture` field to `"private"` — the fallthrough for any unrecognized `VatDisplayPosture` (a typo'd or future stored `default_vat_display` value) returns the most legally-loaded gross-only view and overwrites `posture: "private"` in the output, so anything that logs/persists the view records a fabricated posture with no error/warning signal, inconsistent with the engine's typed-failure discipline everywhere else. [src/lib/money/vat.ts:1123-1124] (blind@primary + blind@secondary + edge@secondary) Recommended: fix: keep the conservative gross fallback but return the *original* input posture in the view (do not relabel to `"private"`) — or surface a typed failure — so an invalid stored display value cannot be silently laundered into a `private` label. _Auto-resolved (epic mode): fix per triage recommendation — carried into the epic fix pass._
- [x] [Review][Defer][Med] `company_togglable` default `primaryOre` is GROSS (incl-VAT) for a company customer under a nominally excl-first setting — the stored settings axis is `company_togglable`/`company_excl` (excl-by-default, togglable-to-incl), but the selector resolves `company_togglable` with `primaryOre: grossOre` as the *default* surfaced amount. AC2 is satisfied (net/VAT/gross are all representable on the object), but the choice of incl-VAT-as-default for a company customer is a presentation-policy decision that Sign-Off Q2 says is owner-pending; the module header documents only the private→always-incl invariant as the Q2 assumption, not this company-togglable-defaults-to-gross choice. [src/lib/money/vat.ts:1120-1121] (auditor@primary) Recommended: defer: add an explicit Q2 sign-off line noting the company-togglable-defaults-to-gross assumption is a conservative build (not owner-approved), and confirm the intended company default at the Epic-4 VAT-display working session — the conservative build stands until then. _Auto-resolved (epic mode): deferred per triage recommendation — logged to deferred-work.md for the Sign-Off Q2 working session._
- [x] [Review][Decision][Low] `capturedAt` is never validated before being frozen into the tax/VAT assumption snapshot — `estimateDeduction`/`buildTaxAssumptionSnapshot` (and `buildVatAssumptionSnapshot`) thread `capturedAt` straight into the frozen assumption; an empty string, non-ISO, or wrong-format timestamp is captured verbatim while every other input in the engine is defensively type-guarded. The value anchors a frozen assumption that Epic 6's quote-version freeze will consume, so a malformed capture instant is a latent weak link. [src/lib/money/tax.ts:858] (blind@primary + edge@primary) Recommended: fix: add a non-empty-string guard on `capturedAt` in both snapshot builders (reject `""`/non-string with a typed failure, matching `INVALID_QUANTITY`-style discipline); stricter ISO-8601 format validation can follow as a hardening step. _Auto-resolved (epic mode): fix per triage recommendation — carried into the epic fix pass._
- [x] [Review][Patch][Low] Golden-master "no hidden rate literal" grep comment overstates what the loop scans — the tax `tax.golden.test.ts` comment claims bare-integer forms `30`/`50` are forbidden, but the loop only tests the fraction forms `/0\.30/`, `/0\.50/`, `/1\.3/`; the VAT `vat.golden.test.ts` twin claims `25` yet only scans `/0\.25/`, `/1\.25/`. A `basis * 30 / 100` hidden-percent literal would pass the "epic-blocker" guard, and the comment advertises a stronger guarantee than the code delivers. [tests/unit/lib/money/tax.golden.test.ts:4012-4014] (blind@primary) — a bare-`30`/`25` source grep is impractically noisy (matches line refs, array sizes, öre values), so the unambiguous fix is to correct the comments to state only the fraction forms are scanned (the `/ 10000` bp-denominator structural check already prevents a real hidden-percent path).
- [x] [Review][Patch][Low] `ORGNR` privacy-scan regex is byte-identical to `PERSONNUMMER`, so the "EXPLICIT distinct guard (R-411)" comment is false — both are `/\b\d{6}-\d{4}\b/`, so asserting both adds zero detection coverage while presenting two independent controls; a real 10-digit no-dash Swedish orgnr (`5560000000`) is caught by neither. [tests/unit/lib/money/golden-pack.test.ts:2587-2588] (blind@primary + blind@secondary) — make `ORGNR` a genuinely distinct pattern (add the `\b\d{10}\b` no-dash orgnr shape) so it delivers the distinct guard the comment claims, or downgrade the comment to "reuses the personnummer shape for both PII classes".
