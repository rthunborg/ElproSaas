### Key Insights And Patterns

**Insight 1 — A thin per-story review can under-rate a finding on an unverified premise about another layer; the cross-story integration pass is the real backstop.**
The 3.4 reactivate gap was dismissed as Low by the per-story auditor on the claim "the command can already reactivate via UPDATE" — which was simply not true anywhere in the diff. The lesson generalizes beyond this one finding: a thin/fast review pass trades verification depth for speed, and any claim it makes about "another layer already handling X" should be treated as a hypothesis, not a fact, until the integration pass (which reads the whole diff) confirms or refutes it.

**Insight 2 — Silent-failure / data-loss bugs hide behind a specific shape: unbound action state + force-nulled optional upsert fields.**
Both Tier-B-caught bugs (`logo_url` wipe, swallowed archive errors) share the same root cause pattern: a server action's error/result state exists correctly in the type system but is either destructured away (`const [, action] = useActionState(...)`) or an absent optional field is coerced to `null` on write (`input.logo_url ?? null`) instead of omitted. This is now a stated convention: bind + render every action's error state; on upsert, omit-absent rather than force-null optional fields.

**Insight 3 — Long-running dev-story/ATDD agent processes are unstable in this environment, but disk-state survives; verify directly rather than trusting process exit.**
Four crash events across five stories (3.2 dev-story, 3.4 dev-story ×2, 3.5 ATDD) all left complete, correct, gate-passing work on disk — only cheap bookkeeping was lost. The orchestrator's standing mitigation (verify gates against the file system before trusting a "done" claim) worked every time. This is now a proven operational pattern, but the crash *rate* itself (4 events in 5 stories) is worth treating as a real, recurring risk rather than an anomaly — smaller dev-story chunks or more frequent checkpoints are the forward mitigation if the rate doesn't improve.

**Insight 4 — Stale RED-phase test-file headers persist verbatim after suites flip from skipped to green.**
The test-review found this across 11 files: headers still narrate "why `describe.skip`" or "`notYetImplemented()` placeholder" even though the suite is fully green with top-level imports. Harmless today, but a reader skimming a header could wrongly conclude a suite is disabled. New convention: clear/rewrite the red-phase header comment as part of the same PR that flips a scaffold from skipped to green — don't leave it for a later hygiene pass.

**Insight 5 — Planning documents can go stale mid-epic when an owner decision reverses an earlier assumption, and the stale text becomes a latent gate-failure risk.**
The Epic 3 test design (drafted 2026-06-30) still asserts "no personnummer field by default" as R-009/an exit criterion, but a 2026-06-18 owner decision reversed this for `private` customers (required for ROT). The implementation and tests correctly encode the *current* (owner-approved) contract — this is not a coverage gap — but the stale prose in the test-design document could cause a future automated trace run to spuriously FAIL against an obsolete assertion. Caught and flagged for reconciliation at this retro rather than left to surprise a future gate run.
