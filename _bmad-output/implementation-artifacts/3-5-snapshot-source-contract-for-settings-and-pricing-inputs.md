# Story 3.5: Snapshot Source Contract For Settings And Pricing Inputs

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an implementation lead,
I want a shared, documented snapshot-source contract over the mutable settings and pricing inputs (work roles, articles, VAT defaults, quote terms),
so that later calculations and quotes can explain EXACTLY where a customer-visible value came from, and a previously-built snapshot never silently recalculates when its mutable source later changes.

## Acceptance Criteria

1. **Given** the mutable Phase-A sources `work_roles` (3-4: `cost_rate_ore`/`sell_rate_ore`), `articles` (3-4: `unit_price_ore`), `company_settings` (3-3: `vat_rate_bp`/`default_vat_display`), and `quote_terms` (3-3: `terms_text` + the nullable `approved_at` sign-off), **when** the snapshot contract captures one for downstream use, **then** a PURE builder produces a stable, documented `SnapshotSource` value that records — per the contract — the **source id**, a **kind** discriminator, the **display name/content**, **monetary values in INTEGER ÖRE** (never float kronor, never a re-derived/computed value), the **VAT assumptions** (rate in basis points + display mode) where the source carries them, the **source timestamp/version** (`updated_at` of the source row), the **terms sign-off state** (`approved_at`, captured as-is including NULL), and the **tenant ownership** (`tenant_id`). The contract is SMALL and aligned with the ACTUAL columns those four tables ship — NO invented fields, NO new columns, NO calculation. [Source: epics.md#Story 3.5 AC1; architecture.md#11 (snapshot source list: work-role prices, article prices, VAT rate/amount/assumptions, terms), #10 (öre bigint; VAT basis points), #22 (snapshot builders live in `src/lib/snapshots`); epic-3 retro-note (capture source id, display name/content, öre, VAT assumptions, source timestamp/version, tenant ownership; reuse the REAL fields — do NOT invent); 3-4 story (work_roles/articles real columns); 3-3 story (company_settings vat_rate_bp/default_vat_display; quote_terms terms_text + nullable approved_at)]
2. **Given** a `SnapshotSource` value has been built from a source row, **when** that source row is LATER mutated (rate/price/terms/VAT edited) or archived, **then** the previously-built `SnapshotSource` is UNCHANGED and remains fully explainable — it does NOT silently recalculate from the now-mutated source. The builder copies values BY VALUE into a deeply-immutable (frozen) plain object holding no live reference to the source row; a test MUTATES a source after building and PROVES the prior snapshot's captured values are byte-for-byte identical. This is the load-bearing SNAPSHOT-IMMUTABILITY invariant. [Source: epics.md#Story 3.5 AC2 ("the previous snapshot remains explainable and does not silently recalculate from the mutable source"); architecture.md#11 (quote version is the customer-commitment snapshot; once captured, immutable), ADR-A004 (snapshotted assumptions); epic-3 retro-note (SNAPSHOT IMMUTABILITY R-008 score-6 — a snapshot, once built, must NOT silently recalculate; tests must prove mutating the source after a snapshot does NOT change the prior snapshot; "snapshot values frozen — no silent recompute"); project-context.md#Money, Tax, And Quote Rules (snapshot values; immutability)]
3. **Given** the resolved tenant (from active `tenant_admin` membership) and a SOURCE ID supplied for a snapshot, **when** the snapshot-source RESOLVER runs, **then** cross-tenant use of a source id (work role / article / company_settings / quote_terms id belonging to ANOTHER tenant) is REJECTED by BOTH layers: (a) **command/resolver validation** — the source is read on the per-request RLS client and a foreign-tenant id returns zero rows → a typed `TENANT_ACCESS_DENIED` (no snapshot is built, no leaked existence signal); AND (b) **RLS** — the existing own-tenant `is_tenant_admin` SELECT policies on all four tables make the foreign row invisible, proven by the cross-tenant integration suite. The resolver NEVER trusts a client-supplied `tenant_id` — the resolved membership tenant is the only authority, and the built snapshot's `tenant_id` is the resolved tenant. NO new table is created, so NO new H4 inventory enrollment is required (the four source tables are already enrolled by 3-3/3-4). [Source: epics.md#Story 3.5 AC3 ("cross-tenant use of source IDs is rejected by command validation and RLS"), Security/RLS Impact (Medium-high — prevents cross-tenant source spoofing); architecture.md#6 (RLS read isolation; resolved tenant authority), #9 (RLS test matrix); epic-3 retro-note (CROSS-TENANT — cross-tenant use of a source id must be rejected by BOTH command validation AND RLS; reuse the envelope ownership-verify + RLS patterns); project-context.md#Security Regression Harness Rules; 3-3/3-4 stories (company_settings/quote_terms/work_roles/articles already enrolled in the cross-tenant + anon suites + H4 gate)]
