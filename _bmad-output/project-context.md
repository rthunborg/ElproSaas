## Scope Manifest Governance (Epic 10, ADR-B003)

- **`src/scope/manifest.ts` is the SINGLE machine-readable scope source of truth.** It replaced the Epic-9 retro failure mode: four independently-authored copies of "what surface exists" (file-index deny-list, nav-guardrail expected set, H4 `TENANT_TABLES` inventory, deferred-token scope scans) that DRIFTED. Those four are now PURE `§5.3` derivations (`navRoutesFromManifest`, `tenantTablesFromManifest`, `deferredFileTokensFromManifest`, `fileOwnerTypesFromManifest`, in `manifest-schema.ts`) off the ONE `SCOPE_MANIFEST` constant. Do NOT reintroduce a hand-maintained parallel copy of any scope list — extend the manifest and let the derivation flow.
- **The manifest is `satisfies ScopeManifest`-guarded (compile-time shape) AND coherence-validated at runtime.** `validateManifestCoherence` (unit-pinned by `tests/unit/scope/manifest-coherence.test.ts`, each rule with a biting negative case) enforces: an `active` module carries `epic` + `activatedAt`; every surface is traceable to an `active` module (the A22 "presence is not coherence" lesson); a `pending` module carries NO live nav/table/widget; the public-surface union stays ⊆ the ADR-B004 closed set of three (`calendar_feed`/`asset_qr`/`unsubscribe`); module ids are unique; and NO nav route / tenant table / file owner type / widget (hard) NOR notification category / public surface / deferred file token (soft) is declared by two modules (the cross-module UNIQUENESS invariant — the improvement over the `READINESS_CODES` gap, which checked membership but not uniqueness).
- **Module lifecycle: `pending` → `active` in the SAME PR as the module's first schema/nav change (§5.5).** A `pending` module declares only future-surface metadata (its `deferredFileToken`, if any); every live-surface array stays empty. Activating it (setting `status:'active'` + `epic` + `activatedAt` + populating its `navItems`/`tenantTables`/`fileOwnerTypes`) MUST land atomically with the migration/route that makes the surface real — never one PR ahead. On activation a module's `deferredFileToken` drops out of the derived deny-list automatically.
- **Epic 10's activation seam is the `quotes` module:** Stories 10.2/10.3 enrolled `quote_lost_reasons`/`quote_follow_ups` into the already-`active` `quotes` module in the SAME PR as their migration. Epics that DEEPEN an already-active module (Epic 10 deepened `quotes`/`dashboard`; Epics 16–19 deepen `jobs`/`dashboard`) add tables/surface to the existing module — they do NOT create a separate `pending` module.
- **The Phase A `active` partition is exact: 7 nav items / 26 tenant tables / 7 file owner types** (the tenant count grew 24→26 in Epic 10). The derivation tests assert the union equals the authored partition, so a mis-partitioned or forgotten table fails loud. Note the non-obvious placements the manifest encodes: `tenant_counters` sits in `quotes`; `work_roles`/`articles` sit in `settings` (they live under `/settings/pricing`); `foundation` (`tenants`/`tenant_memberships`/`audit_events`) is nav-less; `dashboard` owns zero tenant tables in Phase A (widgets/read-models arrive at E19). E12 (`provisioning`) is the one PLATFORM-scoped module (`scope:'platform'`) — an enumerated exception, not a tenant module.
- **NOT yet derived off the manifest (deliberate §5.3 "later derivation" seams — do not assume they are wired):** the runtime file `OWNER_TYPES` union, the widget registry, the notification-producer registry, the public-surface closed-set derivation, and the permission-matrix-row coherence rule (EB-A5 → wired at Story 11.1, when the matrix source exists; wiring it in 10.1 would self-fail). `nav-registry.ts` derives the route EXPECTATION only; icons/labels stay authored in `nav-items.ts`. Also NOT yet operative: `EXPECTED_NAV_ROUTES` has only a test-only consumer while the OPERATIVE nav guardrail still asserts the authored `nav-items.ts` (the "single source" claim is currently half-built for nav — a deliberate Epic-11.1 forward seam). FORWARD GOTCHA: `tenantTablesFromManifest` filters on `status` only, NOT `scope` — when E12 (`provisioning`) activates a `platform_operators` table it would leak into the manifest-derived H4 tenant union; the E12 activation story must add a `scope !== "platform"` filter (or a separate `platformTables` field) then.

## Architecture Rules

- Default tenant model is pooled multi-tenant, not one Supabase project per customer.
- Use dev, staging, and prod Supabase projects. Production contains many tenant companies.
- **Every tenant-owned business table must carry tenant scoping and be protected by RLS — RLS-by-default, no exceptions.** Phase A convention is a direct `tenant_id` column (the `tenants` root is the exception: its own `id` IS the tenant id). Enable AND `force` RLS on the table.
- **RLS narrows; GRANTs expose.** This stack does NOT auto-expose new `public` tables to Data API roles, and RLS only narrows an already-granted role. Every new tenant-owned table needs explicit GRANTs ALONGSIDE its policies: `authenticated -> SELECT` (+ whatever the app path needs), `service_role -> DML` (for tests/admin paths), `anon -> none`. - **Immutability enforcement is a DB TRIGGER that fails closed, not app-code alone (Epic 6/7/8.4 pattern, now proven THREE times).** A `BEFORE UPDATE`/`BEFORE INSERT OR UPDATE OR DELETE` trigger blocks mutation of an immutable-state row and EXEMPTS only an explicit tuple of derived/allowed columns; it is LOCKED-BY-DEFAULT (enumerate the exempt set, never the locked set). Immutability-trigger tests MUST cover state-machine REVERSAL (e.g. sent → draft) and identity/FK columns (id/tenant_id/parent_id/created_at), not just content columns — a review caught a sent-lock that wholesale-exempted `status` (allowing a sent→draft reversal that disarmed the lock) and left identity/FK columns in neither the exempt nor the locked tuple. **There are now THREE scopes of this ONE model, a shared lock-code FAMILY (related-but-distinct codes, ONE trigger shape — NOT a fork, NOT one reused code, R-822):** the Epic 6 sent-lock PAIR (`enforce_quote_version_sent_lock` + `enforce_quote_version_child_sent_lock`, keyed on `status='sent'`, with a `status`-transition early-return and PDF-column exemptions → `QV409`/`QUOTE_VERSION_LOCKED`), the Epic 7 accepted-lock PAIR (`enforce_quote_acceptance_lock` + `enforce_job_source_ref_lock` → `AR704`/`ACCEPTED_RECORD_LOCKED`), and the Epic 8.4 FILE-lock (`enforce_file_link_lock` on `file_links` + `enforce_file_lock` on `files`, keyed on `is_locked`/`lifecycle_state='locked'` → `FL823`/`FILE_LINK_LOCKED`, migration `20260712120000_file_link_lock.sql`). Key DIFFERENCES to preserve: an acceptance is ALWAYS immutable the moment it exists (no draft acceptance, no lifecycle status), so `enforce_quote_acceptance_lock` has NO status early-return (unlike the sent-lock) and locks every commitment column; the job lock (`enforce_job_source_ref_lock`) locks only the immutable source/identity tuple, leaving the 7.3 allowed-edit columns + the ON-DELETE-SET-NULL `facility_id`/`contact_id` unlocked. **The 8.4 file lock also needs an explicit lock-APPLY layer** — because the RPCs that CREATE the evidence/PDF links are FROZEN, the lock is applied BY CONSTRUCTION by (a) `apply_file_link_lock` (BEFORE INSERT OR UPDATE on `file_links`, parent-state-keyed: a `quote_version` PDF/attachment link whose parent `status <> 'draft'`, or a `quote_acceptance` evidence link whose parent acceptance EXISTS → set `is_locked`/`locked_at` + flip the file to `lifecycle_state='locked'`) AND (b) two PARENT-SIDE apply triggers (`apply_lock_on_quote_version_transition` AFTER UPDATE on the draft→non-draft flip, `apply_lock_on_acceptance_insert` AFTER INSERT) — because `mark_quote_version_sent`/the accept RPC flip the parent status WITHOUT re-writing `file_links`, so a link created while draft would never lock from the child side alone. The lock-apply idempotency guard keys skip-re-locking on `OLD.is_locked` (the UPDATE arm), NOT `NEW.is_locked`, so a disarm attempt reaches the enforce trigger (a naive `NEW.is_locked` guard would mask an `is_locked=false` disarm as a same-tuple no-op — a subtle epic-8.4 trap). The lock-apply trigger is name-ordered to fire BEFORE the enforce trigger (`file_links_a_apply_lock` sorts before `file_links_b_lock`). The 8.4 file lock EXEMPTS only `archived_at`/`updated_at` (link) and `archived_at` + the GUARDED `locked → archived`-only lifecycle transition + `updated_at` (file); a `locked → draft`/`linked` disarm or `locked → deleted` hard-delete RAISES. Reuse this trigger shape (and stay inside the shared lock-code family) for any future immutable-state enforcement; test the reversal and identity paths, and if the create path is frozen, add a parent-side apply trigger too.

## Money, Tax, And Quote Rules

- **SEK money is stored as INTEGER ÖRE (`bigint` in DB, a non-negative SAFE-integer `number` in TS); VAT rate is stored as BASIS POINTS** (2500 = 25.00%; default 2500, configurable, NEVER a code literal). This discipline is LIVE in code (work-role cost/sell hourly rates, article unit prices, `company_settings.vat_rate_bp`) AND is now the internal representation of the entire calculation engine. Two storage enforcement layers, both mandatory for any new money field:
  - **The öre-validity authority is `isOreAmount(v)` / `ORE_AMOUNT_MAX`, now CANONICAL in `@/lib/money` (`src/lib/money/ore.ts`)** and re-exported by `src/server/commands/pricing/validation.ts` — there is exactly ONE implementation, never a forked second rule. It accepts ONLY a non-negative SAFE integer number (0 .. `Number.MAX_SAFE_INTEGER`); REJECTS floats, negatives, NaN/±Infinity, overflow, locale-comma strings (`"850,00"`), decimal/numeric strings (`"850.00"`), and any string/null/object. The UI converts kronor->öre at the boundary; the command RE-VALIDATES the integer öre as the authority (the UI parse is a UX nicety only). Reuse `isOreAmount` for every new öre field. `isVatRateBp` / `VAT_RATE_BP_MIN`/`MAX` moved canonical to `@/lib/money` the same way (settings validator re-exports).
  - **DB CHECK** (`..._ore >= 0`) belt-and-braces the lower bound; a `23514` maps to `VALIDATION_FAILED`.
- **THE MONEY/VAT/ROT CALCULATION ENGINE IS `@/lib/money` (Epic 4, architecture §22) — a PURE `src/lib` library. Every calculation MUST route through it; never re-derive a total, VAT amount, net/gross, or deduction inline.** Epic 5's calc workspace is the FIRST real CONSUMER: `src/features/calculations/totals.ts` is the single editor-totals authority and DELEGATES every öre op to the engine (`lineNetOre`/`lineVatOre`/`sumOre`/`sumVatOre`/`vatBreakdown`/`selectVatDisplay`) — there is NO inline `+`/`*`/`0.25`/`Number(x)*rate` and NO forked rounding/VAT rule anywhere in `src/features/calculations`. Reuse `totals.ts` (or the engine directly) — never re-derive a calc total. Its non-negotiable disciplines:
  - **PURE / DETERMINISTIC / NO PII:** every function is a deterministic function of its inputs — NO I/O, NO DB, NO network, NO clock read (`Date.now()` never appears; a build instant is injected via `opts.capturedAt`, mirroring the snapshot builders). NO personnummer / orgnr / customer field ever enters the engine — it takes a resolved eligibility POSTURE, never PII. This is why it is exhaustively `node --test` unit-testable and golden-pinnable.
  - **INTEGER ÖRE END-TO-END (R-401):** every value crossing a function boundary is öre; the ONLY place öre becomes a kronor STRING is the single presentation-boundary formatter `formatOreAsKronor` (`oreToKronorString` delegates to it — one kronor formatter, no second). No float-kronor value ever survives off the presentation boundary.
  - **ROUNDING (R-402):** LINE-LEVEL, ROUND-HALF-AWAY-FROM-ZERO (`x.5 → x+1`, NOT banker's/half-to-even). Totals PRESERVE exact öre by SUMMING already-rounded lines (`sumOre` / `sumVatOre` = SUM-OF-ROUNDED, never round-of-sum). The mode is golden-pinned (`tests/fixtures/golden/money/rounding-mode.json`) so an accidental flip fails loud. **DOCUMENT-LEVEL rounding, or a discount / negative-amount data model, is a STOP CONDITION (report `needs-human`) — the engine must not invent it.**
  - **VAT is basis-points-only:** `lineVatOre`/`sumVatOre`/`vatBreakdown` derive VAT from the stored `vat_rate_bp` — never a hidden 25% literal. `selectVatDisplay` returns a presentation-only excl/incl/both VIEW (pure öre-selection, no second kronor formatter).
  - **The engine NEVER returns an approved/production-final result.** Errors cross as a typed `Result` discriminated on a `MoneyErrorCode` (`INVALID_ORE_AMOUNT`/`INVALID_QUANTITY`/`INVALID_VAT_RATE_BP`/`INVALID_DEDUCTION_RATE_BP`) — the primitives NEVER throw, NEVER echo the raw invalid value, NEVER return `NaN`/`Infinity`. (Note the two snapshot builders currently discriminate success via absence of an `ok` field rather than the `{ok:true|false}` shape the rest of the engine uses — a known cleanup, not a live bug.)
- **⚠ THE TAX ANSWERS ARRIVED 2026-07-26 — the engine is now KNOWN-WRONG in two places, not merely unapproved.** The accountant ratified the rules (`docs/discovery/phase-b-accountant-answers-2026-07-26.md`; recorded as `architecture-phase-b.md` **§12A** and PRD **NFR55**). **Most answers CONFIRMED the shipped placeholders** — 25 % VAT, ROT 30 %, ROT cap 50 000 SEK/person/year, grön teknik 15/50/50, grön cap 50 000. **Three did not, and two of those contradict shipped behaviour:**
  1. **VAT rounding scope (corrects code).** The engine rounds VAT **per line** and sums rounded line values (`ore.ts`, `vat.ts`, `totals.ts`). The ratified rule is: line NET rounds to öre, then the taxable basis is **summed per VAT category across the document** and VAT is computed and rounded **there** (Peppol/EN 16931 **BR-CO-17**). The accountant's stated reason is the test to write: the per-line model **yields different totals depending on how the same work is split into lines** — economically identical documents must produce identical VAT (*split invariance*).
  2. **Hidden-row deduction basis (corrects an assumption).** "Hidden rows always count in BOTH total and deduction basis" is **half wrong**. The TOTALS pin below is unaffected and still frozen. What changes is the **deduction basis**: a row enters it only if its **cost type** is eligible — **material is never ROT-eligible**; travel, vehicle, machine, and administration are **neither** ROT nor grön. A row therefore needs three INDEPENDENT properties: `VisibleToCustomer`, `IncludedInInvoiceTotal`, `DeductionClassification` (`NONE`, `ROT_LABOR`, `GREEN_SOLAR_LABOR`, `GREEN_SOLAR_MATERIAL`, `GREEN_STORAGE_*`, `GREEN_CHARGING_*`).
  3. **Reverse charge is a VAT TYPE, not a 0 % rate.** Construction-sector *omvänd betalningsskyldighet* becomes `VatType ∈ {STANDARD_VAT_25, REVERSE_CHARGE_CONSTRUCTION, …}`, requires an explicit choice or verified customer setting (being a company is NOT sufficient), and prints the buyer's VAT number plus the required text.
  Also new: Skatteverket **claim amounts truncate to whole SEK** (öre discarded — truncation, not rounding), the **ROT+RUT combined 75 000** ceiling sits alongside the 50 000 ROT cap, rates/caps carry **`ValidFrom`/`ValidTo`** rather than being constants, the grön **97 % schablon is opt-in** and only for a genuine fixed-price total contract, and the ROT tax year follows the customer's **payment** date rather than the invoice date.
  **STORY 10.6 OWNS THIS CHANGE — do not fix it opportunistically in an unrelated story, and do not "helpfully" adjust a golden fixture to match one of these rules in isolation.** Until 10.6 lands, the code is as described above; after it lands, this note's rules are the code. The **ADR-A005 boundary is absolute either way: an already-SENT quote version's frozen snapshot is IMMUTABLE — the corrected rules apply to NEW versions only, never by recomputing a sent snapshot.**
- **The engine is otherwise UNAPPROVED — its remaining VAT-display values are conservative golden-pinned PLACEHOLDERS pending owner sign-off, NOT accounting-final.** Standing sign-off questions carried to the owner working session (do NOT silently "finalize" any of them in code): rounding mode (Q1), VAT display for `company_togglable` default and private→always-incl (Q2), ROT rate/cap/**per-person multiplier**/basis (Q3), grön-teknik rates/caps/mix (Q4), eligibility disclaimer text, personnummer scope, approval posture, accepted-price delta shape (Q8). Named profiles (`ROT_PROFILE_UNAPPROVED`, `GRON_TEKNIK_PROFILE_UNAPPROVED`) carry the UNAPPROVED marker in their names and `estimateDeduction` returns `requiresSignOff: true` as the STRUCTURAL default — an estimate is never approvable without an explicit human sign-off. ROT and grön teknik CANNOT be mixed (a blocking typed failure). **`persons` is a KNOWN inert placeholder:** it is validated + frozen into the assumption snapshot + threaded through the golden fixtures, but the cap is a single FLAT `capOre` — `persons` does NOT scale it (a 3-person ROT job gets the same ceiling as a 1-person job). ## Read-Model Rules (Epic 10, Story 10.4 — the phase-defining `{ data, entitlements }` precedent)

`src/server/read-models/**` is a NEW module family (the quote-pipeline read-model is the first member). Its shape is the precedent EVERY later Phase B read-model inherits — get it exactly right (R-1040):

- **The descriptor shape is `{ data, entitlements: { withheld: FieldPath[] } }`.** A withheld (sensitive/money) field is ABSENT from `data` (DELETED — never `null`, never `0`) AND its stable `FieldPath` string is listed in `entitlements.withheld` — the "absent + listed" rule. UI convention (later): absent + listed ⇒ mask/omit column; absent + NOT listed ⇒ genuinely empty. **The UI NEVER consults role names client-side** — it reads the withheld listing.
- **FAIL-CLOSED entitlement resolution with field-ABSENCE withholding.** The single injectable `resolveMoneyEntitled(input?)` resolver: an explicit `moneyEntitled` wins; else a role set is entitled iff it contains `tenant_admin`; else (NO input at all — the least-known caller) the conservative default is UNENTITLED (money withheld). An OMITTED input resolves the SAME as an explicit empty role set, so the least-known caller is the MOST guarded. Entitled callers (the B1a all-`tenant_admin` reality → `withheld: []`) pass an EXPLICIT `EntitlementInput`; a read-model must NEVER rely on the omitted-input default to EXPOSE money. This is the seam Epic 11 (11.2) feeds the real N-4 permission matrix — do NOT build the matrix or enumerate roles in a read-model. **N-4 was ANSWERED 2026-07-26** and the seed now exists in `architecture-phase-b.md` §3.2A/§3.3A: five tenant roles (**Företagsadmin** as the admin LABEL, `tenant_admin` still the stored literal), **Arbetsledare as a per-JOB assignment rather than a tenant role**, **multi-role membership as a requirement** (`membership_roles` is built in E11, not reserved — permissions evaluate as the UNION over held roles, so a field is withheld only when NO held role is entitled), the owner-named permission keys (`Jobs.ViewAssigned`, `Economy.ViewCostPrice`, `Economy.ViewContributionMargin`, `InvoiceBasis.ExportToFortnox`, …) bound to stable business functions rather than page names, **deny-by-default**, and the money defaults: **Montör sees NO sales price, cost price, or contribution margin; Säljare sees sales prices but NOT cost or TB** unless `Economy.ViewContributionMargin` is granted separately. Read the matrix from there when 11.2 lands; do not re-derive it.

## Critical Implementation Rules

### Language-Specific Rules

- TypeScript `strict` is on. No implicit `any`; type everything. Prefer `readonly` and `as const` for fixed data (see `nav-items.ts`).
- Use the `@/*` alias for intra-`src` imports; avoid deep relative `../../..` chains.
- `isolatedModules` is on — use `import type` for type-only imports.
- **Errors cross boundaries as a typed `Result`, not thrown exceptions.** Server auth/commands return `Result<T, ErrorCode>` (`@/lib/result/result`, `ok`/`err`) over a stable code union (`TenantContextErrorCode`, `CommandErrorCode`). Map thrown I/O failures to a generic retryable `SERVER_ERROR` — fail closed, but do NOT conflate "infrastructure is down" with "you are not authorized" (a transient DB/RLS error must NOT present as a permanent no-access denial). Never leak internal detail, stack, SQL, or tenant/user-existence through an error message; user-facing messages are generic Swedish.
- When selecting among multiple candidate rows (e.g. memberships), choose EXPLICITLY in pure code (`active`-first, stable tiebreak) — never rely on lexicographic `.order()` over an enum, which silently mis-selects when a new enum value sorts before the intended one.

### Security Regression Harness Rules (standing contracts — Epic 2, enforced through Epic 9)

These are AUTOMATED, fail-closed gates that protect every later tenant-owned table and command. Treat their absence/weakening as a release blocker, not a story-level nicety.

- **Cross-tenant negative suite + H4 inventory gate are a single enrollment contract.** The tenant-table inventory `tests/integration/rls/tenant-table-inventory.ts` (`TENANT_TABLES` + per-table spoof/filter/mutation metadata, and the anon-path helpers) is the ONE place a tenant-owned table enrolls. The cross-tenant suite (`cross-tenant-isolation.rls.test.ts`), the anon-path suite (`anon-path-isolation.rls.test.ts`), AND the H4 gate (`rls-inventory-gate.int.test.ts`) all read it. **STANDING CONTRACT (Epics 3-9): any PR that adds or touches a tenant-owned table MUST enroll it in `TENANT_TABLES` (with metadata) BEFORE merge.** The H4 gate introspects the live schema (direct `tenant_id`, FK-to-`tenants` regardless of column name, partitioned parents, non-system schemas, plus the literal `tenants` root) and FAILS CI with a named "table not covered" message when a tenant-owned table is unenrolled — automated enforcement, not reviewer diligence.
- **The metadata model is compile-exhaustive on purpose.** Per-table helpers use `switch(table)` + `assertNever` so a future enrollee missing its metadata is a TYPECHECK error, not a silently mis-shaped (false-green) negative. Preserve this — broadening a fail-closed gate without an exhaustive type model creates false completeness.
- **Service-role containment is enforced at two layers, the bundle layer being authoritative.** Source guard `scripts/verify/check-service-role-containment.mjs` (`verify:service-role-containment`, in CI before build) flags `NEXT_PUBLIC_*SERVICE_ROLE*` names and `SUPABASE_SERVICE_ROLE_KEY` / the `LOCAL_SUPABASE_SERVICE_ROLE_KEY` re-export symbol referenced from a `"use client"` path. The AUTHORITATIVE built-bundle grep `scripts/verify/check-bundle-containment.mjs` (`verify:bundle-containment`, in CI AFTER `pnpm build` — order is load-bearing) scans the produced `.next` payload for any `*SERVICE_ROLE*` token, the JWT-shaped `"role":"service_role"` value, and `NEXT_PUBLIC_*SERVICE_ROLE*` names, and FAILS LOUD if `.next` is absent (never false-greens). This app uses NO service-role key (anon + RLS); a clean build yields zero hits.
- **`audit_events` is append-only and own-tenant-read.** A `BEFORE UPDATE OR DELETE` trigger blocks mutation; SELECT is own-tenant only. Note the trigger also blocks tenant on-delete-cascade of audit rows — privileged test cleanup must delete audit rows before the tenant. Audit metadata is allow-listed + sanitized; never persist raw input.
- **`quote_events` (Epic 6) is append-ONLY-mutation but NOT append-only-INSERT.** A `quote_events_append_only` `BEFORE UPDATE OR DELETE` trigger blocks mutation, but the retained own-tenant INSERT policy + `authenticated` grant let an own-tenant admin insert a forged `sent`/`accepted` timeline event directly (arbitrary `occurred_at`/`channel`/`reference`) below the SECURITY INVOKER RPCs — a KNOWN own-tenant event-log/timeline integrity seam (LOW; no authorization bypass, because the app derives draft/read-only authz from `quote_versions.status`, never from events). Do NOT trust the `quote_events` timeline as tamper-proof; the authoritative lifecycle state is `quote_versions.status`. A future quote-events hardening pass may drop the direct INSERT grant so only the RPCs write it. **Epic 7's `job_events` timeline follows the IDENTICAL pattern** (append-only-mutation trigger, retained own-tenant INSERT grant) — the authoritative job lifecycle state is `jobs.status`, never the `job_events` timeline; do NOT trust it as tamper-proof.
- **File audit goes through the COMMAND envelope's `writeAuditEvent`, NOT a DB trigger — there is deliberately NO `file_events` table.** A DB trigger has no envelope context (no resolved actor/membership), so the 8.4 lock/archive/blocked-delete audit lands through the standard command envelope (`{ targetId }`-only metadata, sanitized). Do not add a `file_events` table or a DB audit trigger for file operations; reuse the envelope's audit path. The 8.4 lock TRIGGERS themselves add NO function grant (they run only as row triggers), NO new policy, and NO storage-plane trigger — a locked file's BYTES are still not reclaimed by the app path (archive-over-delete).

### Critical Don't-Miss Rules

- **Service-role key is SERVER-ONLY.** It bypasses RLS. Never prefix it `NEXT_PUBLIC_`, never import it (or any re-export symbol like `LOCAL_SUPABASE_SERVICE_ROLE_KEY`) into a browser/client path. Any server-side use must be documented (file + purpose) and test-covered. This app currently uses NO service-role key on app paths (anon + RLS); the source + built-bundle containment guards enforce it in CI.
- **RLS-by-default + GRANTs:** a new tenant-owned table is not done until it has (a) `tenant_id` scoping (or is the `tenants` root), (b) enable+`force` RLS with own-tenant policies built on the DEFINER helpers, (c) explicit role GRANTs (`anon -> none`), and (d) enrollment in `TENANT_TABLES`. Missing any one is a tenant-isolation or availability defect.
- **Secrets never get committed.** `.env` and `.env.*` are gitignored; ONLY `.env.example` is whitelisted, and it holds PLACEHOLDERS ONLY — never real project refs, keys, URLs, or PII. Only `NEXT_PUBLIC_`-prefixed vars are exposed to the browser. Do not echo `.env*` contents into prompts.
- **Do not copy from the Lovable app by default** (see Lovable Oracle Policy) — it is a behavioral oracle, not a code source.
- **Stay in Phase A scope.** Do not create migrations, add dependencies, edit `.env`, or modify app code for process-only tasks. If a change touches a deferred module, stop unless there is explicit re-approval in the PR description and a linked planning artifact.
- **CI `pnpm build` is non-hermetic** (the Next scaffold fetches a Google font over the network). Acceptable on networked GitHub runners; revisit (switch to `next/font/local`) only when CI must run network-restricted.
