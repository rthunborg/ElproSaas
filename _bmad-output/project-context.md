# Project Context For BMAD Agents

_Critical rules and patterns AI agents must follow when planning, implementing, or reviewing code in this project. Focuses on unobvious details agents might otherwise miss. Read this before writing any code; when in doubt prefer the more restrictive option._

The durable governance rules (Product Boundary, Architecture, Money/Tax/Quote, Lovable Oracle) are evergreen and phase-scoped. The implementation sections (Technology Stack onward) reflect the conventions established through **Epic 5 close** (the tenant-owned calculation workspace + quote-readiness surface), which builds on the Epic 4 pure money/VAT/ROT engine, the Epic 3 CRM/settings/pricing foundation, and the Epic 2 multi-tenant foundation:

- **Epic 2 (foundation, in code):** tenant-admin login + server-side tenant-context resolution, the `tenants`/`tenant_memberships` schema with SECURITY DEFINER RLS helpers and two-tenant fixtures, the reusable server command envelope + append-only `audit_events`, and the security regression harness (cross-tenant RLS negatives, the H4 table-inventory gate, and source + built-bundle service-role containment checks).
- **Epic 3 (foundation, in code):** the FIRST tenant-owned BUSINESS tables — CRM (`customers`/`facilities`/`contacts`), company settings (`company_settings`/`quote_terms`), and pricing (`work_roles`/`articles`) — plus the first money STORAGE (integer öre / basis points), the first structural sign-off gate (quote-terms `approved_at`), and the small **snapshot-source contract** (`src/lib/snapshots`) that Epic 5/6 freeze. A real browser E2E runner (Playwright) is CI-gated.
- **Epic 4 (foundation, in code):** the pure money/VAT/ROT **CALCULATION ENGINE** — `@/lib/money` (`ore.ts` + `vat.ts` + `tax.ts` + `index.ts` barrel): integer-öre arithmetic + line-level rounding, per-line VAT from basis points + the excl/incl/both display views, and the ROT / grön-teknik ESTIMATE engine (named UNAPPROVED profiles, `estimateDeduction`, `requiresSignOff` default, ROT×grön mix-block, flat cap-clamp). Plus the frozen tax/VAT-assumption snapshot builders and the money-and-tax **golden-master fixture pack** (`tests/fixtures/golden/money/**`). Added NO dependency, NO migration, NO table, NO nav item — a pure `src/lib` + tests library. The engine is UNAPPROVED (conservative golden-pinned PLACEHOLDERS pending owner/accounting sign-off — see Money/Tax rules).
- **Epic 5 (this epic, in code):** the FIRST tenant-owned CALCULATION WORKSPACE that CONSUMES the Epic 4 engine — three new tenant-owned tables `calculations` / `calculation_sections` / `calculation_rows` (migration `20260702120000_calculation_data_model.sql`), each direct-`tenant_id`, soft-archived (`archived_at`), with COMPOSITE same-tenant parent FKs and two SECURITY INVOKER reorder RPCs (`reorder_calculation_rows`/`reorder_calculation_sections`) owning the atomic multi-row ordering transaction. The tenant-owned table set grew from ten to **THIRTEEN** (all enrolled in the H4 gate + the exact-policy enumeration). Server commands (`src/server/commands/calculations/**`) build on the same envelope; a Kalkyl EDITOR UI (`src/components/calculations/**`) lives UNDER the existing `/calculations` nav (still exactly SEVEN nav items). The calc-domain LOGIC is extracted into PURE `src/features/calculations/*.ts` modules protected by the fast unit gate — totals (`totals.ts`, delegates every öre op to `@/lib/money`, no forked arithmetic), VAT-posture resolution (`vat-posture.ts`), the readiness classifier (`readiness.ts`, a blocker-vs-warning rule table), pricing-source snapshotting (`20260703120000_calculation_row_pricing_source.sql` adds frozen copy-by-value `source_*` columns; `source-options.ts`/`source-select.ts`), and a calc GOLDEN pack (`tests/unit/features/calculations/calc-golden-pack*.test.ts`) that REFERENCES the Epic 4 money fixtures. **Epic 5 added NO deferred module, NO supplier/sync scope, and NO new dependency.** The calc surface stays UNAPPROVED for production — VAT display, the low-margin threshold, and ROT/grön assumptions inherit the Epic 4 owner sign-off questions.

## Product Boundary

BMAD agents must plan and review only the Phase A Internal Pilot MVP unless the user explicitly approves a later-phase epic. Phase A is a small internal rebuild for the current company, not the full commercial SaaS.

In Phase A:

- Implement admin-only `tenant_admin` access.
- Preserve pooled multi-tenant architecture from day one.
- Build only the workflow CRM/settings/pricing -> calculations -> quote versions/PDF/acceptance -> basic job/order creation -> required files.
- Include migration/coexistence planning and golden-master comparisons against the current Lovable app.

Do not plan implementation for Fortnox, field-worker UX, supplier APIs, AI jobs, HR, rentals, assets, DoU automation, tender/FKU RAG, or full RBAC unless the user explicitly promotes that scope.

## Architecture Rules

- Default tenant model is pooled multi-tenant, not one Supabase project per customer.
- Use dev, staging, and prod Supabase projects. Production contains many tenant companies.
- **Every tenant-owned business table must carry tenant scoping and be protected by RLS — RLS-by-default, no exceptions.** Phase A convention is a direct `tenant_id` column (the `tenants` root is the exception: its own `id` IS the tenant id). Enable AND `force` RLS on the table.
- **RLS narrows; GRANTs expose.** This stack does NOT auto-expose new `public` tables to Data API roles, and RLS only narrows an already-granted role. Every new tenant-owned table needs explicit GRANTs ALONGSIDE its policies: `authenticated -> SELECT` (+ whatever the app path needs), `service_role -> DML` (for tests/admin paths), `anon -> none`. Treat a per-table GRANT+RLS pair as a single checklist item — a missing GRANT surfaces as a `42501 permission denied` app-path failure (a stronger denial than RLS zero-rows), and a missing RLS policy is a tenant-isolation leak.
- **Authorization is computed via SECURITY DEFINER RLS-helper predicates** (`public.is_active_tenant_member(tenant_id)`, `public.is_tenant_admin(tenant_id)`). They are DEFINER on purpose (an INVOKER helper reading the RLS-protected membership table inside that table's own policy infinite-recurses, Postgres `42P17`). Every DEFINER function MUST pin `set search_path = ''` (empty) and schema-qualify EVERY reference (`public.x`, `auth.uid()`), be marked `STABLE`, and be revoked from `PUBLIC` — an unpinned search_path is a function-hijack / privilege-bypass vector. This is proven by a standing negative test; reuse this exact shape for any future DEFINER function.
- Phase A schema should contain only the v0 tables required by the baseline plan. Current tenant-owned set (Epic 5 close) is EXACTLY these **thirteen** tables — all direct-`tenant_id`, all enrolled in `TENANT_TABLES`: `{tenants, tenant_memberships, audit_events, customers, facilities, contacts, company_settings, quote_terms, work_roles, articles, calculations, calculation_sections, calculation_rows}`. `company_settings`/`quote_terms` are **one-row-per-tenant** (`unique (tenant_id)`, settings-singleton shape); the rest are **many-per-tenant collections** (no `unique (tenant_id)`). Growing this set means enrolling the new table in the H4 gate AND extending the exact-policy enumeration (see below).
- **A composite same-tenant FK requires the parent to carry `unique (id, tenant_id)`.** Epic 5 proved the trap: a child (`calculation_sections`/`calculation_rows`, and `calculations.contact_id`) references its parent on BOTH `(id, tenant_id)` so a child can only point at a same-tenant parent (a bare `references parent(id)` would let it point across tenants). This needs `unique (id, tenant_id)` on the referenced parent — `customers`/`facilities` got it in Story 3.1, but `contacts` did NOT (it was never a composite parent before), so the 5.1 migration ADDITIVELY added `contacts_id_tenant_unique` (a frozen prior migration is NEVER edited — add the missing unique in the new migration). Any future story adding such a same-tenant FK must additively add the parent's `(id, tenant_id)` unique first.
- **Atomic multi-row writes use a narrow SECURITY INVOKER Postgres RPC, NOT client-side multi-step persistence (ADR-A009).** The calc reorder RPCs (`reorder_calculation_rows`/`reorder_calculation_sections`) own the transaction boundary + full rollback for a multi-row ordering write; they are SECURITY INVOKER (execute under the CALLER's RLS — no service-role app path, no membership recheck needed) with a fixed empty `search_path` + schema-qualified refs (mirroring the DEFINER-fn hardening). Prefer INVOKER for any future atomic multi-row write; a DEFINER RPC would need separate approval + a membership check + dedicated negative tests. (Known robustness gap, deferred: the reorder RPCs do not filter `archived_at is null` and accept a partial/empty payload directly — the command layer's non-empty `isUuidArray` check is the only app-path guard; harden at the DB layer on a future pass.)
- **Every new tenant-owned table is an H4 RLS-inventory enrollment obligation — non-negotiable.** Enroll it in `TENANT_TABLES` (`tests/integration/rls/tenant-table-inventory.ts`) with BOTH metadata seams — cross-tenant (`spoofedRowFor`/`tenantBFilter`/`hijackMutationFor`) AND anon-path (`anonRowFor`/`anonFilterFor`/`anonMutationFor`) — before merge, or the H4 gate FAILS CI with a "table not covered" message. The per-table `switch(table)` + `assertNever` exhaustiveness backstop turns a half-enrolled table into a TYPECHECK error, not a silent false-green — preserve it. **Anon isolation asserts anon-DML-empty (SELECT/INSERT/UPDATE/DELETE), NOT anon-grant-empty:** Supabase default privileges grant every role (incl. anon) non-DML REFERENCES/TRIGGER/TRUNCATE on new public tables, so an "anon has zero grants" assertion is factually wrong — scope anon-isolation to the four DML verbs.
- **The migration-reset exact-policy enumeration is EXTENDED, never loosened.** `tests/integration/rls/migration-reset.int.test.ts` asserts the EXACT per-table public policy set (own-tenant SELECT + the writes each table needs; CRM/settings/pricing carry SELECT+INSERT+UPDATE and NO DELETE — archive is a soft `is_active`/`archived_at` flip, never a hard delete). A new table's policies MUST be added to this exact enumeration; a stray policy fails loud. Do NOT relax it to a superset match.
- Do not create placeholder production tables for deferred modules.
- No service-role key may be reachable from browser/client paths. No unauthenticated privileged functions are allowed.
- **Use the server command envelope for EVERY sensitive mutation — this is now the proven, uniform pattern (Epic 3 built ~10 commands on it).** The reusable envelope (`src/server/commands/envelope.ts`, `defineCommand`/`runCommand`) runs the architecture-§5 gates (resolve user from cookies -> resolve active membership -> validate typed input -> verify tenant ownership of targets -> execute on the RLS client -> append-only audit) and returns a stable typed `Result`. No raw throw, stack, SQL, or tenant/user-existence signal crosses the boundary. New commands REUSE this — they never invent a new auth/error/audit mechanism. The established envelope shape, followed by every CRM/settings/pricing command:
  - **Resolved-tenant authority:** the row's `tenant_id` is ALWAYS `ctx.tenantContext.tenantId` (from membership); a client-supplied `tenant_id` is NEVER read (the validators strip/ignore it). The mutation runs on the request-bound RLS client (`ctx.db` via `asCrmWriteClient`), never service-role.
  - **Ownership-verify for UPDATE/archive/reactivate:** `ownership: (input) => input.id ? { table, id: input.id } : null`. A foreign/absent id -> zero rows visible under RLS -> `TENANT_ACCESS_DENIED`. A CREATE (no id) skips the pre-check; the INSERT WITH CHECK (`is_tenant_admin(tenant_id)`) keeps the new row in-tenant. A zero-row write after a passed ownership check maps to `TENANT_ACCESS_DENIED` (a mid-flight race), not a 500.
  - **Audit metadata allow-list is `{ targetId }` ONLY** — never a name, rate, price, personnummer, terms text, or any other PII/business value. `sanitizeAuditMetadata` drops anything else by construction; the allow-list is `{ targetId }` so the drop is belt-and-braces. Bind AND render every server-action's error state (a failed lifecycle action must paint its banner; do not destructure `useActionState` to nothing).
  - **Collection commands soft-archive, and archive MUST be reversible.** Lifecycle is an `is_active`/`archived_at` flip, never a hard DELETE. If an AC lists "reactivate", ship BOTH the reactivate command (inverse UPDATE flipping `is_active` back to true) AND the UI to surface archived rows (an "include archived" view lifting the `is_active=true` read filter) — a review-caught epic-3 trap was an archive that was a one-way, invisible door.
  - **On an upsert, omit-absent optional fields rather than force-NULL them** (a company-settings save once wiped `logo_url` to NULL because an absent input was forced `?? null`); build the UPDATE patch from only supplied fields.
- **Critical commands must be auditable, tenant-scoped, validated, and tested.** Audit rows are written via the append-only `writeAuditEvent` DEFINER-RPC path (`record_audit_event`) into `audit_events`; metadata is allow-listed and run through the sanitizer (`sanitizeAuditMetadata`) — never persist raw caller input or secrets. The `audit_events` table is append-only (a trigger blocks UPDATE/DELETE) and own-tenant-SELECT only.

## Money, Tax, And Quote Rules

- **SEK money is stored as INTEGER ÖRE (`bigint` in DB, a non-negative SAFE-integer `number` in TS); VAT rate is stored as BASIS POINTS** (2500 = 25.00%; default 2500, configurable, NEVER a code literal). This discipline is LIVE in code (work-role cost/sell hourly rates, article unit prices, `company_settings.vat_rate_bp`) AND is now the internal representation of the entire calculation engine. Two storage enforcement layers, both mandatory for any new money field:
  - **The öre-validity authority is `isOreAmount(v)` / `ORE_AMOUNT_MAX`, now CANONICAL in `@/lib/money` (`src/lib/money/ore.ts`)** and re-exported by `src/server/commands/pricing/validation.ts` — there is exactly ONE implementation, never a forked second rule. It accepts ONLY a non-negative SAFE integer number (0 .. `Number.MAX_SAFE_INTEGER`); REJECTS floats, negatives, NaN/±Infinity, overflow, locale-comma strings (`"850,00"`), decimal/numeric strings (`"850.00"`), and any string/null/object. The UI converts kronor->öre at the boundary; the command RE-VALIDATES the integer öre as the authority (the UI parse is a UX nicety only). Reuse `isOreAmount` for every new öre field. `isVatRateBp` / `VAT_RATE_BP_MIN`/`MAX` moved canonical to `@/lib/money` the same way (settings validator re-exports).
  - **DB CHECK** (`..._ore >= 0`) belt-and-braces the lower bound; a `23514` maps to `VALIDATION_FAILED`.
- **THE MONEY/VAT/ROT CALCULATION ENGINE IS `@/lib/money` (Epic 4, architecture §22) — a PURE `src/lib` library. Every calculation MUST route through it; never re-derive a total, VAT amount, net/gross, or deduction inline.** Epic 5's calc workspace is the FIRST real CONSUMER: `src/features/calculations/totals.ts` is the single editor-totals authority and DELEGATES every öre op to the engine (`lineNetOre`/`lineVatOre`/`sumOre`/`sumVatOre`/`vatBreakdown`/`selectVatDisplay`) — there is NO inline `+`/`*`/`0.25`/`Number(x)*rate` and NO forked rounding/VAT rule anywhere in `src/features/calculations`. Reuse `totals.ts` (or the engine directly) — never re-derive a calc total. Its non-negotiable disciplines:
  - **PURE / DETERMINISTIC / NO PII:** every function is a deterministic function of its inputs — NO I/O, NO DB, NO network, NO clock read (`Date.now()` never appears; a build instant is injected via `opts.capturedAt`, mirroring the snapshot builders). NO personnummer / orgnr / customer field ever enters the engine — it takes a resolved eligibility POSTURE, never PII. This is why it is exhaustively `node --test` unit-testable and golden-pinnable.
  - **INTEGER ÖRE END-TO-END (R-401):** every value crossing a function boundary is öre; the ONLY place öre becomes a kronor STRING is the single presentation-boundary formatter `formatOreAsKronor` (`oreToKronorString` delegates to it — one kronor formatter, no second). No float-kronor value ever survives off the presentation boundary.
  - **ROUNDING (R-402):** LINE-LEVEL, ROUND-HALF-AWAY-FROM-ZERO (`x.5 → x+1`, NOT banker's/half-to-even). Totals PRESERVE exact öre by SUMMING already-rounded lines (`sumOre` / `sumVatOre` = SUM-OF-ROUNDED, never round-of-sum). The mode is golden-pinned (`tests/fixtures/golden/money/rounding-mode.json`) so an accidental flip fails loud. **DOCUMENT-LEVEL rounding, or a discount / negative-amount data model, is a STOP CONDITION (report `needs-human`) — the engine must not invent it.**
  - **VAT is basis-points-only:** `lineVatOre`/`sumVatOre`/`vatBreakdown` derive VAT from the stored `vat_rate_bp` — never a hidden 25% literal. `selectVatDisplay` returns a presentation-only excl/incl/both VIEW (pure öre-selection, no second kronor formatter).
  - **The engine NEVER returns an approved/production-final result.** Errors cross as a typed `Result` discriminated on a `MoneyErrorCode` (`INVALID_ORE_AMOUNT`/`INVALID_QUANTITY`/`INVALID_VAT_RATE_BP`/`INVALID_DEDUCTION_RATE_BP`) — the primitives NEVER throw, NEVER echo the raw invalid value, NEVER return `NaN`/`Infinity`. (Note the two snapshot builders currently discriminate success via absence of an `ok` field rather than the `{ok:true|false}` shape the rest of the engine uses — a known cleanup, not a live bug.)
- **The engine is UNAPPROVED — its ROT/grön-teknik and VAT-display values are conservative golden-pinned PLACEHOLDERS pending owner/accounting sign-off, NOT accounting-final.** Standing sign-off questions carried to the owner working session (do NOT silently "finalize" any of them in code): rounding mode (Q1), VAT display for `company_togglable` default and private→always-incl (Q2), ROT rate/cap/**per-person multiplier**/basis (Q3), grön-teknik rates/caps/mix (Q4), eligibility disclaimer text, personnummer scope, approval posture, accepted-price delta shape (Q8). Named profiles (`ROT_PROFILE_UNAPPROVED`, `GRON_TEKNIK_PROFILE_UNAPPROVED`) carry the UNAPPROVED marker in their names and `estimateDeduction` returns `requiresSignOff: true` as the STRUCTURAL default — an estimate is never approvable without an explicit human sign-off. ROT and grön teknik CANNOT be mixed (a blocking typed failure). **`persons` is a KNOWN inert placeholder:** it is validated + frozen into the assumption snapshot + threaded through the golden fixtures, but the cap is a single FLAT `capOre` — `persons` does NOT scale it (a 3-person ROT job gets the same ceiling as a 1-person job). Do not mistake it for an implemented per-person cap; implementing the multiplier is owner-gated under Sign-Off Q3.
- **Calc-workspace money rules (Epic 5, all pure + fast-gate-protected — extract calc logic OUT of `"use client"` islands into `src/features/calculations/*.ts`, never inline):**
  - **Totals INCLUSION is a FROZEN owner pin (2026-06-18), applied by `totals.ts#rowCountsTowardTotal` — do NOT re-decide it.** A SELECTED option (`is_selected === true`) and a HIDDEN row (`is_hidden === true`) COUNT toward basis/net/VAT; an UNSELECTED option (`is_optional === true && is_selected !== true`) does NOT; a row that is neither optional nor selected always counts. A DIFFERENT inclusion rule is a STOP CONDITION (needs-human), not a local invention. (`calculation_sections.display_mode` detailed/summary/text_only and the row `is_hidden`/`is_optional`/`is_selected` flags are PERSISTED by 5.1; the inclusion logic lives in `totals.ts`.)
  - **VAT-display POSTURE is resolved by the single pure helper `resolveVatDisplayPosture(customerType, tenantDefaultVatDisplay)` (`vat-posture.ts`) — no fork.** A `private` customer → the `"private"` incl-VAT INVARIANT regardless of the tenant setting; a NON-private customer (`company`/`brf`/`public`, or unknown → treated conservatively as non-private) → the tenant's `default_vat_display` (`company_togglable`/`company_excl`) AS-IS. The editor reads `readCompanySettings()` in its parallel page load and feeds `default_vat_display` in; a settings-read fault degrades to the conservative `company_togglable` default + a "VAT posture unresolved" readiness WARNING (never a hard failure). Do NOT re-hard-code `company_togglable` for all non-private customers (the fixed 5.2 trap).
  - **A null `unit_cost_ore` means "cost unknown → no computable margin" (returns null), NEVER a silent zero-cost / 100%-margin.** This is a load-bearing fail-CLOSED fix from the epic-5 review — future margin/TB% logic must not reintroduce the fail-open (a missing cost defaulting to 0 would fabricate a 100% margin on a row with unknown cost).
  - **A pricing-source `row_type ↔ source_kind` cross-check exists but the update path has a known narrow gap:** `validateSourcePair` deliberately SKIPS the cross-check when `row_type` is absent on an update (a source-only edit), leaving the DB composite-FK/CHECK as the only backstop for that path. Do not assume the command layer re-validates `row_type↔source_kind` on every update; a stateful execute-layer re-check (load the persisted `row_type` before the cross-check) is the intended future hardening.
  - **READINESS is a rule table, not prose (`readiness.ts`, R-509).** A PURE classifier splitting BLOCKERS (hard, GATE quote creation) from WARNINGS (soft, do not gate). BLOCKERS today are exactly `MISSING_CUSTOMER` + `TOTAL_UNCOMPUTABLE` (an engine `{ok:false}`); everything else (low margin, missing facility/contact, empty section, hidden-rows-count disclosure, tax sign-off, required-files-deferred, VAT-posture-unresolved) is a WARNING — fail-open on classification is the conservative pilot default; a different split treated as production-approved is a STOP. It computes TB% as a pure ratio of already-öre values and delegates all öre arithmetic to `totals.ts`. The low-margin threshold is a documented UNAPPROVED constant (`PILOT_LOW_MARGIN_THRESHOLD = 0.15`) — the owner-decided "TB% vs a global threshold in settings" needs a gated `company_settings.margin_threshold_bp` migration + editor (deferred). Required-file readiness is a `REQUIRED_FILES_DEFERRED` placeholder WARNING pending Story 8.1; the calc feeds `hasDeductionAssumption: false` today (no calc field carries a ROT/grön assumption until Epic 6) — both are surfaced, never silently omitted.
- **Epic 5 extends the snapshot-source contract to the pricing-SOURCE row columns (Story 5.3).** `calculation_rows` carries FROZEN copy-by-value `source_*` columns (`source_kind` ∈ `work_role`/`article`, `source_id`, `source_name`, `source_price_ore`, `source_cost_ore`, source `updated_at`) built by the Story 3.5 `buildWorkRoleSnapshot`/`buildArticleSnapshot` pure builders — a COPY-BY-VALUE, NOT an FK (a later archive/rate-change of the source MUST NOT alter a prior row's snapshot; there is DELIBERATELY no FK from `source_id`). The client `<select>` value `"<kind>:<id>"` sends only the id+kind; the SERVER re-resolves + freezes name/rate (`source-select.ts`/`source-options.ts`, pure + unit-pinned). Money columns are `_ore`-suffixed `bigint` (guard-covered). No supplier/sync/credential/api/fortnox column — a frozen migration-reset guard scans every calc-table column and fails loud. (Known DB-backstop gap, deferred: no both-or-neither / kind↔columns DB CHECK and no `source_id` index — the command path is the only production writer; harden additively later.)
- **The `src/lib/money` enums are hand-forked copies of the server-side source enums to avoid a `src/lib` → `src/server` layer inversion (`VatDisplayMode`, the eligibility-posture union, `DeductionType` mirror `CustomerType` / settings `default_vat_display`).** The fork is the sanctioned choice; NO parity/drift test ties them together yet, so if you add a fifth customer type or a third VAT-display mode to the SERVER enum you MUST hand-update the `src/lib/money` mirror in lockstep — a silent drift would mis-classify eligibility (a money-correctness risk). The `default_vat_display` enum (`company_togglable`/`company_excl`) itself is captured/stored AS-IS by the settings layer; the engine applies the display posture.
- **The snapshot-source contract (`src/lib/snapshots`) is the Phase-A immutability primitive — a PURE builder over the existing settings/pricing rows, NO new table/migration/engine.** Its rules:
  - **Copy-by-value + `Object.freeze` immutability (R-008):** each builder copies every captured field (flat primitives) out of the source row into a fresh frozen `SnapshotSource`; the result holds no live reference to the input row, so mutating/archiving the source afterward can NEVER reach a prior snapshot. A snapshot never silently recalculates.
  - **Pure + deterministic:** no I/O, no DB, no clock read — the build instant is injected via `opts.capturedAt` (never `Date.now()` inside the builder), so builders are golden-pinnable.
  - **Captures STATE, computes nothing:** integer öre stays verbatim öre; `vat_rate_bp` stays basis points; the terms sign-off is captured as `approved_at`/`approved_by` VERBATIM (NULL = not-approved) — the contract NEVER derives an `isApproved` flag and NEVER approves/mutates the source. `updated_at` is the source "version" (no explicit version column). A `buildSnapshotSource` dispatcher uses `switch(kind)` + `assertNever` (a new kind is a compile error).
  - **Cross-tenant source-id rejected at BOTH layers:** the RLS-client resolver (`src/server/snapshots/resolve-source.ts`, anon key, own-tenant SELECT, no client tenant_id) -> `TENANT_ACCESS_DENIED`, AND RLS itself. `CompanySettingsSnapshot` is intentionally identity-PARTIAL (companyName + VAT only); full PDF identity (`org_nr`/address/etc.) is Epic 6's concern — do not treat it as the complete `company_settings` interface.
  - **Epic 4 extends this same contract to the CALCULATION assumptions:** `buildVatAssumptionSnapshot` and `buildTaxAssumptionSnapshot` (in `@/lib/money`) freeze the VAT / ROT-grön-teknik assumptions with the identical copy-by-value + `Object.freeze` + injected-`capturedAt` + captures-state-computes-nothing discipline (the deduction RATE is captured as basis points; no percent literal). Reuse this exact shape for any future assumption freeze.
- **Quote-terms sign-off is encoded STRUCTURALLY, not by a status string** (`quote_terms`, one-row-per-tenant): a nullable `approved_at` (default NULL = not-approved); the ONLY approve path is a deliberate human-only `approveQuoteTerms` command (no `status='approved'` default exists); any edit via `updateQuoteTerms` RESETS `approved_at` to null (an edit invalidates a prior sign-off). A future Epic 6 "send" path must check `approvedAt !== null` before sending; that enforcement is Epic 6's obligation.
- Snapshot (when the quote-version freeze lands, Epic 6): VAT rate, VAT amount, tax assumptions, work-role prices, article prices, and customer-visible quote content.
- A sent quote version is immutable. An accepted quote version and acceptance evidence are immutable except for explicit admin correction workflows. Changes to customer-visible price, terms, tax, attachments, or content after send require a new quote version.
- ROT and grön teknik assumptions require owner/accounting sign-off before production use.
- **Personnummer is stored access-controlled for `private` customers only** (owner decision 2026-06-18, which SUPERSEDES the old "no personnummer" plan text — the stale test-design R-009 wording is a known doc-only divergence, not a code defect). A single nullable `customers.personnummer` column, tied by the `customers_identifier_by_type` DB CHECK to `private` customers (private ⇒ personnummer present + org_nr absent; non-private ⇒ the inverse). ## Critical Implementation Rules

### Language-Specific Rules

- TypeScript `strict` is on. No implicit `any`; type everything. Prefer `readonly` and `as const` for fixed data (see `nav-items.ts`).
- Use the `@/*` alias for intra-`src` imports; avoid deep relative `../../..` chains.
- `isolatedModules` is on — use `import type` for type-only imports.
- **Errors cross boundaries as a typed `Result`, not thrown exceptions.** Server auth/commands return `Result<T, ErrorCode>` (`@/lib/result/result`, `ok`/`err`) over a stable code union (`TenantContextErrorCode`, `CommandErrorCode`). Map thrown I/O failures to a generic retryable `SERVER_ERROR` — fail closed, but do NOT conflate "infrastructure is down" with "you are not authorized" (a transient DB/RLS error must NOT present as a permanent no-access denial). Never leak internal detail, stack, SQL, or tenant/user-existence through an error message; user-facing messages are generic Swedish.
- When selecting among multiple candidate rows (e.g. memberships), choose EXPLICITLY in pure code (`active`-first, stable tiebreak) — never rely on lexicographic `.order()` over an enum, which silently mis-selects when a new enum value sorts before the intended one.
- Node helper scripts live in `scripts/**` as ESM `.mjs` (included in `tsconfig`); keep them dependency-free where possible (the verify guards run on bare Node, no test runner).
- **Multi-step npm scripts use a bare-Node orchestrator (`scripts/run-tests.mjs`), NOT chained `pnpm run X && pnpm run Y`.** Chained-pnpm package.json scripts fail on Windows (the script shell can't resolve pnpm on PATH). Reuse the orchestrator pattern for any future multi-step script.

### Framework-Specific Rules

- App Router only, under `src/app/`. Route groups organize the app: the authenticated shell lives in `src/app/(app)/` with its own `layout.tsx`, which is now a SERVER layout that resolves tenant context server-side (the auth boundary) and passes plain props into the client `AppShell` nav island.
- **Protected `(app)` routes that read per-request auth/cookies MUST set `export const dynamic = "force-dynamic"`.** Adding a server auth boundary silently converts previously-static pages to needing per-request env/cookies, and ONLY the `build` gate (not typecheck/lint/test) catches a missing `force-dynamic`. Set it on every protected route.
- **Auth/authorization is decided server-side from the re-validated JWT.** Resolve the caller via the cookie-bound server client's `getClaims()`/`getUser()` (which re-validate the JWT), NEVER from `getSession()`. The `(app)` server layout enforces: `UNAUTHENTICATED -> redirect("/login")`; no active membership -> render the no-access screen. Tenant context (`resolveTenantContext`) is the single authority; values shown in the UI (tenant name, user email) are presentational only.
- Create the `@supabase/ssr` server client FRESH per request via Next's async `cookies()` (Next 16: `cookies()` returns a Promise — await it). Never share a server client across requests. Use the v0.6+ `getAll`/`setAll` cookie API. Anon key only on any client/SSR path.
- **Navigation is data-driven from a single source of truth:** `src/components/app-shell/nav-items.ts`. It contains EXACTLY the seven IN-scope Phase A modules (Dashboard, Kunder, Kalkyler, Offerter, Jobb/Order, Filer, Inställningar) in that order — no deferred-module labels, still seven after Epic 5. Swedish UI labels map to English lowercase route paths. Epic 3's CRM/settings/pricing UI and Epic 5's Kalkyl editor live UNDER these existing nav destinations (e.g. `settings/pricing`, `/calculations` + `/calculations/[calculationId]`), never as new top-level nav.
- **UI data access runs on the per-request RLS server client, NEVER service-role.** Read modules (`src/features/*/read.ts`) and server commands drive the cookie-bound `@supabase/ssr` anon-key client; RLS scopes every read/write to the caller's tenant with no client-supplied tenant_id. This is enforced in CI by `verify:service-role-containment` (source) + `verify:bundle-containment` (built `.next`). This app uses NO service-role key on app paths. The established SERVER-ONLY convention is a documented file header + no `next/headers`/service-role import (the `server-only` npm package is NOT installed — do not `import 'server-only'`; it would add an undeclared dependency).
- **Never** add a deferred module — as a nav item, a route, or a placeholder. Specifically excluded: "Pilotstöd/Migrering" and all deferred modules (Fortnox, field-worker, supplier, AI, HR, rentals, assets/QR, DoU, tender/FKU, full RBAC, customer portal, analytics). Do not add feature-flag scaffolding for them either (avoid gold-plating). No audit-history dashboard/route/nav item yet — `audit_events` is substrate only; the read UI lands per-entity in its owning Epic 3-8 story.
- **Icons:** inline SVG `path` `d` strings on a shared 24×24 stroke viewBox (`NavIcon`). No icon library (AR28).
- The Phase A shell is intentionally hardcoded-light (`bg-zinc-50`/`bg-white`/`text-zinc-900`); there is deliberately no dark-mode / `forced-colors` theming yet. Do not reintroduce `@media (prefers-color-scheme: dark)` scaffolding.
- `AppShell` remains a client island (it owns `usePathname` + drawer state). When the shell grows, prefer splitting more static chrome into server components rather than enlarging the client island.

### Security Regression Harness Rules (standing contracts — Epic 2, enforced through Epic 5)

These are AUTOMATED, fail-closed gates that protect every later tenant-owned table and command. Treat their absence/weakening as a release blocker, not a story-level nicety.

- **Cross-tenant negative suite + H4 inventory gate are a single enrollment contract.** The tenant-table inventory `tests/integration/rls/tenant-table-inventory.ts` (`TENANT_TABLES` + per-table spoof/filter/mutation metadata, and the anon-path helpers) is the ONE place a tenant-owned table enrolls. The cross-tenant suite (`cross-tenant-isolation.rls.test.ts`), the anon-path suite (`anon-path-isolation.rls.test.ts`), AND the H4 gate (`rls-inventory-gate.int.test.ts`) all read it. **STANDING CONTRACT (Epics 3-9): any PR that adds or touches a tenant-owned table MUST enroll it in `TENANT_TABLES` (with metadata) BEFORE merge.** The H4 gate introspects the live schema (direct `tenant_id`, FK-to-`tenants` regardless of column name, partitioned parents, non-system schemas, plus the literal `tenants` root) and FAILS CI with a named "table not covered" message when a tenant-owned table is unenrolled — automated enforcement, not reviewer diligence.
- **The metadata model is compile-exhaustive on purpose.** Per-table helpers use `switch(table)` + `assertNever` so a future enrollee missing its metadata is a TYPECHECK error, not a silently mis-shaped (false-green) negative. Preserve this — broadening a fail-closed gate without an exhaustive type model creates false completeness.
- **Service-role containment is enforced at two layers, the bundle layer being authoritative.** Source guard `scripts/verify/check-service-role-containment.mjs` (`verify:service-role-containment`, in CI before build) flags `NEXT_PUBLIC_*SERVICE_ROLE*` names and `SUPABASE_SERVICE_ROLE_KEY` / the `LOCAL_SUPABASE_SERVICE_ROLE_KEY` re-export symbol referenced from a `"use client"` path. The AUTHORITATIVE built-bundle grep `scripts/verify/check-bundle-containment.mjs` (`verify:bundle-containment`, in CI AFTER `pnpm build` — order is load-bearing) scans the produced `.next` payload for any `*SERVICE_ROLE*` token, the JWT-shaped `"role":"service_role"` value, and `NEXT_PUBLIC_*SERVICE_ROLE*` names, and FAILS LOUD if `.next` is absent (never false-greens). This app uses NO service-role key (anon + RLS); a clean build yields zero hits.
- **`audit_events` is append-only and own-tenant-read.** A `BEFORE UPDATE OR DELETE` trigger blocks mutation; SELECT is own-tenant only. Note the trigger also blocks tenant on-delete-cascade of audit rows — privileged test cleanup must delete audit rows before the tenant. Audit metadata is allow-listed + sanitized; never persist raw input.

### Critical Don't-Miss Rules

- **Service-role key is SERVER-ONLY.** It bypasses RLS. Never prefix it `NEXT_PUBLIC_`, never import it (or any re-export symbol like `LOCAL_SUPABASE_SERVICE_ROLE_KEY`) into a browser/client path. Any server-side use must be documented (file + purpose) and test-covered. This app currently uses NO service-role key on app paths (anon + RLS); the source + built-bundle containment guards enforce it in CI.
- **RLS-by-default + GRANTs:** a new tenant-owned table is not done until it has (a) `tenant_id` scoping (or is the `tenants` root), (b) enable+`force` RLS with own-tenant policies built on the DEFINER helpers, (c) explicit role GRANTs (`anon -> none`), and (d) enrollment in `TENANT_TABLES`. Missing any one is a tenant-isolation or availability defect.
- **Secrets never get committed.** `.env` and `.env.*` are gitignored; ONLY `.env.example` is whitelisted, and it holds PLACEHOLDERS ONLY — never real project refs, keys, URLs, or PII. Only `NEXT_PUBLIC_`-prefixed vars are exposed to the browser. Do not echo `.env*` contents into prompts.

- **Stay in Phase A scope.** Do not create migrations, add dependencies, edit `.env`, or modify app code for process-only tasks. If a change touches a deferred module, stop unless there is explicit re-approval in the PR description and a linked planning artifact.
- **CI `pnpm build` is non-hermetic** (the Next scaffold fetches a Google font over the network). Acceptable on networked GitHub runners; revisit (switch to `next/font/local`) only when CI must run network-restricted.
